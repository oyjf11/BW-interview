## 一、基础认知：第一道分水岭

### Q1　Chatbot、Workflow、Autonomous Agent 三者本质区别

- 🔵 **考察点**：是否能用体系化认知区分三者，而非背定义；能否说出"自主性双刃剑"
- 🟢 **参考答案要点**
  - Chatbot：单轮 LLM 应答，无工具无规划无记忆
  - Workflow：代码定义固定流程，工具调用预定义，不可动态调整
  - Agent：LLM 自主决策，Thought→Action→Observation 循环，可反思纠正
  - 架构师级认知：Agent 的自主性是双刃剑——给太多不可预期，给太少退化 Chatbot；工程挑战是设计安全的自主边界
- 🟡 **加分项**
  - 能举例三个范式在同一生态中的角色（如 sre-agent 中 LangGraph workflow 编排 + ReAct agent 执行 + chat 前端）
  - 能说清决策主体不同导致的可观测性差异：Agent 需要轨迹追踪，Workflow 只需要节点状态
- 🔴 **危险信号**
  - 只说"Agent 更智能"而不分析工程代价
  - 把 Workflow 和 Agent 混为一谈
  - 背出三者区别但说不出生产环境里的坑

### Q2　Agentic Loop：Thought → Action → Observation 循环

- 🔵 **考察点**：是否理解 ReAct 循环是 Agent 系统的底层通信协议，而非概念层
- 🟢 **参考答案要点**
  - 标准循环：用户输入 → Thought（LLM 推理）→ Action（工具调用）→ Observation（工具结果）→ 循环至目标
  - 消息格式：`<tool_response>` 以 `role: "tool"` 返回给模型（OpenAI function-calling 格式），模型在下轮推理中引用结果
  - 循环终止条件：任务完成 / 反思判定无需继续 / 达到最大步数
- 🟡 **加分项**
  - 能画出完整的循环流程图并标注每一步的数据结构
  - 能区分 ReAct（边想边做）vs Plan-and-Execute（先规划再执行）vs Hierarchical（多层规划）的循环形态差异
- 🔴 **危险信号**
  - 不知道 tool_response 传回模型的角色是什么
  - 把 ReAct 说成"Reality Action"（正确是 Reasoning + Acting）

## 二、核心架构五大模块

### Q3　感知模块设计

- 🔵 **考察点**：需求澄清机制、多模态输入处理、输入规范化
- 🟢 **参考答案要点**
  - 核心目标：精准理解用户终极目标，感知环境变化
  - 意图识别：规则引擎 + LLM 双校验（规则快速兜底，LLM 处理模糊输入）
  - 输入规范化：多来源（标准输入、告警事件、工单 API）统一转结构化对象；环境/服务/时间范围做标准化处理
- 🟡 **加分项**
  - 能说出多模态处理路径（语音转文字→文本归一化→LLM）
  - 能举例感知失败时的降级策略（规则兜底→未知类型→转人工）
- 🔴 **危险信号**
  - 只说"用 LLM 理解用户意图"而没有具体 pipeline
  - 忽略多模态的工程挑战（格式统一、延迟控制）

### Q4　规划模块设计——从 CoT 到 ReAct 到 Hierarchical Planning

- 🔵 **考察点**：能否说出各规划范式的原理、适用场景及其升级原因
- 🟢 **参考答案要点**
  - CoT：模型逐步写出推理过程，只能"想"不能"做"——纯文本空间推理
  - ReAct：Thought→Action→Observation 循环，边想边做——因为真实任务需要跟外部世界交互
  - Plan-and-Execute：先全局拆解再串行执行——流程固定场景效率高，但不适应变化
  - Hierarchical：顶层目标→中层子任务→底层执行——工业级最常用，兼顾效率与灵活性
  - Reflexion：每步自我反思，失败则回滚重规划——长任务/高可靠性场景
- 🟡 **加分项**
  - 能提出"混合模式"：规划用强模型（GPT-4），执行层用弱模型做确定性校验（成本优化）
  - 能举例故障类型驱动的层次化规划（如 deployment_regression → K8s 检查 + DB 检查 + 日志检查三个并行子任务）
- 🔴 **危险信号**
  - 只知道 CoT 和 ReAct，说不出什么时候需要升级
  - 把 ReAct 说成"比 CoT 快"（ReAct 更慢，因为要跟外部交互）
  - 说不出 Reflexion 和普通错误重试的本质区别

### Q5　行动/工具模块设计——工程落地核心难点

- 🔵 **考察点**：工具 Schema 设计、参数校验、重试策略、安全沙箱、工具爆炸治理
- 🟢 **参考答案要点**
  - Schema 设计：强类型 JSON Schema，描述清晰（避免模型误调），参数校验层拦截非法调用
  - 重试策略：指数退避 + 最大重试次数（如 tenacity 库，2 次重试，1-10s 退避）
  - 安全控制：禁止关键操作工具（如 execute_action 列入 FORBIDDEN_TOOLS），按 Agent 白名单授权
  - 审计追踪：每次工具调用记录：工具名、参数（脱敏）、结果、耗时
- 🟡 **加分项**
  - 能说出工具风险分级（L0 只读→L3 生产高危需人工审批）
  - 能举例工具预筛选策略：向量化工具描述→检索 Top-5→LLM 再选
  - 能说出容错降级：工具不可用时自动降级到 mock 模式或规则兜底
- 🔴 **危险信号**
  - 只说"定义 function calling schema"而忽略参数校验和容错
  - 不知道重试策略需要指数退避（直接重试 3 次）
  - 没考虑工具调用的安全边界（谁都能调 exec_command）

### Q6　记忆模块设计——2026 年最硬核考点

- 🔵 **考察点**：四层记忆架构、记忆治理（写入污染、召回污染、选择性遗忘）、基于检索 vs 基于权重的记忆
- 🟢 **参考答案要点**
  - L1 工作记忆：当前任务上下文，会话结束销毁，直接入 LLM 上下文窗口
  - L2 短期记忆：会话历史、证据收集，滚动窗口 + 摘要压缩，用 checkpoint 持久化
  - L3 长期记忆：跨会话经验、知识库、历史案例，向量检索（ChromaDB/Pinecone）+ RAG
  - L4 认知记忆：人工确认后的知识写回（runbook），供未来运行使用
  - 记忆治理三大坑：写入污染（过滤低价值信息）→ 召回污染（相似度+时效性过滤）→ 遗忘（过期淘汰）
- 🟡 **加分项**
  - 能点出"基于检索的记忆（Memo）vs 基于权重的记忆（True Memory）"区分
  - 能说出向量+FTS5 关键词混合检索（RRF 融合）在记忆召回中的应用
  - 能举例记忆污染的具体案例和解决方案
- 🔴 **危险信号**
  - 只知道短期记忆和长期记忆，说不出工程实现差异
  - 不知道记忆需要治理（认为"存越多越好"）
  - 说不出 RAG 在记忆系统里的角色

### Q7　反思模块设计

- 🔵 **考察点**：反思触发机制、Reflexion 框架理解、反思频率与系统质量的关系
- 🟢 **参考答案要点**
  - 核心价值：每步执行后自我检查——"这步做对了吗？偏离目标了吗？"
  - 工业实现：Critic 节点评估证据质量和诊断置信度，四路路由：通过→继续 | 缺证据→补采 | 矛盾→重规划 | 超限→转人工
  - 反思频率解读：太高=规划差，太低=没兜底
- 🟡 **加分项**
  - 能说出 Reflexion 与简单重试的本质区别：Reflexion 会分析失败原因并调整策略，重试只是重复
  - 能举例 outcome-level 验证（如部署后检查实际 K8s 状态，不信任执行器的返回）
- 🔴 **危险信号**
  - 把反思等同于"让 LLM 再回答一次"
  - 不知道反思需要循环上限（防止无限反思）
  - 只说"用 LLM 做反思"，不知道代码层也可以做规则检查

## 三、MCP 协议：从加分题变必答题

### Q8　MCP vs 传统 Function Calling

- 🔵 **考察点**：是否理解 MCP 的根本改进不只是"标准化"，而是"把工具从一次性编码变成可复用资产"
- 🟢 **参考答案要点**
  - 工具定义：MCP 统一协议，一次定义到处用；Function Calling 每个厂商语法不同
  - 新增工具：MCP 动态发现即插即用；Function Calling 改代码部署重启
  - 执行标准：MCP 自带权限/审计/监控/限流；Function Calling 全靠自己硬编码
  - 可复用性：MCP Server 写一次，所有 Agent 所有项目所有模型都能用
  - 深一层理解：MCP 让工具治理从散乱变集中，安全可观测性强一个量级
- 🟡 **加分项**
  - 能说出 MCP 在生产环境的关键价值：治理集中+审计全量+版本管理
  - 能区分"MCP 协议"和"MCP Server 实现"两个概念
  - 能用 Tool Gateway 类比 MCP（capability discovery + schema validation + retry + audit）
- 🔴 **危险信号**
  - 只说"MCP 更标准"而没有深入分析
  - 不知道 MCP 的服务端/客户端架构
  - 把 Function Calling 说成"传统方法过时了"（MCP 底层还是 function calling 格式）

### Q9　MCP 工具爆炸治理

- 🔵 **考察点**：工具数量爆炸时的管理策略
- 🟢 **参考答案要点**
  - 分类标签：按功能/领域分类，给 Agent 分配工具白名单（如 k8s agent 只看 k8s 工具）
  - 元数据管理：每个工具记录描述、参数、风险等级、超时、重试策略
  - 权限控制：按 Agent 角色/场景控制工具可用范围
  - 配置化加载：工具可用列表从 YAML 配置加载，动态校验可用性
- 🟡 **加分项**
  - 能说出向量检索做工具预筛选的完整方案
  - 能区分静态工具（代码注册）vs 动态工具（MCP 发现）的管理差异
  - 能举例工具分级 + 白名单如何防止 LLM 误调用不相关工具
- 🔴 **危险信号**
  - 只说"放到知识库里检索"而没有具体策略
  - 没考虑工具调用的权限边界

## 四、多 Agent 协作：架构师核心区分点

### Q10　四种协作模式与适用场景

- 🔵 **考察点**：是否理解四种模式的结构、适用场景和取舍
- 🟢 **参考答案要点**
  - Boss-Worker（中心化）：主 Agent 拆解分配，子 Agent 执行——任务分工明确，适合故障排查
  - Pipeline（流水线）：A 输出→B 输入——流程化任务，适合内容生成管线
  - Joint Discussion（民主协作）：多 Agent 并行运行，结果聚合合成——需要多视角分析
  - Handoff（交接）：Agent A 做不了→转给 Agent B——能力边界清晰
- 🟡 **加分项**
  - 能说明为什么 sre-agent 采用 Boss-Worker + Joint Discussion 混合：planner 分配任务（Boss-Worker），specialist 并行采集（Joint Discussion）
  - 能说出 Handoff 和重路由的区别（Handoff 是 agent-to-agent，重路由是 orchestrator-to-node）
- 🔴 **危险信号**
  - 把四种模式全说成"多 Agent 协作"而不区分中心化/去中心化
  - 说不出每种模式适合什么场景

### Q11　多 Agent 三大坑及解决方案

- 🔵 **考察点**：是否能识别多 Agent 系统的工程风险并给出具体解决方案
- 🟢 **参考答案要点**
  - **无限循环**：两个 Agent 互相等待或反思→重规划循环
    - 解法：状态机控制 + 最大迭代次数（MAX_STEPS=30，recursion_limit=50）+ loop_count 超限转人工
  - **通信冗余**：Agent 间传递重复信息，Token 爆炸
    - 解法：结构化 prompt 构建 + 独立并行执行 + 超时取消（300s 硬超时）
  - **错误放大**：一个 Agent 的错误被下游放大
    - 解法：独立执行隔离 + 优雅降级（每个 specialist 失败不影响其他）+ 能力预检
- 🟡 **加分项**
  - 能说出 loop_count 机制的具体设计：每次 critic 循环 +1，超限强转 NEEDS_HUMAN + 记录 terminal_reason
  - 能说出 LLM 置信度封顶（0.9）在多 Agent 场景的作用：防止一个 agent 的过度自信影响聚合决策
  - 能说出独立执行 vs 串行依赖的权衡：何时该隔离，何时该串行
- 🔴 **危险信号**
  - 只说"加超时"而不提循环检测机制
  - 不了解 error amplification（错误放大）在多 Agent 中的严重性

### Q13　关键设计决策

- 🔵 **考察点**：对采样策略、上下文存储、告警策略、多 Agent 追踪、规划/执行模型分离的实际判断力
- 🟢 **参考答案要点**
  - Trace 采样：全量记录（小规模）+ 错误全量+慢请求全量+正常 10%（大规模）
  - 上下文存储：短期 graph state（内存 TypedDict）+ checkpoint 持久化（SQLite 序列化）+ 长期向量库
  - 告警策略：固定阈值（成功率<95%）+ ML 异常检测（延迟突变）组合
  - 多 Agent 追踪：必须关联！run_id 串联 A2A 通信，子 span 挂在父 span 下形成 trace tree
  - 规划与执行分离：规划节点生成任务计划，执行节点 interpret，对高风险操作做能力预检
- 🟡 **加分项**
  - 能说出全量 trace 的成本估算和降采样策略
  - 能说出 trace tree 结构（graph span → node span → specialist span → tool_call span）
- 🔴 **危险信号**
  - 不知道上下文该存多少（全量存 vs 摘要存）
  - 多 Agent 追踪用独立 trace_id（无法串联）

### Q14　异常处理四层防御体系

- 🔵 **考察点**：是否能设计完整的防御体系，从输入到输出层层拦截
- 🟢 **参考答案要点**
  - **L1 输入护栏**：输入规范化（env/service/time_range）+ 三级分诊降级（规则→LLM→兜底）
  - **L2 推理护栏**：输出值校验（enum 强制转换，非法值→other）、LLM 置信度封顶 0.9
  - **L3 输出护栏**：风险门（risk_gate）→ 关键操作+生产环境+低置信度 → BLOCKED；能力预检→不可用工具→NEEDS_HUMAN；无人信任证据→不生成操作
  - **L4 业务护栏**：部署后验证（实际 K8s 状态检查 + 健康检查 + 流量检查），而非信任执行器返回
- 🟡 **加分项**

  - 能举例"从不生成无证据操作"这个业务护栏的代码实现
- 🔴 **危险信号**
  - 只说"加个 guardrail"而没有分层设计
  - 忽略输出护栏（以为输入检查就够了）

## 六、RAG 检索优化

### Q15　RAG 完整链路设计

- 🔵 **考察点**：是否理解 RAG 的完整链路及每步的工程实现
- 🟢 **参考答案要点**
  - 文档→分块（chunk_size=512，overlap=80）→向量化（text-embedding-v2）→向量检索（ChromaDB 余弦相似度）→关键词检索（FTS5）→RRF 融合→重排序（gte-rerank-v2）→生成
  - 查询端：query 改写（停用词过滤+术语扩展）→召回（candidate_k=top_k×3）→重排序压缩 → 生成
- 🟡 **加分项**
  - 能画出 parent-child chunking（小→大检索）流程图
  - 能说出 RRF（Reciprocal Rank Fusion）的公式和 k=60 的含义
  - 能区分 ingestion pipeline 和 query pipeline
- 🔴 **危险信号**
  - 只说"用向量数据库检索"而忽略完整链路
  - 不知道为什么需要 rerank

### Q16　RAG 高频追问

- 🔵 **考察点**：对 RAG 工程细节的真实理解
- 🟢 **参考答案要点**
  - **为什么切片？** 上下文窗口限制 + 检索粒度 + 避免信息稀释
  - **切片大小？** 512 tokens，取决于 Embedding 模型最大输入长度和业务精度需求
  - **Overlap？** 80 tokens，约 15% 重叠率，确保边界语义连续
  - **为什么要 Rerank？** 向量检索侧重语义相关性，Rerank（cross-encoder）补足精确匹配，解决"语义对但答案不对"
  - **Top-K？** 召回 K=5，候选扩展 3x→15 条，Rerank 后压缩到 3-5
  - **稠密 vs 稀疏？** 稠密（向量/语义）+ 稀疏（FTS5 关键词）混合检索，RRF 融合效果最好
- 🟡 **加分项**
  - 能说出重叠率计算公式和选择依据
  - 能区分 bi-encoder（向量检索）和 cross-encoder（rerank）的计算复杂度差异
- 🔴 **危险信号**

## 七、评测体系设计

### Q17　三层评估框架

- 🔵 **考察点**：是否能设计多维评估体系，不只是"答案对不对"
- 🟢 **参考答案要点**
  - **L1 任务级**（结果对不对）：最终答案正确率、目标达成率、incident_type 分类准确率
  - **L2 过程级**（推理对不对）：Runtime Fidelity——checkpoint 是否完整、事件是否记录、DB 是否持久化
  - **L3 组件级**（能力边界在哪）：RAG 召回率（Recall@K）、MRR、NDCG；工具调用成功率
- 🟡 **加分项**
  - 能说出轨迹评测（Trajectory Eval）——评估每一步 Thought/Action 质量——是 2026 新趋势
  - 能说出 RAG 评估的 A/B/C/D/E 五路对比方案（裸向量/加改写/加重排序/关键词/混合）
- 🔴 **危险信号**
  - 只说"用 LLM 评测"而没有多层设计
  - 不知道过程级评测测什么

### Q18　LLM-as-Judge 自恋偏见

- 🔵 **考察点**：是否知道 LLM-as-Judge 的局限及解决方案
- 🟢 **参考答案要点**
  - 偏见来源：同一个模型家族评分倾向于给"自己风格"的输出更高分
  - 解法 1：**避免 LLM-as-Judge**——用封闭 enum 值做严格字符串等值比较，这是本项目的实际做法
  - 解法 2（若必须用）：多 Judge 投票 + Judge 模型与被评模型解耦 + 金标集校准 + 定期人工校准
  - 关键洞察：评估的正确性比评估的速度更重要——确定性评分 > 快速评分
- 🟡 **加分项**
  - 能说出 how to design an eval system that is 100% reproducible（封闭输出空间+确定性评分函数）
  - 能说出人机一致性指标（Human-Agreement Score）的作用
- 🔴 **危险信号**
  - 盲目信任 LLM-as-Judge 而不提偏见
  - 不知道可以用确定性方案替代

## 八、架构设计真题

### Q19　设计一个生产级 Agent 系统（以 SRE 故障处置为例）

## 九、自研 vs 框架选型

### Q20　为什么不用 LangChain/LangGraph，选择自研/治理平台？

- 🔵 **考察点**：是否有框架选型的独立判断力，而非跟风
- 🟢 **参考答案要点**
  - 治理优先于框架："不从买哪个 Agent 框架开始，而是从一个更硬的目标开始：把 AI 研发升级成企业可治理、可评测、可追责、可复用的工程系统"
  - LangChain 的问题：多层抽象遮挡日志和请求链路，调试困难；性能损耗；定制化差
  - 自研平台的优势：每一层都能埋点、每一层可替换、治理集中在控制平面
  - 两个项目的互补关系：sre-agent 用 LangGraph 做 Agent 实现（快速落地），harness-system 做治理平台（长期治理）——不是互斥而是互补
- 🟡 **加分项**
  - 能说出什么时候该用框架（快速验证），什么时候该自研（长期治理需求）
  - 能说出 LangGraph 的优点（StateGraph 内置 checkpoint 和 conditional routing）和适合的场景（复杂状态机）
- 🔴 **危险信号**
  - 盲目拥护或盲目贬低某一框架
  - 说不出选型的具体理由，只有"大家都在用"
  - 没分清 Agent 实现框架和治理平台的不同定位
