# Prompt 工程与上下文工程 面试官评分手册

**方向**：Prompt Engineering & Context Engineering
**岗位画像**：技术专家 / 架构师
**题量**：20 题，分 5 个模块
**建议时长**：单题 5–8 分钟，可深挖追问；整套 45–60 分钟取其中 6–10 题
**最能拉开档次**：Q3 / Q9 / Q10 / Q11 / Q14 / Q17 / Q20

---

## 使用说明

- 每题给出四部分：**考察点**（看什么）、**参考答案要点**（及格线在哪）、**加分项**（优秀候选人会说什么）、**危险信号**（出现即扣分）。
- 参考答案要点是「评分锚点」，不要求逐字命中；候选人用自己的话覆盖核心思想即可。
- 加分项往往是区分「会调 prompt」与「懂上下文工程系统设计」的关键，重点关注。
- 危险信号若反复出现，说明候选人停留在「调 demo」层面，缺乏规模化与可靠性认知。
- 所有题目均为开放题，鼓励顺着候选人的回答追问到底，观察其思考深度而非记忆量。

# 一、Prompt 基础与设计原则

## Q1 　 system / developer / user 三类消息的职责边界

**🔵 考察点**

- 是否理解不同 role 的优先级、持久性与用途差异，而非把所有内容堆进一个 prompt。
- 对「指令该放哪一层」的工程判断。

**🟢 参考答案要点**

- system/developer：设定稳定的角色、规则、输出契约、安全边界，全程生效、不随单轮变化；user：承载具体任务与变量输入。
- 稳定且高优先级的约束放系统层（模型对其遵从度更高、更难被后文覆盖）；易变的任务上下文放 user 层。
- 三层存在优先级：系统指令应压过用户的越界请求；这是安全与一致性的基础。
- 工程上把「不变的部分」与「每次变的部分」分离，利于缓存、复用与维护。

**🟡 加分项**

- 讨论不同模型对 system 层遵从度的差异，主张关键约束冗余表达而非只放一处。
- 把系统提示版本化、与代码一起管理，而非散落在业务里硬编码。
- 意识到系统层过长会挤占预算、稀释关键指令，需精炼。

**🔴 危险信号**

- 把所有东西都塞进一条 user message，不分层。
- 把易变的任务数据写进系统提示，导致无法缓存、频繁改。
- 认为 role 只是格式，没有优先级与遵从度含义。

## Q2 　清晰指令的设计：约束、格式、示例怎么给

**🔵 考察点**

- 能否把模糊需求翻译成模型可稳定执行的明确指令。
- 对「过度约束 vs 欠约束」的平衡感。

**🟢 参考答案要点**

- 明确：任务目标、输入说明、输出格式与字段、边界与禁止项、失败/缺数据时该怎么办。
- 用正例 + 反例界定期望；对易歧义处给具体示例(few-shot)消除分歧。
- 把「做什么」与「不做什么」都说清；对格式用显式 schema/模板而非口头描述。
- 指令顺序与结构化(分段/标题/分隔符)影响遵从度，关键约束前置或重申。

**🟡 加分项**

- 区分「指令式」与「示例式」哪个更可靠：规则清晰用指令，难言说的风格用示例。
- 给「兜底分支」：数据缺失/无法完成时输出什么，避免模型自由发挥。
- 意识到约束越多越可能冲突，需检查指令间矛盾。

**🔴 危险信号**

- 指令含糊(「写得专业一点」)却期待稳定输出。
- 只给正例不给边界，模型在边缘 case 乱来。
- 堆砌大量相互冲突的规则，自己都没核对一致性。

---

## Q3 　结构化输出：JSON mode、function calling 与受限解码

**🔵 考察点**

- 对「让模型稳定产出可机读结构」的多种手段及其可靠性差异。
- 是否知道为何「prompt 里要求输出 JSON」不够可靠。

**🟢 参考答案要点**

- 手段从弱到强：prompt 要求 → JSON mode → 工具/函数调用的 schema 约束 → 受限解码(constrained decoding/grammar)强制合法。
- 纯 prompt 要求不可靠：模型可能加解释、漏字段、格式错；受限解码从采样层保证语法合法。
- 用 schema 校验做最后兜底，校验失败回灌错误让模型修正或重试。
- 权衡：受限解码最稳但可能限制表达/增加集成成本；JSON mode 是常见折中。

**🟡 加分项**

- 区分「语法合法」与「语义正确」：受限解码只保证前者，字段值对不对还得校验。
- 讨论结构化约束对模型推理质量的潜在副作用(强约束可能压制 CoT)，必要时先想后输出。
- 对流式 + 结构化的组合处理(增量解析)有方案。

**🔴 危险信号**

- 只在 prompt 里写「请返回 JSON」就当稳了，无校验无重试。
- 不知道受限解码/JSON mode 的存在。
- 解析失败直接报错，不回灌纠正。

## Q4 　 Prompt 的可维护性与版本化工程

**🔵 考察点**

- 是否把 prompt 当「代码/配置」严肃管理，而非散落的字符串。
- 架构师视角：规模化后 prompt 的治理。

**🟢 参考答案要点**

- prompt 与代码解耦、版本化(模板 + 变量)，纳入评审与变更记录；改 prompt 等同改逻辑，需可回滚。
- 模板化：固定骨架 + 插槽变量，避免拼字符串散落各处；统一管理便于复用与一致性。
- 每次改动配评测回归(见后续题)，防止「改好一个 case 改坏一片」。
- 环境隔离：开发/灰度/生产用不同版本，灰度验证后再全量。

**🟡 加分项**

- 建立 prompt 注册中心/配置化，支持 A/B 与灰度。
- 记录每个 prompt 版本对应的评测分数，可追溯。
- 区分「面向模型的 prompt」与「面向人的文档」，两者一致但分开维护。

**🔴 危险信号**

- prompt 以裸字符串硬编码散落代码各处。
- 改 prompt 不评测、不灰度，直接上线。
- 无版本无回滚，出问题不知道改了什么。

# 二、推理范式与高级提示技巧

## Q5 　 CoT / 思维链：原理、适用与代价

**🔵 考察点**

- 理解 CoT 为何有效、何时该用、何时反而有害。
- 对「显式推理 vs 直接输出」的成本与质量权衡。

**🟢 参考答案要点**

- CoT 让模型显式分步推理，对多步/逻辑/数学类任务能显著提升正确率。
- 代价：更多 token、更高延迟与成本；对简单任务收益小甚至画蛇添足。
- 适用：复杂推理、需要中间步骤可检查的场景；不适用：简单分类/抽取(直接输出更快)。
- 推理链可被隐藏(只取最终答案)或保留(供审计/调试)，按需取舍。

**🟡 加分项**

- 区分「让模型想」与「让用户看到想的过程」是两件事，可解耦。
- 提到推理型模型已内化 CoT，外部再强加 CoT 可能冗余甚至干扰。
- 讨论 CoT 暴露的中间步骤也可能成为攻击/泄露面。

**🔴 危险信号**

- 无脑给所有任务都套 CoT，徒增成本。
- 认为 CoT 一定提升效果，不看任务类型。
- 不知道 CoT 的 token/延迟代价。

## Q6 　 Few-shot 示例工程：选择、数量、顺序

**🔵 考察点**

- 对示例如何影响输出的细致认知(不只是「多给几个例子」)。
- 示例工程中的隐蔽坑(分布偏差、顺序敏感、标签泄漏)。

**🟢 参考答案要点**

- 示例要覆盖目标分布与边界 case，代表性比数量重要；过多示例占预算且收益递减。
- 示例的格式即「隐式指令」：模型会模仿示例的风格/结构，故示例须与期望输出严格一致。
- 顺序会影响结果(近因/位置效应)，对顺序敏感的任务需注意；可固定或检验。
- 动态 few-shot：按当前输入检索最相关示例(类似 RAG)，比固定示例更优。

**🟡 加分项**

- 提到示例的标签/格式不一致会「教坏」模型，须严格清洗。
- 讨论 few-shot vs 微调的边界(高频稳定任务可考虑微调省 token)。
- 动态示例检索 + 去重，避免与当前输入雷同或冲突。

**🔴 危险信号**

- 示例分布偏(只给简单例子)却期待覆盖难 case。
- 示例格式不统一，模型学到混乱模式。
- 盲目堆很多示例，撑爆上下文又无增益。

## Q7 　 ReAct 等「推理+行动」范式与 agent 的关系

**🔵 考察点**

- 理解 ReAct(reason-act-observe)如何把推理与工具调用结合，是 agent 循环的提示层基础。
- 对范式落地时的可靠性问题的认知。

**🟢 参考答案要点**

- ReAct：模型交替产出「思考」与「行动(工具调用)」，根据观测继续，形成 agent 的基本循环骨架。
- 提示层定义思考/行动/观测的格式，运行时(harness)解析行动并回灌观测——提示与运行时配合。
- 可靠性问题：模型可能产出不合法行动、思考与行动不一致、陷入循环，需 harness 侧约束。
- 现代 function calling 已把「行动」结构化，比纯文本 ReAct 更稳。

**🟡 加分项**

- 明确 ReAct 是提示范式，真正生产可靠性靠运行时硬约束，两者不可混为一谈。
- 对比 ReAct 与 plan-and-execute 等其他 agent 范式的取舍。
- 讨论思考过程是否计入上下文(占预算)与是否暴露的权衡。

**🔴 危险信号**

- 把 ReAct 当万能，忽略其在生产中的不稳定。
- 分不清提示范式与运行时编排的职责。
- 认为有了 ReAct prompt 就不需要工具校验与停止条件。

## Q8 　自洽性、自我反思与多轮校验(self-consistency / reflection)

**🔵 考察点**

- 对「用多次采样/自我批判提升质量」类技巧的理解与代价权衡。
- 能否判断这些技巧的真实收益边界。

**🟢 参考答案要点**

- self-consistency：多次采样取多数/聚合，降低单次随机性带来的错误，代价是成倍成本。
- reflection/self-critique：让模型审视并修正自己的输出，对可验证错误有效。
- 适用复杂、易错、值得加成本的任务；对简单任务或模型「看不出自己错」的场景收益有限。
- 关键：反思需有「外部信号」(工具结果/校验)才更可靠，纯自我反思可能自我强化错误。

**🟡 加分项**

- 指出纯自我反思的局限：模型对自身盲区无感，需外部 grounding。
- 讨论 self-consistency 的成本-收益曲线，按价值决定采样数。
- 把反思与可验证器(单元测试/校验函数)结合，形成闭环。

**🔴 危险信号**

- 迷信「让模型自己再检查一遍」必然变好。
- 无视多次采样的成本翻倍。
- 纯自我反思无外部信号，反而固化错误。

# 三、上下文工程

## Q9 　上下文工程 vs prompt 工程：边界与重心

**🔵 考察点**

- 能否清晰区分两者：prompt 是「怎么写指令」，上下文工程是「在有限窗口内放什么、怎么组织、怎么动态装配」。
- 对「上下文是 agent 时代核心瓶颈」的认知。

**🟢 参考答案要点**

- prompt 工程偏静态指令设计；上下文工程偏动态信息装配——决定每一步窗口里放哪些历史、检索结果、工具返回、记忆。
- 核心问题：窗口有限且贵，要在「信息充分」与「精简降噪」间最优装配；放错/放多都会降质且烧钱。
- 上下文工程贯穿：组织顺序、相关性筛选、压缩摘要、外置与召回、去重去噪。
- agent 多轮场景下，上下文是动态变化的工程对象，而非一次写定的 prompt。

**🟡 加分项**

- 提出「上下文是一种受限预算资源，需主动分配管理」的视角。
- 讨论上下文中噪声/无关信息对模型的干扰(分心、被误导)。
- 把上下文装配本身做成可观测、可调试的环节。

**🔴 危险信号**

- 认为上下文工程就是「写好 prompt」，分不清动静态。
- 无视窗口预算，能塞就塞。
- 看不到上下文质量对 agent 行为的决定性影响。

---

## Q10 　上下文窗口预算的分配与组织

**🔵 考察点**

- 在有限 token 内做信息取舍的工程能力。
- 对上下文内部「位置/顺序」影响的认知(lost in the middle 等)。

**🟢 参考答案要点**

- 把窗口当预算切分：系统指令、任务、关键历史、检索证据、工具结果、输出留白各占多少要有意识。
- 关键信息放在模型注意力强的位置(开头/结尾)，避免重要内容埋在长上下文中段被忽略。
- 按相关性筛选与排序，砍掉无关/重复内容；为输出预留足够 token。
- 随对话增长动态调整分配，老旧低价值内容压缩或移出。

**🟡 加分项**

- 明确提到「lost in the middle」现象并据此安排关键信息位置。
- 对不同信息源设优先级与配额，冲突时按优先级裁剪。
- 讨论长上下文模型「能放下」不等于「能用好」。

**🔴 危险信号**

- 把所有可得信息一股脑塞满窗口。
- 不知道上下文中段信息易被忽略。
- 不给输出留预算，导致被截断。

---

## Q11 　上下文压缩与摘要的「不丢关键依赖」

**🔵 考察点**

- 压缩历史时保留关键事实的细致度。
- 对摘要引入误差的风险意识。

**🟢 参考答案要点**

- **五种主流手段**：
  ① 硬截断（按条数/字符/token 一刀切，最简单但可能切断关键信息）；
  ② 摘要压缩（模型生成摘要替代原文，可细分为滚动摘要和增量摘要，核心风险是 lossy——丢精确值）；
  ③ 分层记忆（小 chunk 检索覆盖 + 大 chunk 按需取回完整上下文）；
  ④ 关键值钉住（ID、数字、句柄、未决待办标记 pinned 跳过压缩，只压缩叙述性文本）；
  ⑤ 外置引用（大结果不进上下文，只留摘要+引用句柄，LLM 需要时主动取回）。手段间不互斥，工程上常组合使用。压缩触发按窗口阈值/步数，压缩本身可能丢信息，需保留还原路径。

**🟡 加分项**

- 对关键值做 pinning(钉住不被压缩)。
- 讨论摘要质量本身需评估，劣质摘要比不摘更糟。
- 分层记忆 + 滚动摘要 + 事实保留组合方案。

**🔴 危险信号**

- 一把摘要丢掉后续要用的精确值。
- 认为摘要无损，不留还原路径。
- 无差别截断最早消息。

## Q12 　 RAG 上下文的组织：检索结果如何进 prompt

**🔵 考察点**

- 检索到的内容如何组织进上下文以最大化有用性、最小化误导。
- 对检索噪声、冲突证据、来源标注的处理。

**🟢 参考答案要点**

- 检索结果需筛选 + 重排(rerank)后再进上下文，只放最相关的 top-k，控制数量与噪声。
- 标注来源/出处，便于模型引用与事后溯源，也利于减少幻觉。
- 处理冲突证据：呈现多源时让模型知道存在分歧，而非默认第一条为真。
- 组织顺序与格式影响利用率；明确「答案应基于检索内容」并给「检索不足时怎么办」的兜底。

**🟡 加分项**

- 讨论「检索召回多」与「上下文噪声大」的张力，rerank 与裁剪是关键。
- 对检索内容与模型先验冲突时的策略(以检索为准 vs 标注不确定)。
- 提到引用/出处可做成结构化，支持答案可验证。

**🔴 危险信号**

- 把检索 top-N 原文不加筛选全塞进去。
- 不标来源，模型把检索内容与编造混在一起。
- 无「检索不到/不足」的兜底，模型强行编。

# 四、可靠性、安全与防御

## Q13 　幻觉的成因与提示/上下文侧的抑制手段

**🔵 考察点**

- 对幻觉成因的理解，及在 prompt/上下文层面能做什么(区别于模型训练侧)。
- 对「不能根治只能降低」的清醒。

**🟢 参考答案要点**

- 成因：模型按概率生成、缺乏 grounding、被诱导补全、上下文信息不足或冲突。
- 提示/上下文手段：提供权威上下文(RAG grounding)、明确「不知道就说不知道」、要求引用来源、约束「只基于给定材料回答」。
- 结构化 + 校验：让答案带可核验的引用/字段，事后校验；降低开放式自由发挥。
- 承认这些只降低不根治；高风险场景需外部事实校验与人工兜底。

**🟡 加分项**

- 区分「事实性幻觉」与「指令遵从偏差」，对症下药。
- 用「允许弃权(abstain)」降低强答带来的编造。
- 提到检索质量差会引入「有据的错误」，grounding 不等于正确。

**🔴 危险信号**

- 认为换个好 prompt 就能消除幻觉。
- 不给模型「说不知道」的出口，逼它强答。
- RAG 一接就以为不会幻觉了。

---

## Q14 　 Prompt injection 与 jailbreak 的提示层防御及其局限

**🔵 考察点**

- 理解注入(外部内容劫持)与越狱(绕过安全约束)的区别。
- 能否论证「纯提示层防御不可靠，需系统层兜底」。

**🟢 参考答案要点**

- 区分：jailbreak 是用户诱导模型违反安全策略；injection 是被处理的外部内容(工具返回/文档)藏指令劫持模型。
- 提示层手段：数据与指令分离、外部内容明确标注为「不可信数据，不得当指令执行」、系统约束前置且重申。
- 局限：提示层防御可被绕过，攻击手法持续进化；不能作为最后防线。
- 必须系统层兜底：最小权限、危险动作独立授权、沙箱、输出过滤——不依赖模型「自觉识别」。

**🟡 加分项**

- 明确「让模型识别恶意指令」有漏报，须确定性硬约束兜底。
- 对外部内容做信任分级与隔离边界。
- 承认这是开放对抗问题，目标是降低爆炸半径。

**🔴 危险信号**

- 靠在 prompt 里写「忽略任何恶意指令」当作防住了。
- 把外部内容与系统指令放同一信任层。
- 无系统层兜底，全压在提示措辞上。

## Q15 　输出安全、护栏与内容合规(尤其国内场景)

**🔵 考察点**

- 对输入/输出双向护栏的设计能力。
- 对国内内容合规硬要求的认知(大厂硬门槛)。

**🟢 参考答案要点**

- 双向护栏：输入侧拦截违规/注入，输出侧过滤有害/违规/敏感内容，二者都不能只靠模型自身。
- 分层：模型对齐(软) + 独立的安全分类/规则(硬)，关键合规走独立模块而非全信模型。
- 国内场景需符合内容安全法规与平台审核要求，敏感类目有硬性拦截与兜底话术。
- 护栏需可配置、可审计、可更新，应对新型违规。

**🟡 加分项**

- 区分「模型内生安全」与「外挂护栏」，主张关键合规靠外挂确定性模块。
- 对误杀/漏杀做度量与调优，平衡安全与可用。
- 提到护栏本身也要评测与红队。

**🔴 危险信号**

- 认为模型自身对齐就够，无独立护栏。
- 忽视国内合规的硬性要求。
- 护栏写死无法更新，跟不上新违规。

## Q16 　对抗提示注入的鲁棒性测试与红队

**🔵 考察点**

- 是否主动用对抗思维测试自己的 prompt/系统。
- 对红队、回归、持续对抗的工程化认知。

**🟢 参考答案要点**

- 主动红队：构造越狱/注入/诱导用例攻击自己的系统，发现弱点。
- 把已发现的攻击沉淀为回归测试集，每次改动/换模型都跑，防回退。
- 覆盖多种攻击面：用户输入、工具返回、被处理文档、多轮诱导。
- 持续更新攻击库，因为攻击手法不断进化；结合自动化对抗生成。

**🟡 加分项**

- 用自动化/对抗模型批量生成攻击用例，而非纯手工。
- 把安全测试纳入 CI/发布门禁。
- 度量「攻击成功率」并跟踪其随版本变化。

**🔴 危险信号**

- 只测正常用例，从不做对抗测试。
- 发现漏洞修了不沉淀为回归，下次又复现。
- 认为安全是一次性的，不持续对抗。

# 五、评测、优化与工程化

## Q17 　 Prompt 的评测：如何科学衡量「改好了」

**🔵 考察点**

- 能否建立客观评测而非「看几个例子感觉变好了」。
- 对评测集、指标、自动化的工程认知。

**🟢 参考答案要点**

- 建评测集：覆盖真实分布 + 边界 + 历史 bad case；带期望输出或评分标准。
- 指标按任务：可程序校验的用准确率/匹配；开放生成用 rubric + 人工/模型评审并校准。
- 每次改 prompt 跑全量回归对比基线，避免「修一个坏一片」；关注分项不只看均值。
- 考虑随机性：多次运行看分布与稳定性，而非单次。

**🟡 加分项**

- 区分离线评测与线上指标，建立对应。
- 对 LLM-as-judge 做一致性校验与抽检。
- 评测集防过拟合：holdout、持续刷新。

**🔴 危险信号**

- 凭手感判断 prompt 好坏，无评测集。
- 只看个别 case，无回归无基线对比。
- 忽略输出随机性，单次定论。

## Q18 　 Prompt 的成本与延迟优化

**🔵 考察点**

- 在保证质量前提下压成本/延迟的体系化手段。
- 对 prompt 长度、缓存、模型分级的权衡。

**🟢 参考答案要点**

- 精简 prompt：去冗余、压缩示例、外置可检索内容，降低每次 token。
- prompt 前缀缓存(KV cache 复用)：固定 system/前缀部分缓存，长固定前缀收益大。
- 模型分级：简单任务用小模型，复杂才上大模型。
- 权衡：精简过头可能掉质量、减少示例可能降稳定，需用评测验证而非拍脑袋。

**🟡 加分项**

- 量化「每个 token 的边际价值」，砍掉低价值内容。
- 用前缀缓存把固定部分前置以最大化命中。
- 用评测数据驱动「降本不降质」的边界。

**🔴 危险信号**

- 为省钱乱砍 prompt 导致质量下滑还不评测。
- 不知道前缀缓存可大幅降本降延迟。
- 所有任务一个大模型梭哈。

## Q19 　自动化 prompt 优化(APE / DSPy 类)与人工的边界

**🔵 考察点**

- 对自动化提示优化方法的了解与务实判断。
- 能否说清何时该自动化、何时仍需人工。

**🟢 参考答案要点**

- 自动化方法：用模型/搜索自动生成与筛选 prompt，或框架(如 DSPy)把 prompt 当可优化参数按指标调优。
- 前提是有可靠评测信号(指标/数据)，否则自动优化无方向。
- 适用：有明确指标、大量样本、需规模化调优的场景；人工仍负责目标设定、安全约束、定性判断。
- 务实：自动优化能省人力但非银弹，结果需人工校验，且可能过拟合评测集。

**🟡 加分项**

- 强调「自动优化依赖评测质量」，评测不行则优化跑偏。
- 把自动优化产物纳入回归与红队，防过拟合与安全退化。
- 讨论自动优化的可解释性差、难调试的代价。

**🔴 危险信号**

- 迷信自动优化是银弹，无评测就上。
- 自动优化结果不校验直接用。
- 完全不了解此类方法，认为只能手调。

## Q20 　跨模型的 prompt 可移植性与回归

**🔵 考察点**

- 对「换模型 prompt 行为会变」的认知与应对。
- 迁移/升级时防退化的工程方法。

**🟢 参考答案要点**

- prompt 不天然跨模型可移植：不同模型对指令格式、system 遵从度、输出风格、停止行为反应不同。
- 换模型/升版本前跑回归评测，对比关键指标与分项，发现行为漂移。
- 关键约束冗余表达、按模型能力(capability)而非假设统一来组织 prompt。
- 灰度 + 影子流量验证真实行为，门禁挡退化。

**🟡 加分项**

- 为不同模型维护必要的 prompt 变体而非强求一份通用。
- 把「换模型」当作需评测验证的变更，而非无感替换。
- 监控线上行为指标捕捉静默漂移。

**🔴 危险信号**

- 默认 prompt 换模型照样能用，直接替换。
- 升级模型不做回归评测。
- 强求一份 prompt 通吃所有模型，质量参差不查。
