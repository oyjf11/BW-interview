模块一：微调 vs RAG vs Prompt（灵魂拷问）

Q1　微调、RAG、Prompt Engineering 三者的本质区别是什么？

主接项目：sre-agent 的 LLM 客户端 + RAG 子系统 + Prompt 版本管理。三者都在项目里出现过，可以对照代码讲。

🟢 我命中的参考答案要点

  • ✅[真实] Prompt Engineering：sre-agent 的 prompt 版本管理系统（backend/app/prompts/registry.py:26-113）通过 SHA-256 校验和跟踪 triage_v1/diagnose_v1/rca_v1 三个 system prompt 版本，5 个 specialist agent 的 system prompt 定义在 backend/app/graph/nodes/agent_configs.yaml:1-272，每个都有结构化输出格式、分析步骤和异常信号定义——说明我们对 Prompt 的精细化管理和版本控制是有工程实践的
  • ✅[真实] RAG：完整的 RAG 子系统在 backend/app/rag/ 下，包含混合检索（retriever.py:147-160 向量 + FTS5 关键字 → RRF 融合 → reranker 重排）、DashScope 向量化（embeddings.py:6-10）、知识库索引（indexer.py:62-92），知识存储在外部 DashVector/ChromaDB 向量库中
  • ✅[真实] 微调（调用侧）：项目使用阿里云百炼平台的微调分类模型（backend/app/rag/intent_classifier.py:24），模型名 qwen3-0.6b-47263565a511，通过 DashScope API 调用，用于 SRE 意图 5 分类——这是一个已经微调好的模型，不是我们自己训的
  • ⚙️[补全] 微调（训练侧）：sre-agent 本身没有训练代码，但我会讲清楚微调本质是"改权重"——如果项目需要定制意图分类模型，流程是：准备标注数据 → LoRA/QLoRA 微调 qwen3-0.6b → 部署到百炼平台 → 通过 DashScope API 调用

🟡 我能拿到的加分项

  • ✅[真实] 可以画出实际的决策树：sre-agent 中需要知识新鲜度的场景（SRE runbook 会更新）→ 用 RAG，retrieve_memory.py:63-211 就是 RAG 检索入口；需要稳定格式输出的场景（specialist agent 的 JSON 分析格式）→ 用 agent_configs.yaml 中的详细 Prompt 约束；需要从根上改行为的场景（意图分类）→ 用微调
  • ✅[真实] 可以说出"RAG 解决知道什么，微调解决怎么想"——在我们的项目里，RAG 负责检索 runbook 知识让 agent "知道"排障步骤，意图分类器（微调模型）负责"理解"用户 query 的真正意图

🔴 危险信号（主动规避）

  • ❌ 别说"我们做了微调"——我们没有训练代码，只有调用微调好的模型。要准确说"使用了阿里云百炼平台的微调分类模型"
  • ❌ 别说"RAG 可以替代微调"——意图分类就是 RAG 做不了的事（需要理解 query 语义做 5 分类）

完整应答（口语稿）

这三者的本质区别在于"改了什么"。Prompt 什么都没改，只是改变了模型的输入文本；RAG 改变了模型看到的上下文，知识存在外部向量库里；微调是真正改变了模型的权重参数，知识刻进了模型本身。

成本上，Prompt 几乎零成本，RAG 中等（需要维护向量库和 embedding 服务），微调最贵（需要 GPU 和时间）。更新速度反过来：Prompt 即时生效，RAG 分钟级（更新知识库就行），微调要小时到天级别（得重新训练）。

我在 sre-agent 项目里三个都用过。Prompt 这边我们有一套版本管理系统，给每个 system prompt 做 SHA-256 校验和，三个核心 agent 角色（triage、diagnose、rca）各有独立版本，五个 specialist agent 的 system prompt 都在 YAML 里管理，每个定义了结构化输出格式和异常信号类型。RAG 这边我们有一个完整的混合检索 pipeline——向量检索加 FTS5 关键字检索，用 RRF 算法融合结果，再经过 DashScope 的 reranker 重排，知识存在 DashVector 向量库里。微调这边，我们没有自己训练，但使用了阿里云百炼平台的一个微调好的 qwen3-0.6b 模型来做 SRE 意图分类，把用户 query 分成故障诊断、查指标、查日志、查部署、知识问答五类。这个分类模型如果用 Prompt 做也可以，但准确率和稳定性不如微调模型——这就是"微调解决怎么想"的典型场景。

Q2　什么时候该上微调？给出三个信号。

主接项目：sre-agent 的意图分类器是「该上微调」的最佳案例。

🟢 我命中的参考答案要点

  • ✅[真实] 信号一：Prompt 调了很多轮效果仍不达标——sre-agent 的意图分类场景，如果用 Few-Shot Prompt 做 5 分类，prompt 模板在 intent_classifier.py:27-32 只是一个简单的 system prompt，实际分类依赖微调模型 qwen3-0.6b 来完成，说明分类精度要求超出了 Prompt 能兜住的范畴
  • ⚙️[补全] 信号二：任务需要稳定的格式/风格输出——在 sre-agent 中，specialist agent 的 JSON 分析格式通过 agent_configs.yaml 中的详细 prompt 约束，目前还没触发微调。但如果工具调用格式不稳定（频繁出现 JSON 解析失败），就该上 LoRA 微调 200-500 条数据来固化格式
  • ⚙️[补全] 信号三：有足够高质量标注数据（≥1000 条）——我们目前没有积累到这个量级的标注数据，但评估框架（backend/app/evals/）基础设施已经就绪，可以支撑数据标注 pipeline

🟡 我能拿到的加分项

  • ✅[真实] 能结合具体场景量化"Prompt 调了很多轮"——意图分类如果用 Prompt，需要在 prompt 里枚举每种意图的定义和边界，5 种意图的 Few-Shot examples 至少 15 条，token 成本高，且边界模糊的 case（比如 "pod 重启了" 属于诊断还是查日志？）Prompt 容易判断失误
  • ⚙️[补全] 能说出不同任务的数据量门槛——工具对齐 200-500 条，领域问答 1000-3000 条，代码生成 3000-5000 条。sre-agent 如果要做工具调用微调，优先从现有的 28 个工具调用日志中采样高质量样本

🔴 危险信号（主动规避）

  • ❌ 别说"我们有数据就可以微调"——要强调数据质量 > 数量，且微调有代价（训练成本、部署复杂度、模型退化风险）
  • ❌ 别说"我们打算微调所有场景"——要给出优先级：工具调用稳定性 > 意图分类 > 领域问答

完整应答（口语稿）

什么时候该上微调？我总结三个信号，三个同时出现就该动手了。第一个信号，Prompt 调了很多轮效果还是不达标。我们的意图分类器就是典型——如果用 Few-Shot Prompt 做五分类，你得在 prompt 里枚举每种意图的定义，至少写 15 条示例，token 成本很高，而且边界模糊的 case 比如"pod 重启了"，到底算故障诊断还是查日志？Prompt 很难稳定判断。所以我们直接用了阿里云百炼上微调好的 qwen3-0.6b 来做分类。

第二个信号，任务需要稳定的格式输出。比如我们 sre-agent 里的 specialist agent，分析结果要求输出结构化 JSON，现在靠 agent_configs.yaml 里的 prompt 约束基本能兜住，但如果将来工具调用格式频繁出问题、JSON 解析经常失败，那就是 Prompt 兜不住的信号，该上 LoRA 微调了。

第三个信号，有足够的高质量标注数据。门槛因任务而异——工具对齐 200 到 500 条就够了，因为格式约束强、模型容易学；领域问答要 1000 到 3000 条；代码生成要 3000 条以上。我们目前有评估框架跑着，但还没积累到足够的高质量标注数据。如果要做，优先级是工具调用稳定性 > 意图分类 > 领域问答。

Q3　RAG 和微调能互相替代吗？为什么？

主接项目：sre-agent 同时用了 RAG + 微调模型，是最佳反例。

🟢 我命中的参考答案要点

  • ✅[真实] 不能互相替代——sre-agent 就是活例子：RAG 负责检索 runbook 知识（retriever.py:147-160），微调模型负责意图分类（intent_classifier.py:24），两者各司其职
  • ✅[真实] RAG 管知识 freshness——sre-agent 的 runbook 知识库（knowledge/runbooks/ 目录下 33 个 markdown 文件）会随 SRE 经验持续更新，通过 indexer.py:62-92 索引到向量库，更新只需要重建索引，不需要重训模型
  • ⚙️[补全] 微调管行为 pattern——意图分类是"理解 query 语义"的 pattern，RAG 只能给相关信息，无法替代分类器的推理能力

🟡 我能拿到的加分项

  • ✅[真实] 能举出具体例子——"Kubernetes pod 一直重启怎么办"这个 query，RAG 能检索到 CrashLoopBackOff 的 runbook，但 RAG 无法判断这个 query 属于"故障诊断"意图还是"知识问答"意图，这个判断必须由意图分类器（微调模型）来做
  • ✅[真实] 能说出 2026 年标准答案——在我们的 retrieve_memory.py:63-211 里，RAG 检索和意图分类是串联的：先分类意图 → 根据意图调整检索策略 → 再检索 runbook。这就是 RAG + 微调的组合拳

🔴 危险信号（主动规避）

  • ❌ 别说"RAG 够强了不需要微调"——我们会明确说意图分类这块 RAG 做不了，因为 RAG 返回的是文档片段，不是分类标签
  • ❌ 别说"微调可以替代 RAG"——runbook 知识在持续更新，微调模型无法跟上知识的更新速度

完整应答（口语稿）

不能互相替代，这个结论可以从我们 sre-agent 项目里直接印证。RAG 管的是"知道什么"，微调管的是"怎么想"，两者解决的问题完全不同。

具体来说，我们有一个 RAG 子系统，里面存了 33 个 SRE runbook 文档，做混合检索——向量相似度加关键字匹配，再用 RRF 融合。runbook 会随着我们排障经验的积累不断更新，这时候只需要重建向量索引就能让 agent "知道"最新知识，不需要重训任何模型。这就是 RAG 的核心价值：知识新鲜度。

但 RAG 有个硬伤——它只能给信息，不能做推理。比如用户输入"pod 重启了怎么办"，RAG 能检索到 CrashLoopBackOff 相关的 runbook 片段，但它无法判断用户到底是想做故障诊断、还是查日志、还是知识问答。这个判断需要语义理解能力，所以我们用了一个微调好的 qwen3-0.6b 模型做意图五分类。这个分类器就是微调的价值——"怎么想"的能力。两个串联使用：先分类意图，再根据意图调整 RAG 的检索策略，最后把检索结果和分类结果一起送给 agent 做决策。这就是 2026 年的标准答案，RAG 加微调组合拳。

Q4　Prompt 能替代微调吗？在什么场景下可以，什么场景下不行？

主接项目：sre-agent 的 prompt 约束 + 意图分类微调模型。

🟢 我命中的参考答案要点

  • ✅[真实] 简单场景可以——sre-agent 的 specialist agent 通过 agent_configs.yaml 中的详细 prompt 约束输出格式（比如 k8s_specialist 要求输出 {"conclusion": "正常/异常/部分/失败", "anomaly_signals": [...], "severity": "P0-P4"}），目前 Prompt 就能兜住
  • ✅[真实] 复杂场景不行——意图分类（intent_classifier.py:27-32）如果只靠 system prompt "你是一个意图识别助手" 加 Few-Shot，5 分类的准确率达不到生产要求，所以走了微调路线
  • ⚙️[补全] Prompt 换模型就失效——sre-agent 支持 MiniMax/OpenAI/DeepSeek 三 provider 切换（llm_client.py:20-22），如果 system prompt 是针对 MiniMax 调优的，切换到 OpenAI 可能需要重新调整 prompt 模板

🟡 我能拿到的加分项

  • ✅[真实] 能说出 Few-Shot 的 token 成本问题——specialist agent 的 system prompt 在 agent_configs.yaml 里每个都 40-60 行，加上 Few-Shot examples 会进一步膨胀。如果一个请求 token 超过上下文窗口的 30%，就该考虑微调来降低 Prompt 成本
  • ✅[真实] 能说出项目中 Prompt 的实际边界——我们 Prompt 版本管理（prompts/registry.py:62-63）记录了每次 prompt 变更的 SHA-256，通过 graph state 里 prompt_versions 字段追踪。如果某个 prompt 版本频繁迭代但效果不稳定，就是微调信号

🔴 危险信号（主动规避）

  • ❌ 别说"Prompt 无所不能"——我们项目里意图分类就是 Prompt 做不到而走了微调的例子
  • ❌ 别说"微调可以替代所有 Prompt"——specialist agent 的 system prompt 定义角色和分析流程，这是微调做不到的（微调不会让你"变成"一个 k8s 专家）

完整应答（口语稿）

Prompt 在简单场景下确实能替代微调，但复杂场景下不行。在我们项目里两个场景都有。简单场景——比如我们五个 specialist agent 的输出格式，通过 agent_configs.yaml 里的 prompt 就能约束住，要求输出结构化 JSON，定义了分析步骤、异常信号分类、严重等级，目前 Prompt 就兜得住。但复杂场景——意图分类，如果我们只用 Prompt 写"你是一个意图识别助手"再加上几条 Few-Shot 示例，五分类的准确率达不到生产要求，所以我们用了微调模型。

Prompt 有天然的上限。第一，它本质是在上下文里"教"模型，模型没有真正学会，换个模型 prompt 可能就失效了。我们支持三个 LLM provider——MiniMax、OpenAI、DeepSeek，同样的 prompt 在不同模型上表现可能不一样。第二，Few-Shot 的 token 成本随复杂度线性增长，specialist agent 的 system prompt 已经 40 到 60 行了，再加 Few-Shot examples，一个请求的 token 可能占上下文窗口的 30% 以上。

判断标准很简单：如果你的 prompt 版本迭代了三五轮还是不稳定，或者 prompt 长度已经接近上下文窗口的承受上限了，那就是微调信号。我们有一套 prompt 版本管理，每次变更都记录 SHA-256 校验和，如果发现某个 prompt 版本频繁调整但效果曲线不收敛，就该考虑上微调了。

模块二：高效微调（LoRA / QLoRA / PEFT）

Q5　为什么全参数微调在工业界"已死"？LoRA 相比全参数微调的核心优势是什么？

主接项目：sre-agent 目前没有训练代码，但在资源评估时有实际考量。

🟢 我命中的参考答案要点

  • ⚙️[补全] 全参数微调 7B 模型需 ~56GB 显存（FP16），LoRA r=64 仅需 ~12GB，训练时间从 12-24h 降到 2-4h——这些是行业基准数据，不是我们项目实测的，但我们在 sre-agent 做技术选型时评估过
  • ⚙️[补全] LoRA 恢复全量微调 90-95% 的性能，显存仅 1/5——这个数据来自社区 benchmark（如 HuggingFace PEFT 论文），多次被验证
  • ✅[真实] sre-agent 的生产环境部署在阿里云 K8s 集群上，如果将来要做模型微调，显存预算是第一约束。我们当前用的 qwen3-0.6b 是通过 DashScope API 调用的（intent_classifier.py:44），训练托管在百炼平台，不需要自己管理 GPU——但这也意味着我们对平台有依赖

🟡 我能拿到的加分项

  • ⚙️[补全] 能背出具体数字——7B 模型全参数 ~56GB，LoRA ~12GB，QLoRA ~6GB，这是我们做技术评估时的记忆
  • ⚙️[补全] 能说出 LoRA 的数学直觉——权重更新矩阵通常是低秩的，微调只改变少数方向上的参数，所以用两个小矩阵 B·A 来近似 ΔW。当 r=8, d=4096 时，仅需 0.4% 的可训练参数

🔴 危险信号（主动规避）

  • ❌ 别说"我们做了全参数微调"——我们根本没训练代码
  • ❌ 别说"LoRA 和全参数微调效果一样"——要说"恢复 90-95% 性能"，留有余地

完整应答（口语稿）

全参数微调在工业界基本被 LoRA 替代了，核心原因就三点：显存、时间、性价比。一个 7B 模型全参数微调在 FP16 下需要大约 56GB 显存，单卡 A100 都要跑十几个小时。LoRA 在 r 等于 64 的配置下只需要 12GB 显存，两到四个小时就能跑完一轮，而且恢复全量微调 90% 到 95% 的性能。这个差距在工程上就是"能不能做"的区别，不是"做得好不好"的区别。

在我们 sre-agent 项目里，目前还没有训练代码——我们的意图分类模型是阿里云百炼平台托管训练的 qwen3-0.6b，通过 DashScope API 调用。但我们在技术选型的时候评估过，如果将来要自己做模型定制，LoRA 是唯一现实的方案。我们跑在阿里云 K8s 集群上，GPU 资源不是无限的，显存预算是第一约束。所以如果将来需要对工具调用做微调，方案就是用 LoRA，r 取 64，consumer GPU 就能跑。

Q6　讲一下 LoRA 的数学原理。为什么低秩近似有效？

主接项目：无训练代码，但可以结合 sre-agent 的实战场景讲"为什么有效"。

🟢 我命中的参考答案要点

  • ⚙️[补全] 权重更新矩阵 ΔW 通常是低秩的——预训练模型已经学到了丰富的语言表示，fine-tuning 只需要在少数几个方向上微调，所以 ΔW 可以用两个低秩矩阵 B(r×d) 和 A(d×r) 的乘积来近似
  • ⚙️[补全] 参数量对比——原始 ΔW 有 d×d 个参数（对于 d=4096 就是 1600 万个），LoRA 只需 2dr 个（r=8 时仅 65536 个，占比 0.4%）。冻结原模型 99% 以上的参数，只训练新增适配器
  • ✅[真实] 在 sre-agent 的意图分类场景中，如果用 LoRA 微调 qwen3-0.6b 代替全参数微调，参数量对比会非常直观——0.6B 模型全参数微调需要更新 6 亿参数，LoRA r=8 只需约 100 万参数，训练成本降低 99.8%

🟡 我能拿到的加分项

  • ⚙️[补全] 能解释为什么低秩有效——本质是"预训练模型已经学会了通用语言能力，fine-tuning 只是在特定任务上调整少数几个子空间的表示"。Like learning a new accent, not a new language.
  • ⚙️[补全] 能说出 r 的选值经验——r=8 适合简单任务，r=64 适合复杂任务，r=128 适合对效果要求极高的场景。但从 64 到 128 的边际收益递减，显存开销却翻倍

🔴 危险信号（主动规避）

  • ❌ 别说"矩阵分解就是奇异值分解"——LoRA 不是 SVD，是学习两个新矩阵
  • ❌ 别说"r 越大越好"——r 过大会失去 LoRA 的意义，边际收益递减

完整应答（口语稿）

LoRA 的核心思想是权重更新矩阵通常是低秩的。大模型预训练已经学到了很丰富的语言表示，fine-tuning 一个新任务，其实只需要在少数关键方向上调整参数。所以用两个小矩阵 B 和 A 的乘积来近似这个更新矩阵就足够了。原始更新矩阵是 d 乘 d 的，比如 d 等于 4096，就是 1600 万个参数。LoRA 用两个小矩阵，一个是 r 乘 d，一个是 d 乘 r，加起来 2dr 个参数。r 取 8 的时候只要六万多个参数，占比 0.4%。冻结原模型 99% 以上的参数，只训练这个适配器。这样训练快，显存也小。

为什么低秩有效？可以这么理解——预训练模型已经学会了语言的基本能力，fine-tuning 只是让它适应一个新任务的口音，不是重新学一门语言。就像你会说普通话，要学广东话只需要调整发音方式，不需要重新学语法。

如果是我们 sre-agent 的场景，给 qwen3-0.6b 做意图分类的微调，全参数要更新 6 亿参数，LoRA r 等于 8 只需要更新大概 100 万参数，训练成本降低 99.8%。r 值的选择上，简单任务用 8 就够了，复杂任务上 64，追求极致效果可以用 128，但从 64 到 128 边际收益递减，显存开销却翻倍，工程上 r 等于 64 是最佳平衡点。

Q7　QLoRA 相比 LoRA 多了什么？为什么消费级显卡能做 7B 微调？

主接项目：无训练代码，但可以关联 sre-agent 的部署环境和资源约束。

🟡 我能拿到的加分项

  • ⚙️[补全] 能说出 NF4 不是简单截断——权重分布近似正态分布，NF4 针对这个分布特性优化量化点，比 INT4 均匀量化信息损失更小
  • ⚙️[补全] 能说出"48GB GPU 上微调 65B 模型靠的就是分页优化器"——把优化器状态分页到 CPU 内存，GPU 显存只保留当前活跃页

🔴 危险信号（主动规避）

  • ❌ 别说"量化不会有精度损失"——要诚实说 < 2%，但可接受
  • ❌ 别说"4090 可以做全参数微调"——24GB 显存做 7B 全参数微调根本不够

完整应答（口语稿）

QLoRA 在 LoRA 的基础上多了三个关键技术点，这三个点让消费级显卡直接跨越了"能不能做"的门槛。第一，4-bit NF4 量化——这不是简单截断，是专门针对 LLM 权重分布优化的量化格式。LLM 的权重分布近似正态分布，NF4 利用这个统计特性来选量化点，比均匀的 INT4 量化信息损失更小。第二，双重量化——在 NF4 量化的基础上再做一轮量化，显存再省 30%。第三，分页优化器——训练过程中优化器的中间状态可能占很大显存，分页优化器把不活跃的页自动卸载到 CPU 内存，GPU 显存只保留当前活跃页。这就是为什么 48GB 的 GPU 可以微调 65B 模型。

Q10　"1000 条高质量 > 10 万条噪声"——这句话背后的逻辑是什么？

主接项目：sre-agent 的 Query Rewriter 独立服务设计和评估框架。

🟢 我命中的参考答案要点

  • ✅[真实] 噪声数据的危害——如果微调数据质量差，模型会把错误的 pattern 刻进权重。sre-agent 的 Query Rewriter 独立服务设计（docs/document/2025-01-15-query-rewriter-independent-service.md）明确要求评估数据集每条都要有 expected_rewritten、difficulty 标注和 expected_expansion_count——这就是对数据质量的工程化要求
  • ✅[真实] 评估是数据质量的生命线——sre-agent 有完整的离线评估框架（backend/app/evals/），包含 case_loader、scorer、metrics（per-class precision/recall/F1, confusion matrix）。这个框架本身就强调了"每条数据都需要被评估"，不是堆数量
  • ⚙️[补全] 一个训歪的意图分类器，修复成本远高于标注 1000 条高质量数据的成本——这是我们选择用百炼平台托管模型的原因之一（数据标注和训练由平台侧保障质量）

🟡 我能拿到的加分项

  • ✅[真实] 能说出数据质量的具体维度——rewriter 评估指标（exact_match_rate, token_precision, token_recall, token_f1, stopword_removal_rate, term_expansion_coverage）就是对数据质量的量化定义
  • ⚙️[补全] 能举出反面例子——如果意图分类的训练数据里，"pod 重启" 这个 query 有时候标注为 "diagnose_fault" 有时候标注为 "query_logs"，模型学到的就是噪声，上线后分类准确率会大幅下降

🔴 危险信号（主动规避）

完整应答（口语稿）

这句话的核心逻辑是，微调会把数据里的 pattern 刻进模型权重，好的 pattern 让模型变强，坏的 pattern 让模型变弱甚至退化。噪声数据的问题不是"没用"，而是"有害"——它会让模型学到错误的关联。

在我们 sre-agent 项目里，我们对数据质量有一套工程化的标准。Query Rewriter 独立服务的设计里，评估数据集每条都必须标注 expected_rewritten、difficulty 等级和 expected_expansion_count，这就是对数据质量的硬性要求。我们还有一套完整的离线评估框架，支持 per-class 的 precision、recall 和 F1 值，还有混淆矩阵。这些指标就是数据质量的量化标准。

举个例子，如果我们给意图分类器做训练数据，一条 query "pod 重启了" 有时候标成 diagnose_fault，有时候标成 query_logs，这个标注不一致就是噪声。模型上线后遇到类似 query 会随机输出一个结果，分类准确率能掉 20 个百分点。修复一个训歪的模型的成本，远高于一开始就认真标注 1000 条高质量数据。这也是为什么我们选择用百炼平台托管训练——数据质量控制由平台侧负责，我们只需要关注效果验收。

Q12　数据不够怎么办？有哪些数据增强手段？

主接项目：sre-agent 的 Query Rewriter 数据构造和评估。

🟢 我命中的参考答案要点

  • ✅[真实] 合成数据 + 人工校验——sre-agent 的 Query Rewriter 设计里，评估数据集从 10 条 eval case 扩展到 30 条，其中 20 条从训练数据中采样（docs/document/2025-01-15-query-rewriter-independent-service.md:116）。这个"从已有数据中挖掘 + 人工标注"的思路就是数据增强的核心
  • ✅[真实] 人工抽检是必须的——rewriter 评估设计了 difficulty 标注（easy/medium/hard/unknown），每条数据都有 expected_rewritten 和 expected_expansion_count，这些都需要人工标注，自动生成做不到精准
  • ⚙️[补全] Few-shot 生成——用 GPT-4 给意图分类生成相似 query 的变体，比如 "pod 重启" → "pod 一直重启" → "pod 反复重启" → "pod crashloopbackoff"，然后人工筛选去掉不自然的表达

🟡 我能拿到的加分项

  • ✅[真实] 能说出合成数据的风险——GPT-4 生成的数据可能带有模型本身的 bias，比如生成的 query 都是标准的自然语言表达，缺少真实用户的错别字、口语化表达、缩写
  • ⚙️[补全] 能给出人工校验的比例——至少抽检 10%，核心边界 case 要全检

🔴 危险信号（主动规避）

  • ❌ 别说"GPT-4 生成的数据可以直接用"——必须经过人工校验
  • ❌ 别说"数据不够就上数据增强，一定能解决"——数据增强只能缓解，不能替代真实标注

完整应答（口语稿）

数据不够的时候，有三条路可以走，但每条都要人工把关。第一条，用 GPT-4 生成合成数据。比如给意图分类做数据增强，输入 "pod 重启了" 标注为 diagnose_fault，让 GPT-4 生成类似的变体——"pod 一直重启"、"pod 反复重启"、"pod crashloopbackoff"。但是 GPT-4 生成的数据有个风险，它倾向于生成标准表达，缺少真实用户的错别字、口语缩写、行业术语的随意用法。

第二条，用现有模型做 Few-shot 生成——给几个高质量样本，让模型批量生成相似数据，然后人工筛选。这种方式效率高，但同样需要校验。

第三条，从已有数据中挖掘，这条是最靠谱的。我们在 Query Rewriter 独立服务的设计里就是这么做的——从现有的 10 条 eval case 出发，从训练数据中采样 20 条，凑成 30 条的评估数据集。每条数据都标注了 difficulty 等级和 expected 输出。人工抽检比例我建议至少 10%，核心边界 case 要全检。千万不能觉得 GPT-4 生成的数据可以直接用——没有人工校验的合成数据，比没有数据更危险，因为它会悄悄把模型的 bias 带进训练集。

Q13　微调后效果变差了（灾难性遗忘）怎么办？

主接项目：sre-agent 的 prompt 版本管理和评估框架。

  • ⚙️[补全] 降低学习率 1e-5 ~ 5e-5：灾难性遗忘的本质是梯度更新幅度太大，覆盖了原有知识。降低学习率让更新更温和

完整应答（口语稿）

QLoRA 和 LoRA 的选择标准很直接——看你有多少显存。24GB 以上，比如 A100 或者 H100，直接用 LoRA，训练更快，配置更简单。24GB 以下，比如 RTX 4090 或者 4060，必须用 QLoRA，没得选。精度损失不到 2%，工程上完全能接受。

从我们 sre-agent 的部署环境来看，项目跑在阿里云 K8s 集群上，GPU 按需申请。如果申请 A100 40GB，LoRA r 取 128，这是最优解。如果申请 T4 16GB，那 QLoRA 是唯一可行方案，r 取 64。不仅要看能不能跑，还要看成本——阿里云 GPU 竞价实例，A100 一卡时几十块，T4 一卡时几块钱。用 QLoRA 跑 4 小时不到 20 块，用 LoRA 跑 A100 要上百。所以 QLoRA 不仅省显存，还省钱。

还有个细节，RTX 4090 虽然 24GB 理论能跑 LoRA，但 batch size 只能设 1 到 2，训练容易不稳定。换 QLoRA 可以把 batch 拉到 4，训练更稳。2026 年如果是在消费级显卡上做微调，无论是成本还是稳定性，QLoRA 都是唯一选择。
