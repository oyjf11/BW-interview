## 模块一：AI 安全——提示注入与攻击面

### Q1　提示词注入原理、分类与防御体系（★拉档题）

- 🔵 考察点：是否真正理解 LLM 提示注入的本质——语义层绕过而非语法层绕过，能否区分直接/间接注入，能否给出分层防御方案。
- 🟢 参考答案要点：
  - 原理：LLM 无法区分系统指令与用户输入，所有内容在上下文中混合处理，是语义层面的绕过，与 SQL 注入（语法层）本质不同。
  - 分类：直接注入（用户直接改写指令）vs 间接注入（载荷藏在 RAG 知识库、网页、上传文档中）。
  - 防御四层：输入侧正则+语义双校验 → 系统指令/用户数据隔离 → 系统提示词硬编码存储 → 输出侧二次审计。
- 🟡 加分项：
  - 提到做过 system/user role 的硬分离——系统提示词用独立 message role，永远不和用户输入拼接。
  - 能说出间接注入最难防，因为载荷来自可信检索结果，必须在检索结果进入 LLM 前加一层安全过滤。
  - 提到工具白名单/黑名单作为注入后的兜底防御——即使 LLM 被注入要求执行危险操作，工具层也能拦截。
  - 能说出 OWASP LLM Top10（2025）前三：提示注入 > 不安全输出处理 > 训练数据投毒。
- 🔴 危险信号：
  - 认为"只要 prompt 写得好就不会被注入"——忽略间接注入和语义绕过。
  - 把提示注入和 SQL 注入混为一谈，说不清本质差异。
  - 防御方案只有"加规则"一个维度。

### Q2　间接注入——RAG 知识库投毒攻击与防御

- 🔵 考察点：是否理解间接注入的独特威胁模型——攻击者不直接输入恶意 prompt，而是污染数据源，让 LLM 在正常检索过程中被注入。
- 🟢 参考答案要点：
  - 攻击路径：攻击者向知识库/向量库/公开网页植入恶意内容 → 用户查询触发检索 → 恶意内容随检索结果注入 LLM 上下文。
  - 关键防御点：检索结果进入 LLM 前必须经过安全过滤层，不能直接拼接。
  - 向量碰撞投毒：攻击者构造语义相近但内容恶意的向量混入库中，需要用向量签名校验 + 文档来源分级防御。
- 🟡 加分项：
  - 提到做过 FTS5 查询注入防御——在全文搜索中对特殊字符做转义，防止搜索语句本身就是注入。
  - 提到向量相似度阈值（如 cos_sim < 0.3 滤掉）作为第一道防线。
  - 能说出文档来源分级的具体方案：可信源（内部文档）权重高 → 半可信源（用户上传）需审核 → 不可信源（公开爬取）需安全过滤。
  - 提到定期审计向量库分布，发现异常聚类及时告警。
- 🔴 危险信号：
  - 没意识到检索结果本身就是注入载体，只说"输入校验"。
  - 认为"向量搜索是确定性的，不会被投毒"。

### Q3　模型投毒（训练投毒/后门投毒/RAG 污染）与防御

- 🔵 考察点：是否理解模型投毒的三种形式，各自防御手段，尤其是 RAG 场景下的数据污染防御。
- 🟢 参考答案要点：
  - 训练数据投毒：向训练集植入恶意样本，让模型学错知识——防御靠数据源校验 + 样本审计。
  - 后门投毒（Trojan）：嵌入隐藏触发器，正常输入表现正常，特定关键词触发恶意输出——防御靠推理层后门检测 + 异常输出人工审核。
  - RAG 数据污染：向向量库注入恶意文档，检索后触发注入——防御靠文档上传内容审核 + 检索结果安全过滤。
- 🟡 加分项：
  - 提到工具元数据中加入 risk_level 作为"模型行为护栏"——即使 LLM 被投毒建议危险操作，工具层根据 risk_level 拦截。
  - 提到文件上传的白名单机制（扩展名校验 + 大小限制）作为 RAG 数据入口的第一道防线。
  - 能说出向量签名校验的具体做法：对文档嵌入做哈希签名，检索时验证签名一致性。
- 🔴 危险信号：
  - 只说"数据要审核"但说不清审核什么、怎么审。
  - 混淆训练投毒和后门投毒的触发机制。

### Q4　模型窃取、对抗样本与影子 AI 综合

- 🔵 考察点：对三个进阶安全威胁的认知广度——模型窃取（商用 API 场景）、对抗样本（绕过审核）、影子 AI（企业内部数据泄露）。
- 🟢 参考答案要点：
  - 模型窃取：攻击者通过大量 API 调用蒸馏模型能力。防御：API 限流 + IP 画像 + 输出加微小扰动。
  - 对抗样本：文本场景下用隐形字符、同义词替换绕过安全审核。防御：输入归一化 + 对抗训练。
  - 影子 AI：员工私用 ChatGPT 上传代码/数据。防御：流量审计 + DLP + 推广私有模型。
- 🟡 加分项：
  - 提到工具调用的 timeout 机制和重试限制（如 tenacity 指数退避）作为基础的 API 滥用防护。
  - 能说出环境感知的策略控制：生产环境限制执行类操作，仅允许只读查询——相当于缩小模型窃取可利用的攻击面。
  - 提到评估模式下用 fixture 数据替代真实调用，降低影子 AI 风险。
- 🔴 危险信号：
  - 不知道影子 AI 是什么。
  - 认为"加个 API key 就安全了"。

## 模块二：对齐（Alignment）技术

### Q5　RLHF 全链路（SFT → RM → PPO）（★拉档题）

- 🔵 考察点：是否理解 RLHF 三阶段各自做什么、为什么需要三个阶段、与纯 SFT 的本质差异。架构师必须能手推流程。
- 🟢 参考答案要点：
  - SFT（监督微调）：用高质量指令数据微调基座模型，让模型学会"怎么说"——数据质量 > 数据量。
  - RM（奖励模型）：训练一个评价模型学习人类偏好排序——面临奖励黑客（Reward Hacking）风险。
  - RL（PPO）：用 PPO 策略优化，让模型输出高奖励内容——KL 散度约束防止策略跑偏。
  - RLHF vs SFT 的本质差异：SFT 学"怎么说"，RLHF 解决"说什么更好"——对齐人类价值观。
- 🟡 加分项：
  - 提到在 agent 系统中做了自动质量打分——虽然不是 RLHF，但体现了"用可量化信号评价模型输出"的思想，类似于奖励模型的工程化落地。
  - 能说出设计多级质量门控（quality_score < 0.4 → 触发 critic 重试）作为类似 PPO 迭代优化的工程实践。
  - 提到 RLHF 的三个核心价值：减少有害输出、提升指令遵循能力、学会拒绝。
- 🔴 危险信号：
  - 说不清 PPO 为什么需要 KL 散度约束（防止策略偏离太远，模型投机取巧）。
  - 认为 RLHF 就是"多标一些数据"。

### Q6　DPO vs RLHF：原理对比与选型（★拉档题）

- 🔵 考察点：2025-2026 最热对齐技术。必须能说出 DPO 的核心原理（为什么不需要奖励模型）、与 RLHF 的 tradeoff、什么时候 DPO 不够。
- 🟢 参考答案要点：
  - DPO 本质：把 RLHF 的奖励模型隐含到偏好对中，用分类损失替代 RL 的策略梯度——流程从三阶段简化为两阶段。
  - 优势：简单稳定、不需要训练奖励模型、LoRA+DPO 是 2026 标配。劣势：依赖高质量偏好对，不能在线迭代。
  - 选型：有高质量人类偏好数据 → DPO 首选。需要持续在线迭代 → RLHF 或 RLAIF。
- 🟡 加分项：
  - 提到 agent 系统中用"多种信号加权聚合"的思路（multi-evidence quality scoring）做决策，类似于 DPO 隐式建模偏好的思想——不显式训练奖励模型，而是直接基于多个信号打分。
  - 能说出 LoRA+DPO 的工程优势：显存小、训练快、可以在同一基座上快速迭代多个对齐版本。
  - 提到实际架构中 DPO + RLAIF 混合使用：DPO 快速对齐 baseline，RLAIF 做持续迭代。
- 🔴 危险信号：
  - 说不清 DPO 和 RLHF 的本质差异（DPO 不需要奖励模型）。
  - 认为 DPO 可以完全替代 RLHF——忽略在线迭代和偏好数据质量的限制。

### Q7　Constitutional AI（宪法 AI）+ RLAIF 与对齐技术演进

- 🔵 考察点：是否了解 Anthropic 的 Constitutional AI 思想和 RLAIF 方案，能否对比各种对齐方法的适用场景。
- 🟢 参考答案要点：
  - Constitutional AI：用 AI 反馈替代人类反馈，让模型根据一组宪法原则自我修正——适用于标注成本高的场景。
  - RLAIF：用 AI 做奖励模型——大规模对齐、降低标注成本。
  - 与 RLHF/DPO 的关系：标注成本从高到低——RLHF（全人工）> DPO（偏好对）> RLAIF（AI 奖励）> CAI（自我修正）。
- 🟡 加分项：
  - 提到在 agent 系统中设计的多层校验规则（spec validation rules、工具风险分级）类似于"嵌入式宪法"——把行为约束硬编码到系统层面而非仅靠 prompt。
  - 提到 AGENTS.md 中的 Constitution Gates 清单——用 checklist 方式让 agent 在规划阶段自我审查，是 CAI 思想的工程化落地。
  - 能说出 CAI 的一个核心风险：原则本身可能有偏差，需要定期审计和校准。
- 🔴 危险信号：
  - 不知道 Constitutional AI 和 RLAIF 的区别。
  - 认为"宪法就是 prompt 模板"。

### Q8　红队测试方法论与评估

- 🔵 考察点：是否真正做过安全测试，能否说出红队测试的方法论（自动化红队 vs 人工红队），以及如何度量测试效果。
- 🟢 参考答案要点：
  - 目的：模拟恶意攻击，找出模型安全漏洞。
  - 方法：自动化红队（用 LLM 生成攻击 prompt）+ 人工红队（安全专家手工构造）。
  - 指标：攻击成功率、漏洞严重等级、修复后回归通过率。
  - 2026 趋势：LLM-as-Attacker 自动红队 + 对抗性评估基准（SafetyBench、TrustGPT）。
- 🟡 加分项：
  - 提到做过具体的安全测试用例：SQL 注入防御测试——输入 `"; DROP TABLE--"` 验证查询不执行注入。
  - 提到有安全事件评估用例（security incident scenario），验证系统的 risk_decision 输出为 NEEDS_APPROVAL。
  - 提到评估用例的 schema 校验（_validate_case）确保测试数据质量，是红队测试基础设施的基础。
- 🔴 危险信号：
  - 说"我没做过红队，但我知道很重要"——没有实践经验。
  - 认为红队测试就是"找几个人随便测测"。

## 模块三：护栏（Guardrails）工程

### Q9　护栏四层架构设计（L1-L4）（★拉档题）

- 🔵 考察点：架构师核心能力。能否画出四层护栏架构、说出每层的职责和拦截策略、理解层与层之间的协作关系。
- 🟢 参考答案要点：
  - L1 输入护栏：提示注入检测 + 参数校验 + 环境策略（如生产环境禁止危险操作）。
  - L2 推理护栏：实时监控 Token 消耗 + 异常行为告警 + 质量门控（低质量输出触发重试/降级）。
  - L3 输出护栏：敏感信息过滤 + 置信度封顶 + 审计日志脱敏。
  - L4 业务护栏：领域规则引擎 + 人工审核触发 + 分级响应。
- 🟡 加分项：
  - 能对应到具体实现：L1 对应 ToolGateway 的参数校验 + EnvPolicy 环境白名单；L2 对应 risk_gate_node + loop_guard 循环熔断 + evidence quality gating；L3 对应 ConfigMap 敏感键脱敏 + confidence 上限 0.9 + audit sanitization；L4 对应 approval_interrupt_node + HITL 审批流程。
  - 提到 L1 和 L3 都用到了敏感键脱敏——L1 是工具参数脱敏，L3 是审计日志脱敏，覆盖不同阶段。
  - 能画出完整的请求链路：用户输入 → L1 → L2 → 模型推理 → L3 → L4 → 用户输出。
  - 提到多 Agent 场景下护栏需要 trace_id 串联，防止 A2A 通信中的注入传播。
- 🔴 危险信号：
  - 只说"需要护栏"但画不出分层架构。
  - 混淆输入护栏和输出护栏的职责（输入防注入，输出防泄露+幻觉）。

### Q10　护栏关键设计决策

- 🔵 考察点：工程决策能力——护栏放哪里、语义判断用什么、告警策略怎么定、多 Agent 护栏怎么设计。
- 🟢 参考答案要点：
  - 护栏位置：输入侧 + 输出侧两侧都放。输入防注入，输出防幻觉+敏感信息泄露。
  - 语义判断：输入侧用规则（低延迟），输出侧可用小模型做安全分类。
  - 告警策略：固定阈值（成功率 <95%）+ ML 异常检测（延迟突变、Token 分布偏移）组合。
  - 多 Agent：统一护栏，trace_id 串联，防止 A2A 通信中的注入传播。
- 🟡 加分项：
  - 提到实际工程中做的决策：工具层用白名单（agent config 中的 tool_names）而非黑名单——默认拒绝，显式授权，符合零信任原则。
  - 提到四种风险路由决策（LOW_ONLY / NEEDS_APPROVAL / BLOCKED / NEEDS_HUMAN）作为告警策略的工程落地。
  - 提到工具注册时声明的 risk_level + requires_approval + timeout_ms 元数据是护栏策略的数据基础。
- 🔴 危险信号：
  - 认为"输入侧就够了"——忽略输出侧的幻觉和泄露风险。
  - 说"用 GPT-4 做安全判断"——不考虑延迟和成本的实际工程约束。

### Q11　幻觉治理全链路

- 🔵 考察点：是否理解幻觉治理需要多层级协同——检索层、生成层、验证层、闭环，缺一不可。
- 🟢 参考答案要点：
  - 检索层：混合检索 + 重排序 + 硬负样本训练 → Precision@k, Recall@k。
  - 生成层：受限解码（top-p + 复制机制）+ 引用归属 → 引用准确率。
  - 验证层：事实核查模型 + 人工审核（高风险场景）→ 事实一致性得分。
  - 闭环：反馈感知训练 + 对比学习惩罚偏离输出 → 用户反馈回流 → 增量训练。
- 🟡 加分项：
  - 提到多证据源加权打分（evidence quality scoring）——收集多个 specialist agent 的分析结果，按 quality_score 加权，低质量证据不被采纳——从源头减少幻觉。
  - 提到置信度强制封顶（confidence ≤ 0.9）——即使 LLM 说"我很确定"，系统也只给 0.9——这是架构层面的幻觉防控。
  - 提到分级降级策略：LLM 失败时回退到规则引擎（rule-based fallback），规则结果是确定性的，不会产生幻觉。
  - 提到 2026 新方向：神经符号融合——将 LLM 语言能力与符号系统逻辑推理结合，减少无依据猜测。
- 🔴 危险信号：
  - 认为"写个好 prompt 就解决了幻觉"。
  - 不知道引用归属（citation attribution）是什么。

### Q12　多 Agent 护栏与 Agent 互注入防御

- 🔵 考察点：多 Agent 场景下的独特安全挑战——Agent A 的输出是 Agent B 的输入，注入可跨 Agent 传播。能否给出防御方案。
- 🟢 参考答案要点：
  - 问题本质：多 Agent 系统中，恶意内容可以通过 Agent 间通信链路传播，单一 Agent 的护栏无法防御。
  - 防御方案：统一护栏架构，每个 Agent 入口都做安全校验；trace_id 串联 A2A 通信；Agent 之间不共享上下文，只传递结构化数据。
  - 关键设计：Agent 间传递的是结构化结果（JSON），不是自然语言上下文——减少注入传播面。
- 🟡 加分项：
  - 提到 agent 之间通过 shared graph state 传递结构化数据而非自由文本——每个 agent 只读写 graph state 中的特定字段，相当于天然隔离。
  - 提到 agent 级别的工具隔离（k8s agent 只能调 query_k8s_* 工具）——即使一个 agent 被注入，攻击面也被限制在其 category 内。
  - 提到 FORBIDDEN_TOOLS 的设计——所有 specialist agent 都禁止调用执行类工具，只能由专门的 executor 执行——这是最小权限原则在 Agent 层的体现。
- 🔴 危险信号：
  - 认为"每个 agent 单独做护栏就行"——不知道 Agent 互注入的概念。
  - 多 Agent 之间共享同一份 system prompt——这是高危设计。

## 模块四：隐私保护与合规

### Q13　隐私保护技术全景（DP/FL/HE/MPC/水印）

- 🔵 考察点：对隐私保护技术全景的认知——差分隐私、联邦学习、同态加密、安全多方计算、模型水印各解决什么问题、适用场景。
- 🟢 参考答案要点：
  - 差分隐私（DP）：训练数据加噪声保护个体隐私，ε 取 1-10，越小越安全但模型越差。适用联邦学习、统计查询。
  - 联邦学习（FL）：数据不出本地，只传梯度。适合多机构协作（医疗/金融）。需安全聚合防投毒。
  - 同态加密（HE）：密文上直接计算，不解密。适合高敏感推理，计算开销大。
  - 安全多方计算（MPC）：多方协同计算，彼此看不到数据。通信开销大。
  - 模型水印：在输出中嵌入不可察觉的标识，可追溯泄露源。需抗微调、抗蒸馏。
- 🟡 加分项：
  - 提到生产环境的只读默认（mysql_readonly: True）——这是数据最小化原则在工程实践中的体现，虽然不直接是 DP/FL，但体现了"用不到的权限就不给"的隐私设计思想。
  - 提到敏感数据脱敏的两层实现：工具层（K8s ConfigMap 敏感值脱敏）+ 审计层（审计日志递归脱敏），覆盖了数据全生命周期。
  - 提到使用 bcrypt + salt 对密码做哈希存储——标准密码学实践，虽然不在 DP/FL 范畴，但展示了正确的安全工程习惯。
- 🔴 危险信号：
  - 说不清差分隐私的 ε 是什么。
  - 认为"同态加密已经实用了"——不了解其性能开销。

### Q14　中国法规合规（个信法/网安法/生成式 AI 办法）

- 🔵 考察点：对国内合规要求的实际理解——三法对应什么场景、在系统设计中如何落地。
- 🟢 参考答案要点：
  - 《个人信息保护法》：敏感信息需单独同意、去标识化、传输加密。RAG 系统中的用户查询数据、上传文档都涉及个信法。
  - 《网络安全法》：数据本地化、跨境审批、数据最小化。模型部署在海外的场景需要特别关注。
  - 《生成式 AI 管理办法》：训练数据合规、内容安全、标识义务——生成内容需要打水印。
- 🟡 加分项：
  - 提到生产环境的 config validation（validate_for_production）——检查 CORS 不为 *、debug 关闭、adapter mode 不为 mock——这是合规要求中的"安全基线"在工程中的体现。
  - 提到敏感数据脱敏覆盖工具调用全链路——即使调用了第三方服务，敏感字段也已经被脱敏，满足"数据传输最小化"。
  - 提到日志脱敏（_sanitize_for_audit）确保审计日志不包含明文敏感信息——满足个信法的"去标识化"要求。
- 🔴 危险信号：
  - 把个信法、网安法、生成式 AI 办法混为一谈。
  - 认为"合规是法务的事，技术不用管"。

## 模块五：评测体系

### Q15　安全评测基准（SafetyBench / TrustGPT / ToxiGen 等）

- 🔵 考察点：是否了解业界主流安全评测基准，各测什么维度，怎么集成到 CI/CD 中。
- 🟢 参考答案要点：
  - SafetyBench：综合安全能力（注入、偏见、有毒输出），2026 大厂内部标配。
  - TrustGPT：LLM 可信度多维评估，学术+工业都认。
  - ToxiGen：有毒内容生成检测，专注偏见评测。
  - AdvBench：对抗鲁棒性，红队评估。
  - BBQ：社会偏见，公平性必测。
- 🟡 加分项：
  - 提到安全事件评估用例的设计——用结构化的 eval case（security incident scenario）验证系统的 risk_decision 输出，相当于自建的 minibench。
  - 提到 eval case 的 schema 校验保证测试数据质量——好的评估基准首先要有好的测试数据。
  - 提到在实际系统中可以跑多个维度的评估：安全性（注入检测）、鲁棒性（SQL 注入测试）、行为对齐（risk_decision 准确性）——这就是多维度安全评测的工程实践。
- 🔴 危险信号：
  - 不知道 SafetyBench 和 TrustGPT 的区别（前者是综合安全，后者是可信度）。
  - 认为"安全性不需要专门测，跑跑业务用例就行"。

### Q16　对齐评测方法（LLM-as-Judge / 人类评估 / Elo / A/B Test）

- 🔵 考察点：对齐效果的评估方法——各自优缺点、适用场景、怎么组合使用。
- 🟢 参考答案要点：
  - LLM-as-Judge：用更强模型评输出质量——快、可扩展，但有自恋偏见。
  - 人类评估：人工打分——最准，但贵且慢。
  - A/B Testing：线上对比两版模型——真实反映体感，周期长。
  - Elo Rating：类似棋手排名，pairwise 对比——Chatbot Arena 用的就是这个。
  - 自恋偏见解决方案：多 Judge 投票 + Judge 与被评模型解耦 + 定期用人类评估校准。
- 🟡 加分项：
  - 提到多 evidence quality scoring 作为自动评估机制——多个 specialist agent 的分析结果按质量加权聚合，低质量证据降权——本质上是 LLM-as-Judge 的思想在 agent 系统中的工程化落地。
  - 提到可以设计 A/B Test 框架对比不同 agent 策略配置（如不同 tool 组合、不同 prompt）的效果——评估框架已有 run_records 持久化，天然支持对比分析。
  - 提到 human approval 流程实际上收集了隐式的人类评估信号——用户批准/拒绝某个决策，就是对齐信号。
- 🔴 危险信号：
  - 不知道 LLM-as-Judge 的自恋偏见是什么。
  - 认为"人类评估就是找几个人看一眼"。

## 模块六：架构设计与前沿

### Q17　企业级 LLM 安全护栏架构设计（★拉档题）

- 🔵 考察点：综合架构设计能力。能否设计一个生产可用的、覆盖输入→推理→输出→业务四层的安全护栏架构。这是高级研发和架构师的核心区分题。
- 🟢 参考答案要点：
  - 接入层：统一 API 网关，所有请求带 trace_id。输入侧四层检测：正则校验 → 语义安全分类 → 提示注入检测 → 敏感词过滤。
  - 推理层：实时监控 Token 消耗、异常行为（单次输出超长、敏感词密度突增）→ 触发降级（切换到安全小模型或拒绝）。
  - 输出层：事实核查验证引用准确性 + 敏感信息二次过滤 + 引用归属检查。
  - 反馈层：所有被拒绝/降级的请求回流，用于红队测试和护栏迭代。
  - 告警分级：P0（数据泄露）/ P1（注入攻击成功）/ P2（护栏误杀率突增）。
- 🟡 加分项：
  - 能对应到具体代码实现：trace_id 对应 AgentTracer + run_id 传播；输入校验对应 ToolGateway._validate_tool_params + EnvPolicy；推理层监控对应 risk_gate_node + loop_guard + quality gating；输出护栏对应 ConfigMap 脱敏 + audit sanitization；反馈层对应 eval cases + bad_cases 表。
  - 提到 L0-L3 工具风险分级作为护栏策略的数据基础——每个工具声明 risk_level、requires_approval、timeout_ms，护栏据此自动决策。
  - 提到双策略载体（Policy as Code）：行为侧用 AGENTS.md（软约束），系统侧用插件钩子（硬约束）——策略不能只写在 prompt 里。
  - 能画出完整的架构图并标明每层的拦截触发条件。
- 🔴 危险信号：
  - 架构设计中缺少反馈闭环——护栏是静态的，不会自我进化。
  - 只有输入过滤没有输出过滤——漏掉幻觉和敏感信息泄露。

### Q18　模型对齐效果评估方案设计

- 🔵 考察点：能否设计一套完整的对齐评估方案——测什么、怎么测、用什么指标、怎么闭环。
- 🟢 参考答案要点：
  - 三维评估：安全性（SafetyBench + 自动化红队，测注入成功率）+ 有用性（LLM-as-Judge + 人类评估，测指令遵循率）+ 真实性（TruthfulQA + 幻觉率，测是否扎根检索内容）。
  - tradeoff 管理：安全护栏太强会降低有用性，需用 A/B Test 找平衡点。
  - 评估流程：离线评估（开发阶段）→ 上线前回归 → 在线 A/B → 持续监控。
- 🟡 加分项：
  - 提到 agent 系统中已有的评估基础设施：evidence quality scoring（自动打分）、specialist confidence（置信度评估）、eval cases（结构化评估用例）——这些可以直接扩展为对齐评估框架。
  - 提到 human approval 流程可以作为"人类评估"的持续数据源——每个审批决策都是一个对齐标签。
  - 提到 bad_cases 表和 spec_versions 表可以支持"回归测试"——每次系统变更后，跑历史 bad cases 验证不退化。
- 🔴 危险信号：
  - 只说"用 LLM 打分"——没有考虑自恋偏差和校准方案。
  - 评估方案中缺少人类评估环节。

### Q19　DPO vs RLHF 选型决策与实战

- 🔵 考察点：能否在真实业务场景中做对齐技术选型——考虑的因素包括数据质量、迭代频率、工程复杂度、成本。
- 🟢 参考答案要点：
  - DPO 首选场景：有高质量偏好对、新项目快速启动、LoRA 微调迭代。
  - RLHF 仍需要的场景：需要在线持续迭代（客服机器人）、偏好数据噪声大、需要精细化奖励塑形。
  - 实际推荐：先用 DPO 快速对齐 baseline，再用 RLAIF 做持续迭代。DPO + RLAIF 混合是 2026 主流。
- 🟡 加分项：
  - 提到在 agent 系统中虽然没有 DPO/RLHF，但做了类似的设计选择：证据质量自动打分（类似隐式奖励）+ 规则兜底（类似安全基线）——体现了"自动评估 + 硬约束"的混合思路，类似于 DPO + 护栏的组合。
  - 能说出 DPO 不适合的场景并给出替代方案。
- 🔴 危险信号：
  - 认为"DPO 完全替代 RLHF"——不知道 DPO 的局限性。
  - 选型原因只有"DPO 更简单"——缺乏对具体场景的分析。

### Q20　2026 前沿加分项整合（MCP 安全 / 自我反思 / 鲁棒性 / 可解释性）

- 🔵 考察点：对 2026 年 AI 安全前沿方向的认知广度，能否串联自己的项目经验。
- 🟢 参考答案要点：
  - MCP 协议安全：工具调用集中化，所有调用可审计——从散乱到集中的安全治理。
  - Agent 互注入：多 Agent 下注入可跨 Agent 传播，每个 Agent 入口需做护栏 + trace_id 串联。
  - LLM 自我反思：用思考 token 让模型在输出前做 self-check——Reflexion 框架。
  - 鲁棒性即安全：对抗鲁棒性差的模型，护栏也守不住——先保证鲁棒性再加护栏。
  - 可解释性辅助安全：用 SHAP/LIME 分析模型为什么输出有害内容——定位攻击面。
- 🟡 加分项：
  - 提到 trace_id + AgentTracer 的统一追踪架构——虽然没有直接用 MCP 协议，但实现了 MCP 安全理念的核心：所有工具调用可追踪、可审计。
  - 提到 agent 通过 graph state 传递结构化数据而非自然语言——减少了 A2A 注入传播面，是 Agent 互注入防御的工程实践。
  - 提到 Constitution Gates（AGENTS.md checklist）作为 self-check 机制——让 agent 在规划阶段自我审查，是 LLM 自我反思的工程化落地。
  - 提到 loop_guard（最大 2 轮证据收集）作为"鲁棒性兜底"——系统层面的硬约束防止 agent 陷入无限循环，体现了"鲁棒性即安全"的思想。
- 🔴 危险信号：
  - 说"2026 前沿我都懂"但一个都说不清怎么和项目结合。
  - 把论文概念当项目经验——混淆理论认知和工程实践。
