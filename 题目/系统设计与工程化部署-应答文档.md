## 一、基础认知：第一道分水岭

### Q1　Chatbot、Workflow、Autonomous Agent 三者本质区别

> 主接项目：sre-agent 的 LangGraph 编排 + ReAct specialist agent + rag 的 chat 端点，三者覆盖完整范式谱系。

#### 🟢 我命中的参考答案要点

- ✅[真实] **Workflow 范式**：sre-agent 的 LangGraph 状态机
  - `backend/app/graph/builder.py:161-272` — StateGraph 定义 14 个节点，条件边路由
  - 决策主体是代码而非 LLM

- ✅[真实] **Agent 范式**：sre-agent 的 SpecialistAgent ReAct 循环
  - `backend/app/graph/nodes/specialist_agent.py:184-258` — `for round_num in range(self.config.max_tool_rounds)` 循环
  - 决策主体是 LLM，自主选择调用工具

- ✅[真实] **Chatbot 范式**：rag 项目的 chat 端点
  - `rag/server/src/modules/chat/` — 多轮对话管理，无工具调用，无规划循环

- ⚙️[补全] 三者在同一项目中的统一：实际分布在三个项目中，但架构上可以统一——LangGraph 做 workflow 编排，节点内嵌入 ReAct agent，前端用 chat 接口

#### 🟡 我能拿到的加分项

- ✅[真实] 能举例三者在同一生态中的角色
- ⚙️[补全] 自主性双刃剑的量化分析：Agent 自主度可用"可调用工具数量 × 工具风险等级"量化

#### 🔴 危险信号（主动规避）

- ❌ 别说"sre-agent 里同时实现了三种范式"——chatbot 范式在 rag 项目里
- ❌ 别说"Agent 就是比 Workflow 好"——各有适用场景

#### 完整应答（口语稿）

> 这三者的本质区别在于决策主体。Chatbot 的决策主体是用户——用户问什么它答什么，没有工具没有规划。Workflow 的决策主体是代码——像 sre-agent 里的 LangGraph，14 个节点、条件边路由，都是代码写死的流程，LLM 只在节点内部做推理。Agent 的决策主体是 LLM 本身——像我们的 specialist agent，它在一个 ReAct 循环里自己决定调用哪个工具、什么时候停、什么时候换策略。
>
> 生产环境里最大的坑是 Agent 的自主性。给太多自主权，模型可能做出不可预期的操作；给太少，就退化成 Workflow。我们做的就是在 Agent 外面套一层 Workflow 编排——LangGraph 控制大流程，节点内部给 Agent 有限的自主空间。比如 specialist agent 只能调用它领域内的工具，execute_action 这种高风险操作直接列在 FORBIDDEN_TOOLS 里。这就是"安全的自主边界"。

### Q2　Agentic Loop：Thought → Action → Observation 循环

> 主接项目：sre-agent 的 specialist_agent.py ReAct 循环。

#### 🟢 我命中的参考答案要点

- ✅[真实] **ReAct 循环实现**
  - `backend/app/graph/nodes/specialist_agent.py:184-258` — `for round_num in range(self.config.max_tool_rounds)` 循环
  - 每轮：LLM 调用（含 tools 定义）→ 解析 tool_calls → 执行工具 → 结果以 `role: "tool"` 追加到 self.messages → 下一轮 LLM 推理

- ✅[真实] **tool_response 传回模型的角色**
  - `backend/app/graph/nodes/specialist_agent.py:249-254` — `self.messages.append({"role": "tool", "tool_call_id": tc.get("id", ""), "name": tool_name, "content": json.dumps(...)})`
  - 使用 OpenAI function-calling 标准格式，role 为 "tool"

- ✅[真实] **循环终止条件**
  - 模型不再返回 tool_calls → 进入 final analysis
  - 达到 max_tool_rounds → 强制截断
  - 超时（deadline 检查，`remaining_ms < 2000`）→ 截断

- ⚙️[补全] Harness-system 的 Agentic Loop：AGENTS.md 定义 9 步 SOP 工作流，是 prompt 驱动的声明式工作流，不是编译的状态机

#### 🟡 我能拿到的加分项

- ✅[真实] 能画出完整循环流程图并标注数据结构：graph state（TypedDict）→ specialist agent（self.messages list）→ tool call（JSON Schema）→ tool result（role: "tool" message）
- ✅[真实] 能区分 ReAct vs Plan-and-Execute：AI-PPT 的 generatePresentation 是 Plan-and-Execute，sre-agent 的 specialist agent 是 ReAct

#### 🔴 危险信号（主动规避）

- ❌ 别说"Harness-system 有 LangGraph 式的状态机"——它是 prompt 驱动的 SOP
- ❌ 别说 tool_response 用 user 角色——是 tool 角色

#### 完整应答（口语稿）

> Agentic Loop 的核心是 Thought → Action → Observation 循环。在 sre-agent 里，这个循环实现在 specialist_agent.py 里。每个 specialist agent 启动后，进入一个 for 循环，每轮先调 LLM——LLM 的 system prompt 里带着它这个领域能用的工具列表，LLM 返回 tool_calls。然后代码解析这些 tool_calls，逐个执行，执行结果以 role 为 "tool" 的消息格式追加回 self.messages 列表里。下一轮 LLM 推理时就能看到上轮的工具结果，基于结果决定下一步。
>
> 循环什么时候停？三种情况：模型觉得证据够了不再调工具、达到最大轮数、或者超时。这里有个细节——tool_response 必须用 role: "tool" 回传，不是 user 也不是 assistant。这是 OpenAI function-calling 的标准格式，如果角色搞错了，模型会混淆"这是用户说的"还是"这是工具返回的"，推理质量直接崩。
>
> 另外我们还有 Plan-and-Execute 模式，在 AI-PPT 项目里。先让 Agent1 规划整个 PPT 的大纲，然后 Agent2 并行生成每一页。这个模式适合流程固定的场景，效率高但不适应变化。ReAct 适合开放域探索，Plan-and-Execute 适合标准化任务。

### Q3　感知模块设计

> 主接项目：sre-agent 的 intake + triage + intent_classifier，AI-PPT 的 Agent1 内容分析。

#### 🟢 我命中的参考答案要点

- ✅[真实] **意图识别**：sre-agent 的 intent_classifier
  - `backend/app/rag/intent_classifier.py:1-77` — `classify_intent(query)` 调用 qwen3-0.6b 小模型，返回 5 类意图，失败兜底 unknown

- ✅[真实] **输入规范化**：sre-agent 的 IntakeService
  - `backend/app/services/intake.py:1-83` — 三种输入模式统一归一化为 IncidentTicket，env/service/time_range 标准化

- ✅[真实] **内容分析**：AI-PPT 的 Agent1
  - `apps/server/src/ai/ai.service.ts:737-937` — analyzeContent 提取 suggestedTypes/title/subject/keyPoints/contentBrief

- ⚙️[补全] 多模态感知：sre-agent 当前只处理文本输入，多模态是未来方向

#### 🟡 我能拿到的加分项

- ✅[真实] 感知失败降级策略：triage_node 三级降级——规则匹配→LLM 分类→兜底分类
- ⚙️[补全] 多模态处理路径：语音→ASR 转文字→文本归一化→LLM

#### 🔴 危险信号（主动规避）

- ❌ 别说"感知模块用大模型就够了"——规则引擎兜底是关键

#### 完整应答（口语稿）

> 感知模块的核心是两个能力：理解用户意图和规范化输入。在 sre-agent 里，感知分两层。第一层是 intent_classifier，用 qwen3-0.6b 这个小模型做意图分类，分五类——故障诊断、查指标、查日志、查部署、知识问答。小模型延迟低、成本低，分类不准时兜底 unknown。第二层是 IntakeService，负责把不同来源的输入——可能是手动填的表单、可能是工单系统的 API 回调、可能是告警平台的事件——统一归一化成 IncidentTicket 结构体，env、service、time_range 全部标准化。
>
> 然后进 triage_node 做三级分诊：先规则匹配，比如标题里带 "pod crash" 直接判定 resource_exhaustion；规则匹配不上走 LLM 分类；LLM 失败走兜底分类。这三级保证永远有输出，不会因为 LLM 挂了整个 pipeline 就断了。AI-PPT 项目里也有类似的感知设计——Agent1 分析用户输入，提取主题、关键点、内容摘要，然后传给 Agent2 生成图表。

### Q4　规划模块设计——从 CoT 到 ReAct 到 Hierarchical Planning

> 主接项目：sre-agent 的 planner_node + specialist_agent ReAct + critic_node Reflexion，AI-PPT 的 Plan-and-Execute。

#### 🟢 我命中的参考答案要点

- ✅[真实] **ReAct 规划**：`specialist_agent.py:184-258` — LLM 边推理边调工具，规划和执行交织

- ✅[真实] **Hierarchical Planning**：`nodes/__init__.py:234-383` — 按 incident_type 切换任务模板，两层层次：planner（宏观）→ specialist agent（微观 ReAct）

- ✅[真实] **Plan-and-Execute**：AI-PPT `ai.service.ts:486-575` — Stage 1: planPresentationOutline → Stage 2: Promise.allSettled 并行生成

- ✅[真实] **Reflexion**：`nodes/__init__.py:1115-1174` — critic_node 四路路由：PASS/NEED_MORE_EVIDENCE/REPLAN/CONTRADICTION，loop_count 超限转 NEEDS_HUMAN

- ✅[真实] **Constitution Gates**：harness-system `AGENTS.md:23-33` — 6 项检查（allowed_paths/forbidden_paths/security/tech_stack/rollback/YAGNI）

- ⚙️[补全] 三层层次化规划：当前是两层（planner→specialist），没有中间操作层

#### 🟡 我能拿到的加分项

- ✅[真实] 混合模式：规划用强模型，执行层用确定性校验（enum 强制转换、置信度封顶 0.9）
- ✅[真实] 故障类型驱动的层次化规划：deployment_regression→K8s+DB+日志三个并行子任务

#### 🔴 危险信号（主动规避）

- ❌ 别说 Reflexion 会写回知识——critic_node 只做路由，知识写回是独立节点且需人工确认
- ❌ 别说 Constitution Gates 是编译的规则——是 prompt 里的检查清单

#### 完整应答（口语稿）

> 规划模块是区分高级研发和初级的分水岭。CoT 只能想不能做——模型在文本空间里推理但没法跟外部世界交互。升级到 ReAct 就是因为真实任务需要调工具、查数据、验证假设。在 sre-agent 里，specialist agent 的 ReAct 循环就是边想边做——每轮 LLM 推理后调工具，拿到结果继续推理。
>
> 但 ReAct 的问题是缺乏全局视角，所以我们加了层次化规划。planner_node 先根据故障类型做宏观分解——比如 deployment_regression 要查 K8s deployment 状态、DB 连接数、Pod 日志三个方向——然后分派给三个 specialist agent 并行执行。这就是 Hierarchical Planning 的工业实践：planner 做宏观，specialist 做微观。
>
> 再往上还有 Reflexion。critic_node 在诊断完成后评估证据质量和置信度，四路路由：证据够了就继续，不够就回去补采，矛盾就重规划，超过两次循环就转人工。这跟简单重试的本质区别是：Reflexion 会分析失败原因——是证据不够还是诊断矛盾——然后调整策略，不是盲目重试。Harness-system 里也有类似的机制，叫 Constitution Gates——执行前检查六个约束条件，任何一个不通过就不能执行。

### Q5　行动/工具模块设计——工程落地核心难点

> 主接项目：sre-agent 的 Tool Gateway（gateway.py），harness-system 的 Tool Registry。

#### 🟢 我命中的参考答案要点

- ✅[真实] **Schema 验证 + 重试 + 审计**：`tools/gateway.py:862-1132`
  - `_validate_tool_params()` — JSON Schema 参数校验，缺失参数/类型不匹配返回错误
  - `@retry(stop=stop_after_attempt(2), wait=wait_exponential(...))` — 指数退避重试
  - `_log_audit()` — 每次调用记录工具名、参数（脱敏）、结果、耗时到 IncidentToolAudit 表

- ✅[真实] **安全控制**：`specialist_agent.py:33` — `FORBIDDEN_TOOLS = {"execute_action"}` 全局禁止
  - `specialist_agent.py:35-49` — CATEGORY_PREFIX_MAP 按领域分配工具白名单

- ✅[真实] **工具风险分级**：harness-system `tools/registry/index.yaml:1-142`
  - L0（只读）→ L1（本地写）→ L2（外部写）→ L3（生产高危需审批）

- ⚙️[补全] MCP 协议支持：Tool Gateway 使用 OpenAI function-calling 格式，不是 MCP 协议。MCP 是设计文档中的未来方向
- ⚙️[补全] 沙箱执行：sre-agent 的 ControlledExecutor 做 precondition 校验和 idempotency 检查，但没有容器级隔离。沙箱是 harness-system 的设计概念

#### 🟡 我能拿到的加分项

- ✅[真实] 工具预筛选：specialist agent 按 CATEGORY_PREFIX_MAP 只暴露领域工具，5 个类别约 30 个工具，每个 agent 只看到 3-8 个
- ✅[真实] 容错降级：gateway 支持 mock/real adapter 切换，工具不可用时自动降级

#### 🔴 危险信号（主动规避）

- ❌ 别说 sre-agent 有 L0-L3 分级——那是 harness-system 的设计
- ❌ 别说 sre-agent 支持 MCP 协议——用的是 OpenAI function-calling 格式

#### 完整应答（口语稿）

> 工具模块是工程落地最核心的难点。在 sre-agent 里，我们设计了一个 Tool Gateway，三件事：参数校验、重试、审计。参数校验用 JSON Schema，缺参数或类型不对直接拒绝，不让非法调用到 adapter 层。重试用 tenacity 库，指数退避，最多 2 次。审计是每次调用都记录到数据库——工具名、参数脱敏、结果、耗时——全量可追溯。
>
> 安全控制分两层。全局层：execute_action 直接列在 FORBIDDEN_TOOLS 里，任何 agent 都不能调。Agent 层：每个 specialist agent 有工具白名单，k8s agent 只能调 query_k8s_ 前缀的工具，db agent 只能调 query_db_ 前缀的。这样即使 LLM 幻觉要调不相关的工具，代码层直接拦截。
>
> 工具风险分级我们在 harness-system 里做了 L0-L3 四级。L0 只读随便调，L1 本地写允许，L2 外部写要权限检查，L3 生产高危必须人工审批。这个分级跟 spec-guard 插件联动，运行时自动判断当前操作的风险等级。

### Q6　记忆模块设计——2026 年最硬核考点

> 主接项目：sre-agent 的四层记忆实现。

#### 🟢 我命中的参考答案要点

- ✅[真实] **L1 工作记忆**：`graph/state.py:36-84` — IncidentAgentState TypedDict，40+ 字段，节点间共享
  - `specialist_agent.py:151-153` — self.messages list，包含 system prompt + 对话历史 + 工具结果

- ✅[真实] **L2 短期记忆**：`services/checkpoint.py:9-47` — CheckpointService 每个节点后序列化完整 state 到 SQLite
  - `nodes/__init__.py:49-79` — intake_node 初始化 evidence_items = []

- ✅[真实] **L3 长期记忆**：`nodes/retrieve_memory.py:96-211` — 三源检索：RAG 向量检索 + runbook 工具检索 + 历史相似事件匹配
  - `rag/retriever.py:147-160` — 混合检索：ChromaDB 向量 + FTS5 关键词 + RRF 融合

- ✅[真实] **L4 认知记忆**：`services/knowledge_writeback.py:21-50` — 人工确认后写回 runbook（root_cause + resolution + prevention_items）

- ⚙️[补全] 记忆过期/遗忘机制：无 TTL 策略，记忆按 run 边界重置，长期记忆是 append-only
- ⚙️[补全] 基于权重的记忆（True Memory）：当前是检索式记忆（Memo），不是权重级学习

#### 🟡 我能拿到的加分项

- ✅[真实] 能点出 Memo vs True Memory 区分：当前所有方案都是"存起来检索"，不是"把经验内化为权重"
- ✅[真实] 混合检索在记忆召回中的应用：向量+FTS5+RRF，intent-based filter 适配

#### 🔴 危险信号（主动规避）

- ❌ 别说"四层记忆架构"——认知记忆需要人工确认，说"三层记忆 + 写回能力"更准确
- ❌ 别说有 Redis——用的是 ChromaDB + SQLite FTS5

#### 完整应答（口语稿）

> 记忆模块是 2026 年最硬核的考点。在 sre-agent 里，我们实现了四层记忆。L1 工作记忆就是 graph state 这个 TypedDict，40 多个字段，节点间共享，run 结束就销毁。L2 短期记忆是 checkpoint——每个节点执行完把完整 state 序列化存 SQLite，这样 run 可以中断恢复。L3 长期记忆是 RAG 检索——retrieve_memory 节点在每次新 run 启动时，用混合检索从向量库里召回历史相似事件和 runbook。L4 认知记忆是 knowledge_writeback——人工确认 RCA 报告后，把 root_cause、resolution、prevention_items 写回知识库，供未来检索。
>
> 记忆治理有三个坑。写入污染——不是所有信息都值得存，我们只存关键事件和结论。召回污染——检索可能召回无关或过时信息，我们用 intent-based filter 按故障类型过滤，加相似度阈值。遗忘——目前是按 run 边界自然遗忘，长期记忆是 append-only，这是需要改进的点。
>
> 还有一个前沿认知：当前所有记忆方案本质上都是 Memo 不是 True Memory——只是把信息存起来检索，不是把经验内化为权重级的学习。港中大和浙大 2026 年的论文都在讨论这个方向，面试里能点出这个区分会很加分。

### Q7　反思模块设计

> 主接项目：sre-agent 的 critic_node + verify_outcome_node，harness-system 的 self_check。

#### 🟢 我命中的参考答案要点

- ✅[真实] **Critic 节点四路路由**：`nodes/__init__.py:1115-1174`
  - PASS → 继续 remediation
  - NEED_MORE_EVIDENCE → 回到 evidence_fanout 补采
  - REPLAN → 回到 planner 重规划
  - CONTRADICTION → 回到 planner（证据矛盾）
  - loop_count >= 2 → NEEDS_HUMAN（EVIDENCE_LOOP_EXHAUSTED）

- ✅[真实] **Outcome 级验证**：`nodes/__init__.py:1649-1822` — verify_outcome_node 执行后检查实际 K8s 状态 + 健康检查 + 流量指标

- ✅[真实] **Self-check**：harness-system `AGENTS.md:51-56` — diff review、lint、forbidden_paths、coding_style、security 检查

- ⚙️[补全] Critic 是规则驱动的（数值阈值），不是 LLM 驱动的自我反思

#### 🟡 我能拿到的加分项

- ✅[真实] 能说出 outcome-level 验证的价值：不信任执行器返回，直接查系统实际状态
- ✅[真实] 反思频率解读：太高=规划差，太低=没兜底

#### 🔴 危险信号（主动规避）

- ❌ 别说 critic 用 LLM 做反思——它是规则驱动的（evidence_quality_score 阈值判断）
- ❌ 别说 Reflexion 会更新长期记忆——知识写回是独立节点

#### 完整应答（口语稿）

> 反思模块的核心是每步执行后问自己"这步做对了吗？"。在 sre-agent 里，反思分两层。第一层是 critic_node，在诊断完成后评估证据质量和置信度，四路路由：证据充分就继续，不够就回去补采，矛盾就重规划，超过两次循环就转人工。这里有个关键设计——critic 是规则驱动的，不是 LLM 驱动的。它检查的是 evidence_quality_score 是否达标、missing_evidence_categories 是否为空、contradictions 是否存在。规则驱动的好处是确定性——不会因为 LLM 的随机性导致同一输入不同输出。
>
> 第二层是 verify_outcome_node，这是 outcome 级的验证。执行完修复操作后，不信任执行器返回的 success，而是直接查 K8s deployment 状态、查负载均衡健康检查、查流量指标。只有系统实际状态恢复正常，才算成功。如果只是执行器说成功了但系统还是坏的，那就是 RETRYABLE_FAILURE 或 FATAL_FAILURE。
>
> 反思频率也是个信号。如果 critic 频繁触发 NEED_MORE_EVIDENCE，说明 planner 生成的调查任务不够全面。如果一次都不触发，说明可能缺少兜底——有些问题没被发现。我们在 loop_count 里做了上限保护，防止无限反思。

### Q11　多 Agent 三大坑及解决方案

> 主接项目：sre-agent 的 loop guard + 独立执行 + 优雅降级。

#### 🟢 我命中的参考答案要点

- ✅[真实] **无限循环防护**：
  - `builder.py:21` — MAX_STEPS = 30，MAX_EXECUTOR_RETRIES = 2
  - `nodes/__init__.py:1115-1148` — critic_node loop_count >= max_loop_count → NEEDS_HUMAN + EVIDENCE_LOOP_EXHAUSTED
  - `graph_runner.py:252` — recursion_limit = 50
  - `specialist_agent.py:167,184-192` — deadline 检查，remaining_ms < 2000 截断

- ✅[真实] **通信冗余控制**：
  - `specialist_agent.py:274-289` — _build_task_prompt 结构化构建，只传 service/env/incident_type/extra_context
  - `nodes/__init__.py:591-601` — asyncio.wait timeout=300s，超时取消 pending tasks

- ✅[真实] **错误隔离**：
  - `specialist_agent.py:342-364` — LLM 失败→degraded analysis 或 empty shell，不抛异常
  - `nodes/__init__.py:582-588` — asyncio.gather 独立执行，一个失败不影响其他

- ⚙️[补全] 通信压缩/摘要：没有显式的消息摘要或 token budget 机制
- ⚙️[补全] 错误放大检测：有独立执行隔离，但没有显式的错误放大检测算法

#### 🟡 我能拿到的加分项

- ✅[真实] loop_count 机制设计：每次 critic 循环 +1，超限强转 NEEDS_HUMAN + 记录 terminal_reason
- ✅[真实] LLM 置信度封顶 0.9：防止一个 agent 的过度自信影响聚合决策

#### 🔴 危险信号（主动规避）

- ❌ 别说"通信冗余优化"——没有消息摘要或 token budget，说"结构化 prompt 构建"
- ❌ 别说"错误放大预防"——说"错误隔离通过独立并行执行实现"

#### 完整应答（口语稿）

> 多 Agent 系统有三个经典大坑。第一个是无限循环——两个 agent 互相等待，或者反思→重规划→反思无限循环。我们的防护是三层：MAX_STEPS=30 硬上限、recursion_limit=50 LangGraph 层限制、critic_node 的 loop_count 机制——每次循环 +1，超过 2 次强转 NEEDS_HUMAN，记录 EVIDENCE_LOOP_EXHAUSTED。specialist agent 内部还有 deadline 检查，剩余时间不足 2 秒直接截断。
>
> 第二个是通信冗余——agent 间传递重复信息导致 token 爆炸。我们的策略是结构化 prompt 构建——每个 specialist agent 只收到 service、env、incident_type、extra_context 这几个关键字段，不是全量 state。并行执行用 asyncio.wait 300 秒硬超时，超时的任务直接取消，不让它们继续消耗资源。
>
> 第三个是错误放大——一个 agent 的错误被下游放大。我们的策略是独立执行隔离——每个 specialist agent 独立运行，LLM 失败不抛异常，而是返回 degraded analysis 或 empty shell。aggregator 处理 partial results，不会因为一个 agent 挂了整个 fanout 就崩。LLM 的置信度还做了代码层封顶 0.9，防止过度自信影响聚合决策。

>
> 为什么要 rerank？向量检索用的是 bi-encoder——query 和 document 分别编码再算相似度，速度快但精度粗。Rerank 用 cross-encoder——query 和 document 拼接后一起编码，精度高但速度慢。所以策略是：向量检索召回 candidate_k=15 条（top_k×3），然后用 cross-encoder 重排序压缩到 3-5 条。这样兼顾了召回率和精度。

> 稠密 vs 稀疏：稠密检索（向量）擅长语义匹配——"pod 挂了"能匹配到"容器异常退出"。稀疏检索（FTS5 关键词）擅长精确匹配——"error code 503"精确命中日志。两者用 RRF 融合，k=60 平衡信号权重。实践证明混合检索比单一检索的 Recall@5 高 15-20%。

> LangChain 的问题在于：多层抽象遮挡日志和请求链路，调试困难；冗余组件增加 token 开销和延迟；定制化差——难以适配复杂业务的权限控制、异常降级、记忆治理需求。所以治理平台不适合用 LangChain 那套抽象——需要每一层都能埋点、每一层可替换、治理集中在控制平面。

> 两个项目是互补关系：sre-agent 用 LangGraph 快速实现 Agent 能力，harness-system 提供企业级治理。不是"用哪个替代哪个"，而是"Agent 实现和治理平台是两个不同的层"。
