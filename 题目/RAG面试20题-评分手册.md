# RAG / 检索增强面试官评分手册

**方向**：生产级 RAG 系统（索引 / 检索 / 生成 / 评测 / 工程化）
**岗位画像**：技术专家 / 架构师
**题量**：20 题，分 5 个模块
**建议时长**：单题 5–8 分钟，可深挖追问；整套 45–60 分钟取其中 6–10 题
**最能拉开档次**：Q1 / Q5 / Q7 / Q12 / Q14 / Q19 / Q20

---

## 使用说明

- 每题给出四部分：**考察点**（看什么）、**参考答案要点**（及格线在哪）、**加分项**（优秀候选人会说什么）、**危险信号**（出现即扣分）。
- 参考答案要点是「评分锚点」，不要求逐字命中；候选人用自己的话覆盖核心思想即可。
- 加分项往往是区分「调过 RAG SDK」与「设计过生产级检索系统」的关键，重点关注。
- 危险信号若反复出现，说明候选人缺乏生产级 RAG 的实战认知。
- 所有题目均为开放题，鼓励顺着候选人的回答追问到底，观察其思考深度而非记忆量。

# 一、索引与分块

## Q1 　分块策略选型：固定窗口 / 段落 / 父子 small-to-big 的取舍

**🔵 考察点**

- 是否理解「检索块」与「生成块」的需求矛盾——检索要短而聚焦，生成要长而完整。
- 能否根据业务（FAQ / 长文档 / 多场景）选分块策略，而不是无脑固定窗口。
- 对分块粒度与召回率、上下文完整性的权衡有体感。

**🟢 参考答案要点**

- 固定窗口/滑动窗口：实现简单、可控，但会切断语义边界，长文场景易丢上下文。
- 段落/语义分块：尊重文档结构，但段落长度不均，过短块信息量不足、过长块检索不准。
- 父子分块（small-to-big）：小 chunk 做向量化与精准匹配，大 chunk 通过 parent_id 挂钩，命中后取回完整内容；解决「检索块要短要准、喂 LLM 的块要长要全」的矛盾。
- 分块粒度选择要结合检索召回率与上下文完整性，而非一味追求大块或小块。

**🟡 加分项**

- 主动点出「检索块」与「生成块」的解耦是 small-to-big 的核心价值，不是简单分块技巧。
- 讨论同父块多子块命中时的聚合策略（MAX / 加权 / 投票）。
- 提到过短块会导致 embedding 信息量不足（「语义稀疏」），过长块会稀释相似度信号。

**🔴 危险信号**

- 只答「按 500 字切片」，无策略意识。
- 认为「块越大越好，上下文全」，忽略检索精准度下降。
- 不知道 small-to-big / parent-child，或把它等同于普通分块。

## Q2 　embedding 选型与 query/document 不对称编码

**🔵 考察点**

- 对 embedding 模型选型维度（语言、维度、中英、指令敏感度）的认知。
- 是否知道非对称检索（query 短、document 长）需要区分编码，而非同一 instruction 一把梭。

**🟢 参考答案要点**

- 选型维度：语言覆盖、维度、是否支持中英、是否指令敏感（bge 系需 instruction）、推理成本。
- 非对称检索：query 和 document 用不同 text_type 或 instruction 编码（如 bge-m3 的 query/document 分流、E5 的 query instruction），让短 query 和长 document 在同一空间可比。
- 对称检索（相似句对、聚类）可对称编码；检索场景通常是非对称的。
- 批量嵌入要分批 + 限速，避免触发 API 频率限制。

**🟡 加分项**

- 主动区分「对称检索」与「非对称检索」的编码差异。
- 提到 embedding 缓存：相同文档重复嵌入是浪费，按 content hash 缓存。
- 讨论多语言 / 中英混合场景的模型选型（bge-m3 多语言 vs 中文专用）。

**🔴 危险信号**

- 认为「随便选个 OpenAI embedding 就行」，无视语言和指令敏感度。
- query 和 document 用完全相同的编码方式，不知道非对称问题。
- 批量嵌入不限速不分批，触发频率限制还归咎于「API 不稳」。

---

## Q3 　知识库构建与更新：文档解析、增量索引、索引一致性

**🔵 考察点**

- 对「建库」这一被低估环节的工程能力。
- 增量更新时索引一致性的处理（重索引时检索可用、删除文档后残留块）。

**🟢 参考答案要点**

- 文档解析：按格式选解析器（txt/md 直读、docx 用 mammoth、pdf 用 pdf-parse），解析失败要降级而非崩溃。
- 索引流程：解析 → 分块 → 嵌入 → 写向量库 + FTS 索引，状态机追踪（pending → indexing → ready/failed）。
- 增量更新：新文档追加索引；更新文档要处理旧块失效（删除旧 chunk 再写新 chunk，避免残留）。
- 异步索引：上传响应不阻塞索引，状态字段追踪进度，失败可重试。

**🟡 加分项**

- 提到重索引期间保持检索可用（双索引切换 / 版本号）。
- 讨论文档删除时向量库与 FTS 索引的级联清理，防止「幽灵块」。
- 离线索引优先：文档处理异步执行，不阻塞用户操作。

**🔴 危险信号**

- 认为建库就是「读文件切块存」，无状态机无错误处理。
- 更新文档直接覆盖，不清理旧块，导致检索命中残留内容。
- 索引失败无反馈，用户以为已生效实际没建上。

## Q4 　元数据与结构化过滤：检索前硬过滤 vs 检索后过滤

**🔵 考察点**

- 对「结构化约束 + 语义检索」组合的工程意识。
- 过滤时机（pre-filter vs post-filter）对召回和性能的影响判断。

**🟢 参考答案要点**

- 元数据挂 chunk 级（domain / complexity / multi_user / need_auth / service / env 等），检索前可硬过滤。
- 检索前过滤（pre-filter）：缩小向量搜索空间，召回精准、性能好；适合硬约束（service=payment）。
- 检索后过滤（post-filter）：先召回再筛，可能过滤后结果不足；适合软约束或过滤条件少。
- 结构化过滤与向量检索正交：先按元数据缩小集合，再在子集上算相似度。

**🟡 加分项**

- 主动区分硬约束（pre-filter）与软约束（post-filter 或加权）。
- 讨论元数据放在子块还是父块（small-to-big 场景：子块过滤、父块取回）。
- 提到过滤后结果不足时的兜底（放宽过滤 / 跨库检索 / 拒答）。

**🔴 危险信号**

- 不做元数据过滤，全靠向量召回再人工筛。
- 一律 post-filter，过滤后结果不够还不自知。
- 元数据不挂结构化字段，全塞进文本，无法硬过滤。

# 二、检索与排序

## Q5 　混合检索（向量 + 关键词）的必要性与融合方法

**🔵 考察点**

- 是否理解纯向量检索的失败模式（专有名词、代码、ID、精确匹配）。
- 对融合方法（RRF vs 加权）的原理与适用场景的掌握。

**🟢 参考答案要点**

- 纯向量检索对专有名词、产品名、错误码、精确 ID 召回差——这些是关键词检索的强项。
- 混合检索：向量（语义匹配）+ 关键词（精确匹配 / FTS5）两路召回，融合排序。
- 融合方法：
  - RRF（Reciprocal Rank Fusion）：按排名倒数融合（1/(rank+K)），不依赖分数尺度，跨方案可比。
  - 加权融合：α·向量分 + (1-α)·关键词分，依赖分数归一化，尺度不一致会失真。
- RRF 对分数尺度不敏感，是跨异构检索器融合的稳健默认选择。

**🟡 加分项**

- 主动点出 RRF 优于加权融合的原因：不依赖分数尺度，向量 cosine 和 FTS rank 天然不同尺度。
- 讨论关键词检索的中文分词 / n-gram 处理（单字 + 二元组）。
- 提到 query 净化：FTS5 MATCH 要去除特殊字符防注入 / 语法错误。

**🔴 危险信号**

- 认为「向量检索就够了」，无视精确匹配场景。
- 用加权融合但不归一化分数，向量 0.9 和 FTS rank 直接加权。
- 不知道 RRF，或把它当成简单平均。

---

## Q6 　RRF vs 加权融合 vs rerank 的定位与取舍

**🔵 考察点**

- 对三种「融合/排序」手段的定位是否清晰——它们不是互斥替代，而是不同层。
- 能否论证各自适用场景而非站队。

**🟢 参考答案要点**

- RRF：多路召回的排名级融合，不依赖分数尺度，适合异构检索器（向量 + 关键词）的粗融合。
- 加权融合：分数级融合，需要同尺度或归一化，适合同质检索器（多向量模型）或带调参能力时。
- rerank：cross-encoder 精排，对 query-doc 对打分，准但贵；用于粗排后的候选集（top-N）精排。
- 三者分层：粗排召回（向量/关键词）→ 融合（RRF/加权）→ 精排（rerank）。不是二选一。

**🟡 加分项**

- 主动画出「召回 → 融合 → 精排」三段式管线，指明各段目标。
- 讨论 rerank 的成本控制：只对粗排 top-N 精排，不全量 rerank。
- 提到 rerank 失败的 fallback：回退 cosine 排序，链路不断且标记可观测。

**🔴 危险信号**

- 把 RRF 和 rerank 当成「二选一」的替代方案。
- 全量 rerank 不做粗排，成本爆炸。
- rerank 失败直接报错中断，无 fallback。

---

## Q7 　两阶段检索（粗排 + 精排）与 rerank 的价值边界

**🔵 考察点**

- 是否理解 rerank 的真正价值（排序质量 / 置信度）而非只看命中率。
- 对「rerank 命中率没提升是不是白接了」的判断力——这是分水岭题。

**🟢 参考答案要点**

- 两阶段：粗排（向量 cosine 召回 top-recall_k，快/便宜/广）→ 精排（cross-encoder 只算这 N 个，准/贵）。
- rerank 的价值不止在命中率，更在排序质量（MRR/NDCG）和置信度（margin）。
- 命中率没提升 ≠ rerank 无用：可能是测试集对基线太简单，命中率早打满天花板；rerank 收益在 margin 拉大 → 可设置信度门槛做拒答/转人工。
- 评测要分两类指标：命中率（hit）+ 置信度（margin），光看命中率漏掉一半故事。

**🟡 加分项**

- 用「命中率 +0pp 但 margin 翻倍」这类反直觉结论论证 rerank 的真实价值。
- 讨论 margin 作为生产决策工具：阈值扫描找精度/召回/拒答率/F1 的最佳点。
- 提到 cross-encoder 与 bi-encoder 的本质区别（query-doc 联合编码 vs 独立编码）。

**🔴 危险信号**

- 只看命中率，rerank 没提升命中率就下结论「rerank 没用」。
- 全量 rerank 不做粗排，或粗排召回数等于最终返回数（精排失去意义）。
- 不知道 margin / 置信度门控，只会报命中率一个数。

## Q8 　query 改写 / 扩展：补 vocabulary gap，规则 vs LLM

**🔵 考察点**

- 是否意识到「用户口语 vs 知识库书面语」的词汇鸿沟是召回失败的主因之一。
- 对改写手段（规则 vs LLM）的成本与适用判断。

**🟢 参考答案要点**

- vocabulary gap：用户说「卖东西的网站」，知识库写「电商 在线商城」——语义同但词面不同，向量检索召回差。
- query 改写 embedding 前做：去口语停用词（帮我/做个/那个）+ 术语扩展（口语→专业术语映射）。
- 规则改写：零延迟零成本，覆盖明确的口语→术语映射；维护成本随规模上升。
- LLM 改写：能理解隐含意图、补全模糊词，但有延迟和成本；适合规则覆盖不到的长尾。
- 生产策略：规则优先（快/省），规则覆盖不到时 fallback LLM。

**🟡 加分项**

- 主动点出改写的本质是补 vocabulary gap，不是「让 query 更好懂」。
- 讨论规则改写的维护性：术语映射表可运营、可版本化。
- 提到改写的副作用：过度扩展会引入噪声导致召回漂移（翻车），需评测验证。

**🔴 危险信号**

- 不知道 vocabulary gap，认为「向量检索能理解语义就够了」。
- 一律 LLM 改写，每条 query 多一次 LLM 调用，延迟和成本翻倍。
- 改写不做评测，不知道改写是翻盘还是翻车。

## Q9 　多意图拆分与多路召回

**🔵 考察点**

- 对「一句话多需求」这一真实场景的检索设计能力。
- 拆分手段（规则 vs LLM）的取舍与聚合策略。

**🟢 参考答案要点**

- 多意图问题：一句话含多个需求（「管客户还要能提工单」），单路检索会偏好「最像」的那个，忽略次要意图。
- 拆分：把多意图句子拆成独立子问题，每个子问题独立检索，再聚合。
- 聚合策略：union + max 聚合（同父块多子问题取最高分），或按意图权重加权。
- 拆分手段：规则拆分（按连接词「还要/同时/以及」）零成本，LLM 拆分能理解隐含意图但有成本。
- 多意图评测要引入覆盖度（Coverage@k）和精度（Precision@k），不只 hit1。

**🟡 加分项**

- 主动区分 hit1（单意图）与 Coverage@k（多意图）的评测差异。
- 讨论规则拆分 vs LLM 拆分的最佳生产策略：规则优先，拆不开时 fallback LLM。
- 提到多意图拆分的副作用：过度拆分会把单意图拆碎，增加噪声。

**🔴 危险信号**

- 不处理多意图，单路检索一把梭，次要意图全丢。
- 一律 LLM 拆分，每条 query 多一次调用。
- 多意图场景还只用 hit1 评测，不引入覆盖度指标。

# 三、生成与上下文

## Q10 　检索结果如何喂给 LLM：引用、排序、截断、上下文构造

**🔵 考察点**

- 对「检索到生成」这一交接环节的工程细致度。
- 上下文构造对生成质量与成本的影响判断。

**🟢 参考答案要点**

- 检索结果按相关性排序后注入 prompt，带来源标注（doc_id / 文件名 / 片段），让模型可引用。
- 截断策略：按 top-K + 相关性阈值，超出 token 预算的截断；保留高置信块，外置低置信块句柄。
- 上下文结构：指令 + 检索结果（带来源）+ 用户问题；明确分隔检索内容与指令，降低 injection 风险。
- 流式输出：生成结果按事件流式返回（chunk/reasoning/sources/done），降低首响延迟。

**🟡 加分项**

- 主动点出「检索结果带来源标注」是 citation 可溯源的基础。
- 讨论上下文超预算时的取舍：保留高置信块 + 外置低置信块句柄（Small-to-Big 回退）。
- 提到「渲染后上下文」与「模板」的区别，定位拼装 bug。

**🔴 危险信号**

- 检索结果不带来源，模型无法 citation，事后无法溯源。
- 无截断策略，top-K 全塞，超窗口或成本失控。
- 检索内容与指令混在同一信任层，无分隔。

---

## Q11 　幻觉与忠实性：grounded 生成、citation 可溯源

**🔵 考察点**

- 对 RAG 生成幻觉问题的防控能力。
- 「检索到≠忠实于」的认知——模型可能无视检索结果自由发挥。

**🟢 参考答案要点**

- grounded 生成：prompt 约束模型基于检索内容回答，不得超出检索范围编造。
- citation 可溯源：生成内容带来源标注（引用 doc_id / 片段），事后可核对。
- 忠实性检测：生成内容是否能在检索结果中找到支撑（可程序化校验或 LLM-as-judge）。
- 检索为空时明确拒答，而非让模型凭空生成。

**🟡 加分项**

- 区分「检索结果无关导致幻觉」与「模型无视检索自由发挥」，分别处理。
- 提到忠实性评测：人工抽检或 LLM-as-judge 校验生成内容是否 grounded。
- 讨论 low-confidence 检索结果的处置：不直接喂模型，转人工或补检。

**🔴 危险信号**

- 认为「接了 RAG 就不会有幻觉」，无视模型可能无视检索结果。
- 生成内容无 citation，无法事后溯源。
- 检索为空时仍让模型自由生成，把 RAG 退化成普通 LLM。

---

## Q12 　低置信度拒答 / 转人工：置信度门控设计

**🔵 考察点**

- 对「不该答的时候敢拒答」的生产意识。
- 置信度门控的阈值设计能力——这是 RAG 上生产的关键卡点。

**🟢 参考答案要点**

- 置信度信号：top1 分数、margin（top1 − top2）、检索结果数量、相关性阈值。
- margin 作为「敢不敢下结论」的指标：margin 大说明 top1 与次优拉开距离，可下结论；margin 小说明竞争激烈，易错。
- 门控设计：margin < 阈值 → 拒答或转人工，避免低置信度错误。
- 阈值不是拍脑袋：扫描阈值找精度/召回/拒答率/F1 的最佳点，按业务设可运营区间。

**🟡 加分项**

- 主动点出「光看命中率无法做门控，margin 才是门控可用性指标」。
- 讨论阈值扫描的输出：精度↑、召回↓、拒答率↑的权衡曲线，找 F1 最高点。
- 提到 rerank 提升 margin 的真实价值：不是为了命中率，而是让门控更可用（相同精度下拒答率更低）。

**🔴 危险信号**

- 只看命中率，无置信度门控，低置信也硬答。
- 阈值拍脑袋定，不做扫描，不知道不同阈值的精度/拒答率权衡。
- 认为「top1 分数高就够了」，忽略 margin（top1 高但 top2 也高 = 不敢下结论）。

## Q13 　RAG vs 长上下文：什么时候该 RAG、什么时候塞进窗口

**🔵 考察点**

- 对「长上下文模型普及后 RAG 是否还有必要」的判断力——这是常被问的架构题。
- 成本、延迟、可溯源性、动态性等多维权衡。

**🟢 参考答案要点**

- 长上下文不替代 RAG 的理由：成本（每轮塞全文 token 爆炸）、延迟（长输入推理慢）、可溯源（RAG 带来源，长上下文无法定位）、动态性（知识库更新 RAG 增量索引，长上下文要重塞）。
- RAG 适合：知识库大且动态、需要 citation、成本敏感、需要精准召回。
- 长上下文适合：单文档深度理解、文档量小且固定、不要求溯源、一次性分析。
- 两者可组合：RAG 召回 + 长上下文兜底，或长上下文做单文档 + RAG 做跨文档。

**🟡 加分项**

- 主动点出「长上下文有 needle-in-haystack 衰减」，中间内容容易被忽略，不是真「全记住」。
- 讨论成本对比：RAG 每轮只塞 top-K 块，长上下文每轮塞全文，高频场景成本差几个量级。
- 提到可溯源是 RAG 的本质优势，长上下文无法替代。

**🔴 危险信号**

- 认为「长上下文模型出来后 RAG 就过时了」，无成本/延迟/溯源分析。
- 一律 RAG，单文档场景也切块检索，舍近求远。
- 不知道 needle-in-haystack 衰减，认为长上下文 = 全记住。

# 四、评测与质量

## Q14 　RAG 评测体系：命中率指标 vs 置信度指标

**🔵 考察点**

- 是否理解 RAG 评测不止「命中率」一个维度。
- 对「命中率打满天花板后怎么评估」的判断力——这是分水岭题。

**🟢 参考答案要点**

- 命中率指标：Top-1 hit、Top-3 hit、MRR、NDCG@k——衡量「有没有召回正确答案」。
- 置信度指标：平均 top1 分、平均 margin（top1 − top2）——衡量「敢不敢下结论」。
- 两类指标缺一不可：光看命中率漏掉置信度故事，光看置信度不知道命中率基线。
- 测试集对基线太简单时，命中率早打满天花板，优化收益不在命中率在 margin。
- 排序质量指标（MRR/NDCG）纯看排名不看分数，跨方案（尺度不同）可比。

**🟡 加分项**

- 用「命中率 +0pp 但 margin 翻倍」这类反直觉结论论证两类指标的必要性。
- 讨论 MRR/NDCG 为什么跨方案可比（纯排名，不受分数尺度影响）。
- 提到按难度分档评测（easy/medium/hard/multi），看优化在哪个难度区间起作用。

**🔴 危险信号**

- 只报命中率一个数，无置信度无排序质量。
- 命中率打满就下结论「系统没问题」，无视 margin 是否够做门控。
- 用绝对分数横比不同方案（cosine vs cross-encoder），落入尺度陷阱。

## Q15 　评测数据隔离与防过拟合

**🔵 考察点**

- 对「评测集混生产 / 评测集参与调参」导致分数虚高的防控意识。
- 评测数据与生产数据隔离的工程能力。

**🟢 参考答案要点**

- 评测数据物理隔离：eval 表与生产表分离（eval_chunks vs kb_chunks），不混入生产。
- Golden Answer 粒度：文档级别而非 chunk 级别，避免「召回同文档不同 chunk 算错」的假阴性。
- 防过拟合：评测集分公开/私有（holdout），私有集不进迭代；定期刷新用例。
- LLM 生成评测用例：可用 LLM 从文档生成 query + gold_doc_ids，但需人工抽检校准。

**🟡 加分项**

- 主动点出「评测集参与调参 = 刷分」，分数虚高不代表生产表现。
- 讨论评测集随业务演进持续扩充，防「刷分」。
- 提到 LLM-as-judge 的归因难题：judge 引入第二个 LLM 变量，指标变化无法归因。

**🔴 危险信号**

- 评测集和生产数据混在一起，评测过拟合生产。
- Golden Answer 用 chunk 级别，同文档不同 chunk 算错，假阴性虚低。
- 评测集长期不变且参与调参，分数虚高还以为系统在进步。

---

## Q16 　离线消融实验设计：单变量递进、归因分解、尺度陷阱

**🔵 考察点**

- 对消融实验「控制变量」的严谨性。
- 能否识别评测结果中的「尺度陷阱」——这是高级判断力。

**🟢 参考答案要点**

- 单变量递进：A 基线 → B +改写 → C +rerank，每次只加一个变量，归因分解（改写贡献 +X pp、rerank 贡献 +Y pp）。
- 归因分解：把总提升拆到具体优化，区分「翻盘」（基线错改写对）与「翻车」（基线对改写错）。
- 尺度陷阱：不同方案的分数尺度不同（cosine 0~1 vs cross-encoder relevance_score），绝对值不能横比。
- margin 是同尺度内相对差，横比有意义；top1 绝对分横比无意义。
- 报告需对尺度差异标注脚注，或只保留排名指标（MRR/NDCG）和 margin。

**🟡 加分项**

- 主动点出「平均 top1 分横比是视觉错觉」，讲清 margin 横比才可比的理由。
- 讨论归因分解的粒度：不只是总提升，要拆到每个优化的贡献 + 翻盘/翻车案例。
- 提到多臂实验（A/B/C/D/E）同时对比向量/改写/rerank/关键词/hybrid 的全景。

**🔴 危险信号**

- 消融实验不控制变量，一次改多个，无法归因。
- 用绝对分数横比不同尺度方案，得出「C 比 B 分低所以 rerank 退步」的错误结论。
- 只报总提升，不拆归因，不知道提升来自哪个优化。

# 五、工程化与成本

## Q17 　多 Provider 适配与流式协议统一

**🔵 考察点**

- 对多模型 Provider 差异的收敛能力。
- 流式输出协议设计的工程能力。

**🟢 参考答案要点**

- Provider 差异：请求体格式、流式字段、reasoning 通道、token 统计、system prompt 敏感度。
- 适配器模式：每个 Provider 独立适配器，实现统一接口（buildRequestBody / parseChunk），差异收敛在 adapter。
- 上层逻辑只依赖统一接口，不按模型名写 if-else。
- 流式协议：自建 SSE 事件类型（chunk/reasoning/sources/done/plan/image/error），把各家流式归一到一套。

**🟡 加分项**

- 主动点出「完美模型无关抽象不存在」，关键 prompt 仍需按模型微调。
- 讨论 capability flag 显式管理差异（并行 tool call / reasoning 通道 / 窗口大小）。
- 提到流式超时与空响应兜底：不活跃超时、流结束无内容报错而非显示空气泡。

**🔴 危险信号**

- 认为「套个统一 SDK 就模型无关了」，无视 prompt 和行为差异。
- 模型特定 hack 散落在业务逻辑，不收敛在 adapter。
- 流式无超时无空响应兜底，模型沉默时前端永远转圈。

## Q18 　索引/嵌入缓存与成本控制

**🔵 考察点**

- 对 RAG 高 token 成本的体系化控制能力。
- 嵌入缓存、批量、限速、成本预估的工程意识。

**🟢 参考答案要点**

- 嵌入缓存：相同内容重复嵌入是浪费，按 content hash 缓存，变更才重嵌。
- 批量嵌入：分批（batch 25）+ 限速（批次间 200ms），避免触发 API 频率限制。
- 成本预估：实验前预估 embedding 调用次数（建库 + 查询 × case 数），评估几分钱还是几块钱。
- 查询侧成本：query 嵌入每次调用，可短时缓存热门 query。
- rerank 成本：只对粗排 top-N 精排，不全量 rerank。

**🟡 加分项**

- 主动点出「嵌入缓存按 content hash」，文档更新只重嵌变更块。
- 讨论成本预估在实验设计阶段的作用：评估是否值得跑某实验。
- 提到 rerank 成本控制：粗排召回数（recall_k）是成本与质量的旋钮。

**🔴 危险信号**

- 无嵌入缓存，重索引时全量重嵌，浪费成本。
- 批量嵌入不分批不限速，触发频率限制还归咎于 API。
- rerank 全量精排，成本爆炸。

## Q19 　生产 RAG 的可观测与 bad case 闭环

**🔵 考察点**

- 对 RAG 上生产后的可观测设计能力。
- bad case 从发现到回流评测的闭环意识。

**🟢 参考答案要点**

- 可观测：每次检索记录 query、召回结果、分数、margin、是否命中、用户反馈，形成检索日志。
- 指标看板：命中率、margin 分布、拒答率、平均延迟、token 成本，按知识库/难度分维度。
- bad case 闭环：线上低置信/用户负反馈 case → 记录（query + 错误结果 + 根因）→ 回流评测集 → 验证优化是否修复。
- bad case 记录结构化：case_type / case_desc / evidence / root_cause / severity / status，可检索可统计。

**🟡 加分项**

- 主动点出「bad case 不回流 = 评测集不进化 = 系统不进步」。
- 讨论采样与全量的分层存储：正常采样、异常全量，平衡成本。
- 提到 bad case 的归因分类（检索错 / 生成错 / 评测错），分别对应不同优化路径。

**🔴 危险信号**

- 只记最终结果，出问题无从复现检索过程。
- 无 bad case 闭环，线上错误不回流评测集，系统不进化。
- 无指标看板，命中率/成本/延迟全靠猜。

## Q20 　RAG 系统的演进路线：从 baseline 到生产级的迭代判断

**🔵 考察点**

- 架构师的迭代判断力——不是一锤定音，而是随业务阶段演进。
- 对每一步优化「值不值得做」的取舍能力。

**🟢 参考答案要点**

- 演进路线：baseline（裸向量）→ query 改写（补 vocabulary gap）→ 混合检索（向量+关键词）→ rerank（精排）→ 置信度门控（拒答/转人工）→ bad case 闭环（持续优化）。
- 每步优化的判断：用消融实验量化贡献，不盲目堆优化。
- 业务阶段匹配：demo 阶段裸向量够用，生产必须加门控和闭环；高价值场景才值得 rerank 成本。
- 迭代原则：先做评测基线，再逐个加优化并验证，不做无评测的黑盒堆叠。

**🟡 加分项**

- 主动点出「优化必须评测驱动」，不做无归因的黑盒堆叠。
- 讨论不同业务场景的演进终点（FAQ 够 baseline+改写，知识密集型要 rerank+门控）。
- 提到「测试集难度要随系统进化」——基线打满天花板时要换更难的测试集。

**🔴 危险信号**

- 一上来就全堆（rerank + hybrid + 改写 + 门控），无基线无评测。
- 认为「优化越多越好」，不量化每个优化的贡献。
- 无演进视角，一锤定音，不随业务阶段调整。
