# AI Agent 评测与可观测性 · 面试官评分手册

> **方向**：AI Agent 评测、可观测性、质量保障
> **岗位画像**：高级研发 / 架构师
> **题量**：20 题，分 5 个模块
> **建议时长**：单题 5–8 分钟，可深挖追问；整套 45–60 分钟取其中 6–10 题
> **最能拉开档次**：Q1 / Q6 / Q10 / Q14 / Q19 / Q20
>
> 图例：🔵 考察点　 🟢 参考答案要点　 🟡 加分项　 🔴 危险信号

---

## 使用说明

- 每题给出四部分：**考察点**（看什么）、**参考答案要点**（及格线在哪）、**加分项**（优秀候选人会说什么）、**危险信号**（出现即扣分）。
- 参考答案要点是「评分锚点」，不要求逐字命中；候选人用自己的话覆盖核心思想即可。
- 加分项往往是区分「调过可观测平台」与「设计过可观测架构」的关键，重点关注。
- 危险信号若反复出现，说明候选人缺乏生产级 Agent 可观测性的实战认知。
- 所有题目均为开放题，鼓励顺着候选人的回答追问到底，观察其思考深度而非记忆量。

# 一、可观测性设计原则与指标体系

## Q1　Agent 可观测性的四维度设计：功能 / 性能 / 适应 / 协作

**🔵 考察点**

- 是否理解可观测性 ≠ 监控的核心理念。
- 能否从 Agent 特有的非确定性、多步推理角度出发，给出超越日志收集的架构维度。
- 四个维度之间如何关联、各自独立却又相互支撑。

**🟢 参考答案要点**

- **功能维度**：Agent 能执行哪些操作？工具调用覆盖率？如何验证"确实会做"而不仅仅是"被允许调用"。关键要有工具能力探测机制（describe capability / health check），而非依赖模型自身描述。
- **性能维度**：成功率、端到端延迟、P50/P99 延迟、Token 消耗、工具调用次数。要区分"单步性能"与"端到端性能"，特别是指出串行多轮 LLM 调用是延迟主因。
- **适应维度**：模型更换后的行为一致性（回归评测）、新场景的泛化能力（新增故障类型的覆盖）、降级策略是否生效（工具不可用时的 fallback 行为）。关键是换模型后观测体系能否复用。
- **协作维度**：多 Agent 之间的通信是否可追踪、A2A 协议日志是否完整、trace 能否串联跨 Agent 调用链。子 Agent 的失败不要导致整链断裂。

**🟡 加分项**

- 区分"监控告诉你出问题了"与"可观测性让你不看日志也能推断为什么出问题"，给出 LLM 黑箱下的推断策略。
- 四个维度之间有量化关联关系——比如适应维度可通过功能维度的工具可用性数据来验证。
- MCP 协议对可观测性的原生优势：工具调用集中化、审计天然支持、A2A 通信标准化。
- 提出"Agent 可观测性最难的是适应维度——模型底层的非确定性使行为变化不可预测"。

**🔴 危险信号**

- 只答"打日志 + 装监控 Dashboard"。
- 四个维度答不齐，或只能说出功能/性能两层。
- 说不出 Agent 可观测性与传统微服务可观测性的本质区别。
- 认为"换个更强的模型就行了"来回避适应维度的难题。

## Q2　三层指标体系：任务级 → 组件级 → 推理级的分层设计

**🔵 考察点**

- 能否把 Agent 指标分层，给出不同层级需要关注的指标和它们的使用者。
- 对"指标分层的颗粒度"的判断力——不是指标越多越好，而是分层后才有人看。

**🟢 参考答案要点**

- **L1 任务级（业务视角）**：任务完成率 / 目标达成率、端到端成功/失败、目标漂移率。回答"这 task 到底成了没"——给产品和业务看。
- **L2 组件级（系统视角）**：工具调用成功率、工具延迟 P99、LLM 推理延迟、上下文溢出率、幻觉率。回答"哪个部件拖了后腿"——给 SRE 和工程团队看。
- **L3 推理级（Debug 视角）**：Thought 有效性（思考是否指导行动而非自言自语）、Action 相关性（工具选择是否与子目标匹配）、Observation 利用率（工具返回是否被纳入后续推理）、反思触发率（过高过低都有问题）。回答"模型这一步到底在想什么"——给算法和 prompt 工程师看。

**🟡 加分项**

- 主动说出"10 步流程 × 每步 99% 成功率 = 端到端仅 90.4%"这个复利失败公式，说明组件级指标如何推导任务级可靠性。
- 三层指标之间如何建立关联——比如工具调用成功率下降时，L1 任务完成率是否也降？降了多少？能说出从 L3 到 L1 的归因链路。
- 提出"反思触发率"的金发女孩区间：太高说明规划差（每一步都在纠错），太低说明没有兜底（错了不回头）。

**🔴 危险信号**

- 只报成功率一个数，说不出分层。
- L3 推理级完全没概念，认为"模型黑箱不可观测就放弃了"。
- 把 L1/L2/L3 全塞进同一个 Dashboard 给所有人看，没有按角色分层。

## Q3　复利失败公式：从组件指标推导端到端可靠性

**🔵 考察点**

- 是否理解 Agent 系统"串行多步 + 每步乘积累"的可靠性特征。
- 能否用量化方式说明"为什么要关注每一步的质量而不仅仅是最终结果"。

**🟢 参考答案要点**

- 核心公式：端到端成功率 ≈ ∏(每步成功率)。10 步 × 99% = 约 90.4%端到端。
- 这意味着：单步质量的微小退化在长链 Agent 中会被急剧放大。一个从 99% 跌到 97% 的工具调用，10 步后端到端直接从 90% 跌到 74%。
- 工程含义：
  - 必须对每步有独立的质量度量，不能只看最终结果。
  - 降低步数是提升端到端可靠性最直接的手段（减少乘积累数）。
  - 对不可恢复的错误必须尽早 fail-fast，不要让一条链带着脏数据走下去。
- 评测必须反映这一特性：不只评终态对不对，还要评每一步对不对。

**🟡 加分项**

- 区分"乘积累"和"乘积累 + 纠错"两种模型——有自我纠错的 Agent（critic / reflection）会打断纯乘法，实际公式变成带恢复概率的马尔可夫链。
- 能从自己的系统给出具体数字——"我的系统平均 5 步，工具调用成功率 96%，LLM 推理正确率 93%，理论上端到端 82%，实测 79%，差异 3% 来自上下文累积错误"。
- 提到用 `--repeat N` 多次运行取分布，观察端到端成功率的方差——方差大说明某些步的不确定性在高步数场景下被剧烈放大。

**🔴 危险信号**

- 不知道复利失败公式，或者认为"每步都调好了就不用管整体"。
- 只看端到端指标不看 per-step 指标。
- 没有用重复运行（repeat / 分布）来应对 LLM 非确定性。

## Q4　Agent 死循环 / 行为异常的实时检测与归因定位

**🔵 考察点**

- 对 Agent 循环失控这一生产级高发风险的认知和检测设计。
- 能否区分"模型做错了"与"工具/环境出问题了"——归因能力是可观测性的核心。

**🟢 参考答案要点**

- **循环检测层面**：
  - 最大步数硬上限（step_count ≥ MAX_STEPS → 强制停）。
  - 循环次数检测：连续多轮 Action 相同 + Observation 类似 → 陷入循环 → 强制终止并产出具结原因。
  - 状态无变化检测：连续 N 步后状态无进展（无新信息注入）→ 终止。
- **归因定位层面**：
  - 每一类停止产出一个结构化的 `terminal_reason`（code + stage + message + failed_tools），供路由和可观测使用。
  - 错误码分类覆盖：工具返回错误 / 超时 → 环境侧；模型选错工具 / 参数 / 逻辑 → 决策侧；能力不可用（适配器未接）→ 架构侧。
  - 区分 resumable（可恢复，如单工具超时但其他证据可用）和 fatal（不可恢复，如核心适配器不可用）。

**🟡 加分项**

- 用结构化 `terminal_reason` 做线上归类——定期统计哪种 code 最多，驱动系统优化（比如 `EVIDENCE_LOOP_EXHAUSTED` 占比高 → 优化 critic prompt）。
- 对 Action 重复率做实时监控——接近阈值就告警而不是等红屏。
- 循环检测不仅靠轮次计数，还用语义相似度识别"参数微调但本质重复"的动作。

**🔴 危险信号**

- 只设最大步数就完事，没有循环检测和归因。
- 无法区分模型错误与环境错误，"反正都失败了"。
- 没有结构化终止原因——"停了就停了"，无法追溯为什么。

# 二、评测体系设计

## Q5　三层评估框架：L1 任务级 / L2 过程级 / L3 组件级

**🔵 考察点**

- 是否理解 Agent 评测与传统的"断言 input → output"有本质不同。
- 能否构建分层评估——不仅看结果，还要看推理过程和组件能力。

**🟢 参考答案要点**

- **L1 任务级评估（结果对不对）**：最终答案 / 决策是否正确、是否达成用户目标。适用封闭域（精确匹配）或开放域（rubric + 人工 / LLM 评审）。
- **L2 过程级评估（推理对不对）**：规划是否合理（是否走了多余步骤、是否遗漏必要步骤）、工具选择是否正确（是否调了无关工具）、步骤是否存在冗余/遗漏/死循环。关键是要有"中间状态评分"而非仅对比最终输出。
- **L3 组件级评估（能力边界在哪）**：记忆检索准确率（recall@k）、工具单次调用成功率、上下文压缩后的信息损失率。组件级评估的目标是找出"系统哪个模块最弱"。

**🟡 加分项**

- L2 过程级评估做"两种执行路径对比"——比如纯逻辑图 vs 带持久化的完整链路，两路输出 diff 后暴露序列化丢字段、checkpoint 恢复后语义变化等隐藏问题。
- 强调 L2 和 L1 的指标**绝不合并成一个综合数字**——过程正确但结果碰巧对（瞎试中了）不能算高分；过程稳健但结果差（环境问题）不应该和"乱来"同等对待。
- L3 组件级评估与系统监控打通——工具调用成功率在评测中一旦低于阈值，直接抢在线上出问题前发现。

**🔴 危险信号**

- 只评最终结果对不对，无视过程——"答对就行，怎么答的无所谓"。
- 用单一指标综合所有维度——掩盖了过程的严重问题。
- L2 过程级评估完全没概念，认为 Agent 评测和传统分类器评测一样。

## Q6　LLM-as-Judge 的可靠性、偏见校准与多 Judge 投票

**🔵 考察点**

- 是否理解用 LLM 评 LLM 存在结构性偏见。
- 是否有工程手段校准 LLM Judge 的可靠性。

**🟢 参考答案要点**

- **为什么需要谨慎**：用 GPT-4 评 GPT-4 有自恋偏见（偏好自己生成的内容）；Judge 自身波动引入第二个非确定性变量——指标变化时无法归因是模型变了还是 Judge 飘了。
- **何时该用何时不该用**：封闭域（分类对错、规则校验）用确定性规则评——不需要 Judge；开放域（文本质量、总结好坏、对话流畅度）才需要 Judge。
- **校准手段**：
  - 多 Judge 投票（不同模型评判，减少单一偏见）。
  - 一致性校验——同一条输入多次判分，看 Judge 自身稳定性。
  - 人工抽检 + 裁判一致性（human-judge agreement）作为 ground truth 校准。
  - Rubric 打分（给 Judge 注入评分维度，减少主观空间）。

**🟡 加分项**

- **刻意不做 LLM-as-Judge 的设计决策**——当评估场景可以收窄到封闭枚举等值比较时，不做 Judge 反而是更优工程选择：消除第二个非确定性变量、可完全复现、可做 CI 指标。
- 区分"评测什么"的粒度：能转为封闭枚举的一定转（比如 incident type 做成枚举而非自由文本），不能转的再上 Judge，且 Judge 得分需要标注 confidence。
- Judge 模型与被评模型必须解耦——不能用同一家供应商的模型做裁判。多 Judge + majority voting + 一致性校验三层保证。

**🔴 危险信号**

- "用一个更强的 LLM 打分就完了"——无视 Judge 偏见和自身波动。
- 把 LLM Judge 的分数当绝对真值，不做任何校准和抽检。
- 在能确定性地判断对错的地方也上 LLM Judge，浪费且引入噪声。

## Q7　评测集构建策略：正常流程 60% + 边界 30% + 对抗 10%

**🔵 考察点**

- 是否有评测集设计的工程方法——不是随机抽一批线上 case 就完事。
- 对边界和对抗用例的重视程度——这才是暴露系统真正弱点的关键。

**🟢 参考答案要点**

- **三层覆盖**：
  - 正常流程 60%：覆盖主要使用场景的高频路径，验证基本功能。
  - 边界 case 30%：模糊指令、多意图冲突、工具不可用、上下文矛盾、数据稀疏（少量输入判断）。
  - 对抗/逃逸 10%：异常输入、需要说"不知道"而不是胡编的场景、超出分类体系的外域输入（other label escape）。
- **数据结构化**：每个 case 需包含——case_id、描述、输入（或模拟环境状态）、期望输出（包含终态和关键中间状态）、难度标签、所属类别。
- **可维护性**：数据集结构应支持增加新 case 的低成本操作（新增一个故障类型只需加一个 case JSON + 枚举行）。

**🟡 加分项**

- 将"unknown"（证据不足保守回避）和"other"（诚实报告超纲）分成两个独立标签——防止二者混合造成虚假准确率。
- 评测集设计融入"信号稀疏"场景——给极少输入，看 Agent 是否能保守地报告"信息不足"而非强行武断。
- 对 case 做难度分层（easy / medium / hard），per-difficulty 报指标而非全量平均。
- 区分"公开评测集"（供开发者调优用）和"私有 holdout"（不进迭代，只在上线前跑），防止过拟合。

**🔴 危险信号**

- "随机抽几百条线上数据就够"——没有边界/对抗用例。
- 评测集与训练/调优数据不分离，用同一批 case 反复调 prompt → 刷分。
- 不区分 unknown 和 other，模型说"不知道"也算错 → 逼模型瞎猜。

## Q8　离线评测 vs A/B 测试 vs Shadow Mode 的架构选型

**🔵 考察点**

- 能否针对不同阶段给出合适的评测策略，而非一刀切。
- 对三种模式的成本、可信度、反馈周期的清醒评估。

**🟢 参考答案要点**

- **离线评测**：
  - 适用：快速迭代（改 prompt、换模型、换参数）。
  - 优点：快、可复现、无用户影响、成本低。
  - 弱点：覆盖有限、与线上分布有偏差。
- **A/B 测试**：
  - 适用：验证离线结论在真实流量上是否成立。
  - 优点：真实分布、用户行为信号。
  - 弱点：周期长（需跑数天到数周）、需要足够的样本量（至少 200 条达到统计显著性）。
- **Shadow Mode（影子模式）**：
  - 适用：新模型/新策略的上线前过渡——跑在生产流量上但结果不对外暴露。
  - 优点：真实流量、零用户风险。
  - 弱点：需要双倍资源（两个 Agent 并行跑）、不检测"用户是否采纳"。

**🟡 加分项**

- 给出分阶段策略：原型阶段 → 离线评测；迭代阶段 → 离线评测 + Shadow Mode（对高风险任务）；上线后 → A/B 测试 + 线上监控兜底。
- 对 Shadow Mode 补充一个关键约束：**绝不重放副作用**（创建资源、发送通知等要在 Shadow 侧屏蔽），否则影子模式和主模式一起执行危险操作。
- 离线评测中做"两种执行路径对比"（direct vs runner）是 A/B 思想在离线的落地——快速暴露持久化 / checkpoint 层的问题。

**🔴 危险信号**

- "上线前跑一遍离线评测集就够"——忽略线上分布偏差。
- 把三种模式说成非此即彼——应该是组合使用。
- Shadow Mode 不提副作用屏蔽——影子模式误执行写操作的生产事故。

## Q9　AgentBench / GAIA 等 benchmark 的适用性边界与业务定制

**🔵 考察点**

- 对学术 benchmark 与生产系统的差距有清醒认知——不是拿来主义。
- 能否论证"为什么需要自建业务评测集"。

**🟢 参考答案要点**

- **学术 benchmark 的价值**：选型时做横向对比参考、验证基础能力（工具调用、推理、规划）、了解模型在各维度的基线。
- **局限性**：
  - 任务分布与业务不匹配（AgentBench 的任务含 OS 操作、网页浏览，可能跟你的运维 Agent 完全无关）。
  - 评测方式简化（多项选择或精确匹配），无法反映生产中的开放性判断和多步推理质量。
  - 不包含业务特定的安全/合规/审批约束。
- **必须自建的原因**：业务的故障类型枚举、风险判定逻辑、工具集（K8s、MySQL、云监控）是 benchmark 无法覆盖的。评测集必须和你的 action space + observation space 对齐。

**🟡 加分项**

- 在自建评测集中借鉴 benchmark 的方法论——比如任务难度分层（easy/medium/hard）、多轮运行取分布（pass@k）。
- 提出"领域特定枚举"是评测工程化的关键——把开放性判断收窄为封闭枚举（incident type 做成 11 种枚举值），使主指标可做确定性等值比较，消除评测噪声。
- 区分 benchmark 的两种用法：选型时做能力摸底 vs 上线后做回归发现退化——前者用学术 benchmark，后者必须用业务评测集。

**🔴 危险信号**

- "我们用了 AgentBench，所以评测就完备了"——无视分布偏差。
- 全盘否定 benchmark 的价值——选型时它们仍有参考意义。
- 自建评测集无结构、无分层、无维护流程——变成一次性产物。

# 三、生产级可观测性架构

## Q10　全链路 Trace 的数据采集、存储与关联设计

**🔵 考察点**

- 能否设计从请求入口到 LLM 调用的完整 trace 体系。
- Trace 的分层结构（run → node → tool → llm / specialist）的设计能力。

**🟢 参考答案要点**

- **数据采集层**：在 Agent Runtime 的每个关键步骤埋点——Run 启动/结束、每个节点（node）执行、每个工具调用、每次 LLM 推理。每个 span 记录：span_id / parent_id / name / start_time / end_time / duration_ms / status / error / events。
- **Span 层级设计**：run span（顶层）→ node.{name} span（排查哪个节点慢了/错了）→ tool.{name} / llm.{provider} / specialist.{agent_id} span（排查具体调用出了什么问题）。
- **Trace 传播**：用 trace_id（run_id）贯穿整条链，跨异步/并行步骤——asyncio / 多线程 / 多 Agent 场景下不能断链。运行时 trace_id 不能写死全局变量，要随执行上下文传递。
- **存储选型**：热数据 Redis（短期 TTL 支持实时查询），温数据 ClickHouse / Elasticsearch（OLAP 分析 + 全文检索），冷数据 S3/对象存储（长期归档）。

**🟡 加分项**

- 在 span 内嵌入 events 数组（而非平铺）——events 记录每次 tool 调用/LLM 请求的详细信息，挂到对应 span 下，形成 hierarchy。
- 区分 span 的 status（ok / error / degraded）——degraded 是"工具超时但流程继续"这种半成功状态，不能算 ok 也不能算 error。
- 接入行业标准观测平台（LangSmith / LangFuse / Phoenix），不重复造轮子——同时保留 local provider 选项不依赖外部服务。
- Trace 提供 external_trace_url——从内部系统一键跳转到 LangSmith/LangFuse 的完整 trace 页面。

**🔴 危险信号**

- 只记最终结果，出问题无从复现。
- 无法区分"问题出在哪个节点"——所有监控打在一个平面上。
- 异步/多 Agent 的 trace 断裂——父子关系断了，一个 Agent 调用另一个 Agent 的链路串不起来。

## Q11　采样策略博弈：错误全量 + 慢请求全量 + 正常 10% 的工程权衡

**🔵 考察点**

- 全量存储不可行时的工程取舍能力。
- 对"什么叫重要事件"的判断力——不是随机采样就完了。

**🟢 参考答案要点**

- **核心策略**：错误全量（失败了必须能排查） + 慢请求全量（P99 以上的必须看） + 正常请求 10%（看整体趋势和分布）。这是业界共识的最优工程折中。
- **采样粒度**：session 级采样比 event 级采样好——同一个 run 要么全采样要么全不采，避免 trace 断裂。
- **存储分层**：错误/慢请求的 detail trace 保留全量 span + events；采样的正常请求保留 summary 级别（端点、耗时、节点数）。
- **策略可动态调整**：线上故障时手动切全量；平稳期降低采样率；按成本周期调整。

**🟡 加分项**

- 说出"先做全量再收敛"的务实路径——系统初期数据量小时全量存储，积累数据后再引入采样策略并做历史数据裁剪。
- 对采样本身做监控——采样率偏离目标、采样对重要事件的漏抓率。
- 区分"运维采样"（SRE 看趋势）和"评测采样"（离线评测需要全量历史做训练/调参）——两套采样策略独立。

**🔴 危险信号**

- "我们全量存，不差这点存储"——对生产级成本无感。
- 随机采样不考虑重要性——偶发的关键错误可能被漏掉。
- 采样后 trace 断裂——同一个 run 里某些 span 被采样、某些被丢弃。

## Q12　渲染后真实 prompt 的捕获与 prompt 拼装 bug 定位

**🔵 考察点**

- 对"最终发给 LLM 的到底是什么"这一生产排查核心问题的工程方案。
- 区分"记录了模板"和"记录了渲染后内容"——差距巨大。

**🟢 参考答案要点**

- **必须记录的内容**：渲染后的完整 prompt 文本（实际发给 LLM 的最终内容，含拼接了哪些工具结果、历史消息、系统指令），而不只是模板名 + 参数。
- **为什么模板不够**：线上 prompt 问题往往是拼装环节出 bug——截断了不该截断的内容、变量替换错了、多节点历史拼接时顺序乱了——这些只看模板根本查不出来。
- **存储策略**：prompt 全文体量大，采样存或分层存——错误跑全存 prompt 原文，正常跑存 prompt metadata（版本 checksum + 长度 + token 数）。
- **版本追踪**：每次 prompt 变更记录版本号 + checksum，关联到每个 run——出问题时能定位到"这个 bug 是从哪个 prompt 版本引入的"。

**🟡 加分项**

- Prompt 版本管理做成不可变记录——每次修改生成新版本 + checksum，旧版本可追溯可回滚。
- Trace 中的 llm_request event 同时记录 metadata（版本/模型/长度）和 content（采样后），一键从 metadata 跳到原文。
- 用 checksum 做 prompt diff——改 prompt 后运行评测集，对比 checksum 变化前后的指标分布（improved / regressed / unchanged）。

**🔴 危险信号**

- "我记了用了哪个 prompt 模板"——没记渲染后内容，排查时仍需猜测。
- Prompt 改了直接在代码里改字符串，无版本记录——出问题无法回溯是哪个版本引起的。
- 认为"prompt 就那么几行不会有 bug"——生产 Agent 的 prompt 可能是几十个模板动态拼接的，拼装 bug 是常见问题。

## Q13　告警体系：指标阈值 vs ML 异常检测的分层策略

**🔵 考察点**

- 能否区分"固定阈值告警"和"异常检测告警"各自适用场景。
- 告警分级（P0/P1/P2）和告警升级（escalation）的工程设计。

**🟢 参考答案要点**

- **固定阈值告警**（P0/P1 级别）：
  - P0（立即响应）：任务成功率跌破底线（如 < 90%）、安全事件（越权/注入）、核心工具完全不可用。
  - P1（需关注）：工具成功率 < 95%、上下文溢出率 > 10%、平均延迟 > 基线 2x。
  - 固定阈值的优势：确定性强、不会漏、可解释。
- **ML 异常检测告警**（P2 级别）：
  - 适用场景：延迟突变（不是超阈值而是突然飙升）、新故障模式出现（per-class 某个类别突然大量失败）、指标间异常关系（比如步数不变但 token 暴涨）。
  - 与固定阈值互补——固定阈值保下限，异常检测发现"没超阈值但行为异常"。
- **告警升级**：P2 持续 N 个周期未恢复 → 升 P1；P1 持续 → 升 P0。

**🟡 加分项**

- 区分"告警接入"和"告警体系"——前者是能收到告警事件（如 pagerduty webhook → agent），后者是完整的阈值配置 + 升级链 + 通知渠道 + 聚合去重。
- 对告警做去重与聚合——同一根因的 100 条告警汇成 1 条，降低告警疲劳。
- 告警规则可配置化——不是写在代码里，而是运营可在配置中调整阈值和升级策略。

**🔴 危险信号**

- "我们设了几个 Grafana 阈值就能告警了"——无升级链、无聚合、无策略分层。
- 只用阈值告警无视异常模式——延迟没超 10s 但突然从 1s 变 9s 持续 1 小时，阈值告不到。
- 告警没有与 structured terminal_reason 打通——告警响了还得去翻日志才知道原因。

## Q14　多 Agent 场景的 DAG 关联 Trace 与 A2A 通信追踪

**🔵 考察点**

- 对分布式 tracing 在 Agent 领域的工程应用能力。
- 能否设计跨 Agent 调用的 trace 父子关系，并构造完整的 DAG 调用图。

**🟢 参考答案要点**

- **Trace ID 传播**：每个 Agent 维护自己的 trace_id，跨 Agent 调用时透传 parent_trace_id + 生成子 trace_id。最终能还原出 DAG（有向无环图）：编排者派发 → 子 Agent 处理 → 回传结果。
- **Span 层级**：编排 Agent 的"派发子任务"是一个 span，子 Agent 内部的所有操作（node/tool/llm）是该 span 的子 span。这样在 trace 上，编排者的一个 evidence_fanout span 下面挂 5 个子 Agent 的完整 trace 树。
- **A2A 通信记录**：跨 Agent 的输入输出、协议（请求格式/响应格式）、延迟（从发起到收到回传的 wall-clock time）都要记录。
- **DAG 可视化**：最终能在 Dashboard 上看到一个完整的 DAG 图——哪个 Agent 调了哪个、每个节点的耗时、成功/失败状态。

**🟡 加分项**

- 在异步并发场景（如 asyncio.gather 并行派发多个子 Agent），trace_id / parent_span_id 仍能正确传播——因为运行时层（ContextVar / OpenTelemetry）的自动继承机制。
- 区分"层级编排"（planner → 派发 → aggregate → 裁决，是树状结构）和"对等通信"（Agent A 直接调 Agent B，是图结构），两种模式的不同 trace 记录方式。
- 提出"A2A 追踪是 MCP 协议原生能力"——MCP 把所有工具调用集中化，跨 Agent 调用的 trace 天然串起来。

**🔴 危险信号**

- 多 Agent 各自独立 trace，调完就断——两个 Agent 吵架了定位不到谁的问题。
- 认为"日志带个时间戳就能串起来"——异步场景下 timestamp 并发重叠根本无法可靠关联。
- 子 Agent 的 span 挂不到编排者的 span 下——父子关系断裂。

# 四、回归测试与持续质量保障

## Q15　模型升级 / Prompt 变更的回归评测与行为回退检测

**🔵 考察点**

- 对"模型静默退化"这一生产级风险的防控能力。
- 不只是看总成功率，还要看分项是否退化。

**🟢 参考答案要点**

- **回归触发场景**：换模型（deepseek-chat → deepseek-v3）、改 prompt（哪怕改一行）、升级工具（适配器换了实现）、关键依赖升级（LangGraph 版本等）。
- **评测流程**：新版本跑全量回归评测集 → 对比基线各项指标 → 任一关键指标退化超阈值则门禁阻断。
- **必须看分项**：总成功率不降但某类任务暴跌（如 database_failure 从 90% → 60%）必须能被 per-class 指标抓出。
- **应对非确定性**：用 `--repeat N` 多次运行取分布（均值/min/max/variance），对比的是分布而非单点——单点 72% → 68% 可能是随机波动，"3 轮均值从 72% 跌到 58%"才是真实退化信号。

**🟡 加分项**

- 做 **prompt diff 评测**：两个 prompt 版本跑同样的数据集，输出 improved / regressed / unchanged 三类 case 的详细对比。
- 区分"退化"和"随机波动"——用 repeat N 做统计检验（t-test / Wilcoxon）。
- 不仅监控成功率回退，还监控成本/延迟/越界率的回退——换一个"更谨慎"的模型，成功率没降但步数翻倍、成本翻倍，也是退化。
- 用 checksum 管理 prompt 版本不可变历史——任何时候可以回到旧版本跑对比。

**🔴 危险信号**

- "供应商升级了就直接全量切"——无回归评测、无灰度、无回滚预案。
- 只看总成功率——某类任务偷偷崩了不知道。
- 评测集长期不变且参与调 prompt——分数虚高。

---

## Q16　评测防过拟合：holdout 分离、持续刷新、防刷分

**🔵 考察点**

- 对"评测集过拟合"这一隐蔽风险的认知——Agent 评测集同样会被 prompt 调优"刷分"。
- 维护可长期使用评测集的工程方法。

**🟢 参考答案要点**

- **Holdout 分离**：评测集分公开集（开发者日常调优用）和私有集（holdout，只在发版/上线前跑）。公开集的结果不能作为"上线决策依据"——它的分数可能已经被反复调优喂高了。
- **持续刷新**：定期（每月/每季）从线上按分布采样新 case 注入评测集；删除"太老、太偏、已不具代表性"的旧 case；关注分布漂移（线上故障类型分布变了，但评测集还是旧的）。
- **防刷分设计**：
  - 用封闭枚举等值比较作为主指标（彻底消除"讨好 Judge"的空间）。
  - 用 per-class 指标排雷——总分的提升不能靠"提升简单 case 拉平均、难 case 不改善"。
  - 评测框架本身不暴露"是否命中"给调优流程（不参与 prompt 调优循环）。

**🟡 加分项**

- 使用 unknown_rate 指标——模型学会"不知道就说不知道"是好现象，但如果 unknown_rate 飙升（从 5% → 30%），说明模型在滥用保守策略逃逸。
- 加入风险行为指标（risk_accuracy）——不能只看"答对了没"，还要看"该升级的时候升级了没"。
- 引入 minimal fixture 策略——每个 case 只提供信号承载的工具 fixture，未提供的工具返回受控空，减少对特定 fixture 数据的过拟合。

**🔴 危险信号**

- "评测集就是我们调 prompt 用的那批数据"——严重过拟合，分数虚高。
- 评测集永不更新——线上分布变了，评测集还在测半年前的场景。
- 没有 per-class 指标——总分的提升可能来自于简单 case 变强、难 case 不变甚至更差。

## Q17　CI/CD 中非确定性评测的门禁设计

**🔵 考察点**

- 能否正确处理 LLM 非确定性对 CI/CD 门禁的挑战——"随机红绿"会让门禁形同虚设。
- 给出在"严格门禁"与"LLM 不确定性"之间的务实折中。

**🟢 参考答案要点**

- **挑战**：LLM 推理是非确定性的（即使 temperature=0，浮点计算也有差异）。在 CI pipeline 中同一套 prompt 跑同一个 case，今天绿明天红 → 门禁失去可信度。
- **策略一：确定性主指标 + 非确定性辅助指标**：
  - 主指标（门禁用）必须是确定性可复现的——封闭枚举等值比较、规则校验、schema 校验。
  - 辅助指标（指导用，不做门禁）可以是 LLM Judge 评分——趋势参考但不阻断 merge。
- **策略二：分布比较替代单点比较**：
  - 用 `--repeat N`（≥3）多次运行取分布，对比 mean + min/max + variance。
  - 门禁逻辑："mean 跌幅 > 5% AND min 跌幅 > 5%"才阻断——减少随机波动造成的误报。
- **务实路径**：CI 做语法/配置/确定性规则的门禁；非确定性评测作为"开发者触发器"——发版前手动跑并审核报告。

**🟡 加分项**

- **主动声明"这是非 CI 指标"**——报告顶层明确标注 `ci_metric: false`。诚实比伪装好——你不说面试官也知道 LLM 有波动，伪装 CI 可用反而减分。
- 区分"必须过"的门禁（schema 校验、工具可达性、安全规则）和"建议过"的评测（LLM 行为质量）。
- 提出增量评测策略——只在本次改动影响的 case 上做 repeat N，而非全量 repeat（节省成本和 CI 时间）。

**🔴 危险信号**

- "CI 里直接跑 LLM 评分并强制门禁"——非确定性导致随机红绿，门禁被无视。
- "我们测一次过就算过"——无视 LLM 波动。
- 把所有评测都怼进 CI——CI 跑太久（30min+），开发者绕过。

# 五、调试工程与前沿趋势

## Q18　调试三板斧：Trace 回放、步骤级对比、注入测试

**🔵 考察点**

- 对 Agent 调试的工程化能力——不是人工看日志猜测。
- 三种调试方法各自的适用场景和限制。

**🟢 参考答案要点**

- **Trace 回放（Replay）**：
  - 用途："这次为什么答错了？"
  - 做法：固定输入 + 固定历史 + 重放工具返回，重新跑完整流程或重新跑某步，观察产出变化。关键是工具返回通过 fixture 注入而非真调——即 Q1 中的 decision replay（重放决策）而非 effect replay（重放副作用）。
  - 适用：排查 prompt bug、模型行为退化、上下文累积错误。
- **步骤级对比（Step Diff）**：
  - 用途："改了 Prompt 后哪步变了？"
  - 做法：两个版本（old prompt vs new prompt）跑同样的 case set，逐 case 对比终态 + 关键中间状态，输出 improved / regressed / unchanged。
  - 适用：Prompt 迭代、模型选型、工具开关的影响评估。
- **注入测试（Injection Testing）**：
  - 用途："如果工具挂了会怎样？"
  - 做法：Mock 工具返回——返回错误 / 返回空 / 返回超大结果 / 返回超时——验证 Agent 的降级链路（是否触发 fallback、是否正确写 terminal_reason、是否转人工）。
  - 适用：验证安全边界、降级策略、恢复机制。

**🟡 加分项**

- 回放时要区分"可以在回放中重放的"（模型推理）和"不能在回放中重放的"（副作用执行 / 不可逆操作）。在框架层通过 fixture 短路工具调用，保证重放永不触发真实副作用。
- 步骤级对比不仅对比终态——对于中间关键步骤（如 planner 输出的取证计划、critic 的质量分），逐节点 diff 暴露"哪一步开始出偏差"。
- 注入测试覆盖多个维度：工具超时、工具返回错误码、工具返回空结果、工具返回乱码——每种降级行为验证。

**🔴 危险信号**

- "出问题看日志就够"——Agent 的日志量极大，人工排查效率极低且不可复现。
- 回放时不区分决策重放和副作用重放——调试过程中真的执行了危险操作。
- 没有注入测试——工具挂了会怎样全靠上线后才发现。

## Q19　评测基础设施的分层架构与规模化设计

**🔵 考察点**

- 能否设计一个可规模化的评测平台——不是一次性脚本，而是支撑持续迭代的工程系统。
- 对评测平台的分层（数据管理 / 执行引擎 / 报告系统）的理解。

**🟢 参考答案要点**

- **数据管理层**：
  - 评测数据集管理：case 的 CRUD、版本管理、标签体系（难度/类型/优先级）、schema 校验。
  - 评测计划管理：指定数据集 + 参数（模型/prompt 版本/repeat N/mode）→ 提交评测任务。
- **执行引擎层**：
  - 并发执行评测 case（asyncio / worker pool），并行度可配。
  - 支持多种执行模式：纯逻辑图评测（跳过 DB/副作用，快速迭代）、全链路评测（含持久化和事件）、对比模式（A/B 双跑 diff）。
  - Fixture 注入机制——每个 case 的 mock 数据通过 ContextVar 或依赖注入短路上层工具调用，在 mock/real 选择之前。
- **报告与存储层**：
  - 评测结果持久化（追踪每次评测的结果），支持历史趋势分析。
  - 报告输出：JSON（结构化，供程序消费）+ Markdown（供人阅读）。
  - 关键设计：**两层指标永不合并成一个综合数字**——保持各自独立，避免"一个数字掩盖所有问题"。

**🟡 加分项**

- 执行引擎的并发安全设计——ContextVar 做 per-task 隔离，不同 case 的 fixture 互不污染。并发安全在设计层就考虑了。
- 评测基础设施与 CI/CD 的关系——评测框架支持 CLI 独立运行（`python -m app.evals.replay_runner`），为后续 CI 集成预留接口。
- 对评测框架做"元评测"——评测框架自身的稳定性（同一 case 跑 10 次指标是否一致）、准确率（评测结果 vs 人工审查的一致性）。
- 模块化架构——每个模块（loader / scorer / metrics / executor / report）独立文件，可以单独测试和替换。

**🔴 危险信号**

- "我有几个 Python 脚本跑评测"——无结构、无分层、无持久化。
- 所有 case 串行跑，数据集大了评测一次要几个小时。
- 评测结果手动记录，无历史对比——看不到指标趋势。

## Q20　MCP 协议对可观测性的影响与 2026 演进趋势

**🔵 考察点**

- 对 MCP（Model Context Protocol）对可观测性领域的影响有前瞻判断。
- 能否论证"为什么 MCP 原生的可观测性强于传统 Function Calling"。

**🟢 参考答案要点**

- **MCP 对可观测性的核心价值**：
  - **工具调用集中化**：所有工具调用经过 MCP server 收口，天然的审计单点——全部调用可追溯，比传统各工具独立接入的可观测性强一个量级。
  - **审计日志天然支持**：MCP 协议层自带请求/响应/错误记录，不需要每个工具适配器单独实现审计。
  - **A2A 通信标准化**：多 Agent 场景下 Agent 之间的通信走 MCP → trace 可以原生串联跨 Agent 调用链（trace_id 在 MCP header 中透传）。
- **对现有体系的影响**：
  - 工具网关层（如 Tool Gateway 的 schema 校验/审计/风险标注）可以与 MCP 协议层的能力合并，减少自定义代码。
  - 评测的 fixture 注入点可以从"应用层拦截"下沉到"MCP 协议层拦截"——更标准化，与具体工具实现解耦。
- **局限性**：MCP 目前还处于早期阶段，生态和标准化程度在快速演进中，全量依赖 MCP 有风险。

**🟡 加分项**

- 能对 MCP、opencode plugin、自建 tool gateway 三种工具治理方案做横向对比——各自的成熟度、可观测性强弱、定制灵活度。
- 提出"MCP 让可观测性从应用层附加变成协议层原生能力"这一论断。
- 区分 MCP 能做和不能做的——MCP 治理的是工具调用，不治理 LLM 推理黑箱本身。工具调用以外的可观测性（如 prompt 质量、模型决策路径）仍然需要应用层。
- 提出渐进式接入策略：先做 tool registry + plugin guard（自建控制平面），再接入 MCP 协议做工具标准化，而非上来就全押 MCP。

**🔴 危险信号**

- "MCP 是银弹，接了就全解决了"——无视 MCP 的早期阶段性和局限性。
- 对新协议完全无感，只说"我们用 LangSmith 就够了"——对行业演进缺乏关注。
- 过度强调 MCP 治理工具调用，忽略工具调用**以外**的可观测性（规划质量、决策链路、上下文管理）仍需要从应用层做。
