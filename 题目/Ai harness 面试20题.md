# AI Harness 面试官评分手册

**方向**：生产 Agent 平台（三者混合：运行时 / 评测 / 管控）
**岗位画像**：技术专家 / 架构师
**题量**：20 题，分 5 个模块
**建议时长**：单题 5–8 分钟，可深挖追问；整套 45–60 分钟取其中 6–10 题
**最能拉开档次**：Q1 / Q2 / Q9 / Q10 / Q13 / Q19 / Q20

---

## 使用说明

- 每题给出四部分：**考察点**（看什么）、**参考答案要点**（及格线在哪）、**加分项**（优秀候选人会说什么）、**危险信号**（出现即扣分）。
- 参考答案要点是「评分锚点」，不要求逐字命中；候选人用自己的话覆盖核心思想即可。
- 加分项往往是区分「调过 API」与「设计过生产系统」的关键，重点关注。
- 危险信号若反复出现，说明候选人缺乏生产级 agent 系统的实战认知。
- 所有题目均为开放题，鼓励顺着候选人的回答追问到底，观察其思考深度而非记忆量。

# 一、运行时与编排架构

## Q1 　设计生产级 agent 运行时 harness 的核心循环与崩溃恢复

**🔵 考察点**

- 能否把 agent 抽象成一个清晰的状态机/循环，而不是一堆 if-else 拼起来的脚本。
- 对「副作用」与「纯决策」的区分意识——这是恢复语义的关键。
- 对持久化边界、幂等、at-least-once vs exactly-once 的工程理解。

**🟢 参考答案要点**

- 循环抽象为：状态(state) → 模型决策(plan) → 动作(act/tool) → 观测(observe) → 更新状态 → 判停。每一步是可记录、可重放的事件。
- 必须持久化的：会话/任务元信息、完整消息历史(或可重建它的事件日志)、每一步的工具调用与返回、当前 step 游标、预算计数器、外部副作用的执行记录(idempotency key + 结果)。
- 崩溃恢复靠事件溯源(event log) + 检查点(checkpoint)：重启后 replay 到最后一个已确认状态。已执行的副作用动作通过幂等键去重，不重复执行。
- 工具侧尽量幂等；不可幂等的动作(如转账)必须先写「意图记录」再执行，恢复时按记录判断「已发起 / 已完成 / 未知」三态处理。

**🟡 加分项**

- 主动区分「decision replay(重放模型决策)」与「effect replay(重放副作用)」，前者可重放、后者绝不重放。
- 提到 saga / 补偿事务处理跨多个不可逆动作的失败回滚。
- 讨论非确定性带来的恢复难题：重放时模型可能产出不同决策，如何用「固定历史 + 只续跑未完成步」规避。

**🔴 危险信号**

- 把「保存对话历史」等同于「可恢复」，忽略副作用重复执行问题。
- 认为重跑一遍整个任务就是恢复(对带副作用的 agent 是灾难)。
- 完全依赖框架黑盒，说不清状态存在哪、恢复时发生了什么。

## Q2 　停止条件设计

**🔵 考察点**

- 是否意识到 agent 是不定步数循环，停不下来 = 烧钱 + 失控。
- 能否把「停止」拆成多个正交维度并指明各自的判定方。

**🟢 参考答案要点**

- 正常完成：模型显式发出 finish / 输出终态，由 harness 校验产物 schema 后确认。
- 硬上限：step 数、wall-clock 时间、token/成本预算——由 harness 强制，模型无权绕过。
- 兜圈检测：识别重复的(动作,参数)序列或状态无变化，由 harness 基于轨迹判定。
- 卡住/低置信：模型反复表达不确定或反复重试同一失败动作，触发升级(换策略/转人工)。
- 每类停止都应产出结构化的「终止原因」，供上层路由与可观测使用。

**🟡 加分项**

- 把预算做成「分层预算」：总预算 + 子任务预算，子 agent 超支不拖垮全局。
- 兜圈检测用语义相似度而非精确匹配(参数微调但本质重复)。
- 停止条件可配置、可按任务类型分级，而非硬编码。

**🔴 危险信号**

- 只答「设个最大轮数」就完事。
- 把判停完全交给模型自己决定(模型会乐观地认为自己还能再试)。
- 没有成本/时间维度，只有逻辑完成维度。

## Q3 　单 agent 与多 agent 的 harness 差异

**🔵 考察点**

- 对多 agent 协作的真实复杂度(上下文隔离、聚合、失败传播)有无体感。
- 能否论证「什么时候该上多 agent」而不是无脑堆 agent。

**🟢 参考答案要点**

- 差异核心：上下文边界、通信协议、失败域。单 agent 是单一上下文；多 agent 需定义谁能看到什么。
- 子 agent 上下文应隔离传递：只给完成子任务所需的最小上下文，避免污染与 token 爆炸；结果以结构化形式回传编排者。
- 失败/超时：子 agent 失败应被编排者捕获并决策(重试/降级/放弃)，而非直接冒泡终止全局。设独立超时与预算。
- 防级联：子 agent 之间不直接互信结果，编排者做校验与裁决；避免一个错误结论被层层放大。

**🟡 加分项**

- 指出多 agent 的额外成本(协调开销、延迟叠加、调试更难)，主张「能单 agent 解决就别上多 agent」。
- 讨论编排拓扑(层级 / 黑板 / 流水线)各自适用场景。
- 提到子 agent 结果的冲突消解机制(投票 / 裁判模型 / 规则)。

**🔴 危险信号**

- 认为 agent 越多越强，盲目鼓吹多 agent。
- 让子 agent 共享同一份完整上下文，看不到隔离与污染问题。
- 子 agent 失败直接整体崩溃，无隔离与降级。

## Q4 　工具抽象层与非法工具调用的纠错反馈

**🔵 考察点**

- 工具层抽象的完整度(schema、校验、归一化、错误回传)。
- 对「错误反馈如何驱动模型自我纠正」的设计敏感度——这是 harness 的核心价值。

**🟢 参考答案要点**

- 工具抽象：声明式 schema(名称/参数/类型/约束/描述) + 参数校验 + 执行适配 + 结果归一化 + 错误结构化回传。
- 非法调用(幻觉参数/不存在的工具/类型错误)应被 harness 拦在执行前，生成清晰、可操作的错误消息回灌给模型：指出哪里错、期望什么、可选项是什么。
- 错误消息要「教模型怎么改」，而非只抛异常堆栈；保留上下文让模型下一步纠正。
- 对反复犯同样错误要有止损(N 次后升级 / 换路径)，避免无限纠错循环。

**🟡 加分项**

- 用 schema 约束 + 受限解码 / 函数调用接口从源头降低非法调用概率。
- 区分「可恢复错误(参数错,回灌纠正)」与「不可恢复错误(工具本身挂了,需降级)」。
- 工具结果归一化为统一信封(status/data/error)，让上层与模型处理一致。

**🔴 危险信号**

- 把工具原始异常 / 堆栈直接塞回模型上下文。
- 无参数校验，非法调用直接打到下游系统。
- 纠错无止损，模型可无限重试同一错误。

## Q5 　模型无关的抽象层

**🔵 考察点**

- 对不同模型 tool-calling 协议、上下文窗口、停止行为差异的实际认知。
- 抽象设计中「哪些细节会泄漏」的判断力——好架构师知道抽象的边界。

**🟢 参考答案要点**

- 抽象出统一的：消息格式、工具调用协议、流式接口、停止信号、用量统计。底层用 adapter 适配各家差异。
- 上层 agent 逻辑只依赖抽象接口；模型差异(JSON mode、function calling 格式、system prompt 习惯、并行 tool call 支持)收敛在 adapter。
- 最易泄漏的细节：上下文窗口大小、tokenizer 差异导致的计数、对 system/role 的不同敏感度、停止行为(有的爱多话有的爱早停)、并行工具调用能力、对长输出的截断行为。
- 策略：抽象「能力探测 / 特性标志」，让上层按 capability 而非按模型名分支。

**🟡 加分项**

- 承认「完美的模型无关抽象不存在」，关键 prompt 仍需按模型微调，主张用 capability flag 显式管理差异而非假装统一。
- 讨论评测如何保证换模型后行为不退化(见 Q15)。
- 提到成本 / 延迟 / 质量的模型路由策略建在这层之上。

**🔴 危险信号**

- 认为套个统一 SDK 就完全模型无关了，无视 prompt 与行为差异。
- 把模型特定的 hack 散落在上层业务逻辑里。
- 忽略 tokenizer / 窗口差异导致的上下文管理 bug。

# 二、上下文与记忆

## Q6 　上下文超窗管理策略

**🔵 考察点**

- 对长程 agent 必然超窗这一现实的应对能力。
- 压缩 / 摘要时「不丢关键依赖」的工程细致度。

**🟢 参考答案要点**

- 分层：窗口内只保留当前推理必需的(近期步骤、当前子目标、关键约束)；其余外置(向量库 / 结构化存储 / 文件)按需检索。
- 压缩触发：接近窗口阈值或步数到一定量时，对早期历史做摘要，但保留结构化关键事实(ID、句柄、未完成的待办、关键决策)不被摘掉。
- 对工具返回的大结果用「引用 + 摘要」：原文外置，上下文里留摘要与取回句柄。
- 保留「锚点信息」——后续步骤会引用的具体值(订单号、路径、token)绝不进摘要黑洞。

**🟡 加分项**

- 区分「可摘要的叙述」与「不可摘要的事实」，对后者结构化固定保留。
- 用分层记忆 + 滚动摘要 + 关键事实 pinning 组合。
- 讨论摘要本身可能引入错误，需可追溯回原文。

**🔴 危险信号**

- 无脑「截断最早消息」，丢掉早期工具返回的关键 ID。
- 把整段历史一股脑摘要，丢失精确值。
- 认为换个大窗口模型就不用管上下文了。

## Q7 　记忆系统设计与记忆污染防治

**🔵 考察点**

- 短期 / 长期记忆的边界与读写时机设计。
- 对「记忆污染(错误信息被反复检索强化)」这一隐蔽风险的认知。

**🟢 参考答案要点**

- 短期工作记忆：当前任务上下文，任务结束即弃。长期记忆：跨会话沉淀(用户偏好、稳定事实、过往结论)。
- 写入时机：长期记忆不应每句都写，应在「确认有价值且可信」时写入；带来源、时间戳、置信度。
- 检索召回：按相关性 + 时效性 + 可信度排序，融合进上下文时标注其为「记忆」而非当前事实。
- 防污染：写入前校验 / 去重；记忆带可信度与来源，可被新证据修正或淘汰；高风险结论不直接沉淀为「事实」。

**🟡 加分项**

- 记忆条目可版本化、可失效、可溯源，支持「遗忘」。
- 区分 episodic(发生过什么)与 semantic(稳定知识)记忆。
- 讨论检索增强的反噬：召回了错误记忆会自我强化，需要打分与衰减。

**🔴 危险信号**

- 把每轮输出都无条件写入长期记忆。
- 记忆无来源、无时效，错误信息永久驻留并反复污染。
- 把记忆检索结果当作绝对真值注入。

## Q8 　超大工具结果的处理决策放在哪一层

**🔵 考察点**

- 对「上下文经济学」的权衡能力。
- harness 层兜底 vs 交给 agent 自主决策的架构判断。

**🟢 参考答案要点**

- 默认 harness 层兜底：对超阈值结果自动做截断 / 摘要 / 外置 + 句柄，保证不撑爆窗口、不失控烧钱。
- 同时暴露能力给 agent：让 agent 可主动请求「取回完整内容 / 分页 / 按需查询」，兼顾自主性。
- 决策依据：结果大小、任务是否需要全文、下游步骤的引用模式。结构化大结果优先「可查询句柄」而非全量塞入。
- 权衡：全塞入 = 信息全但贵且可能超窗；摘要 / 外置 = 省但可能丢 agent 需要的细节。harness 兜底防失控，agent 自主补全细节。

**🟡 加分项**

- 主张「harness 设默认安全策略 + agent 可覆盖」的分层，而非二选一。
- 对结构化数据提供查询接口而非倾倒全文(让 agent 问而不是读)。
- 讨论摘要丢失关键字段的风险与可回溯设计。

**🔴 危险信号**

- 无条件把工具全量结果塞进上下文。
- 完全交给模型自己处理大结果，无 harness 兜底导致超窗 / 天价账单。
- 一刀切截断，丢掉后续需要的数据。

# 三、安全、权限与管控

## Q9 　副作用动作的权限、确认与可中断设计

**🔵 考察点**

- 对 agent 执行真实危险动作的敬畏心与管控设计。
- 「可拦截、可审计、可中断」三性是否齐全。

**🟢 参考答案要点**

- 动作分级：只读 / 低风险 / 高风险 / 不可逆，分级施加策略。高风险 / 不可逆动作需人工确认(human-in-the-loop)卡点。
- 可拦截：动作执行前经过策略网关(谁 / 在什么上下文 / 能做什么)，越权或越界被拦下。
- 可审计：每个动作记录发起者、参数、审批、结果、时间，形成完整审计链。
- 可中断：会话级 kill switch，能在任意步骤暂停 / 终止；已发起的不可逆动作有明确状态与补偿策略。

**🟡 加分项**

- 策略与代码解耦(policy as config)，分级阈值可运营调整。
- 「dry-run / 预览影响」让人工在确认前看到将发生什么。
- 默认最小权限 + 显式授权(deny by default)。

**🔴 危险信号**

- 给 agent 无差别的高权限，无分级无确认。
- 危险动作执行后才记录，无事前拦截。
- 没有中断机制，agent 跑飞了停不下来。

## Q10 　 Prompt injection 的纵深防御

**🔵 考察点**

- 是否理解 injection 来自工具返回 / 被处理内容这一被动攻击面。
- 能否论证「让模型自己识别注入」为何不可靠。

**🟢 参考答案要点**

- 纵深防御：输入侧(隔离不可信内容、标注来源)、模型侧(系统指令优先、降低对外部内容的盲从)、动作侧(关键防线——危险动作走独立授权,不受被处理内容左右)、输出侧(校验 / 过滤)。
- 核心原则：把「数据」与「指令」分离，外部内容默认当数据不当指令。
- 为何模型识别不可靠：injection 手法无穷且会进化，模型识别有漏报；一旦漏报且无下游硬约束，攻击即得手。必须有不依赖模型判断的确定性兜底(权限 / 沙箱 / 人工卡点)。
- 高风险动作的授权不能由「读了什么内容」决定，而由独立的策略与凭据边界决定。

**🟡 加分项**

- 提到最小权限 + 动作白名单从根上限制注入能造成的破坏。
- 对工具返回内容做来源标注与信任分级。
- 承认这是开放性对抗问题，主张「降低爆炸半径」而非「彻底防住」。

**🔴 危险信号**

- 认为「让模型识别并忽略恶意指令」就够了。
- 把外部内容与系统指令混在同一信任层。
- 高权限动作的触发依赖被处理内容，无独立授权边界。

---

## Q11 　多租户下的凭据隔离与越权阻断

**🔵 考察点**

- 多租户凭据管理的安全工程能力。
- 「凭据不进模型上下文」「越权在架构上阻断」的设计落地。

**🟢 参考答案要点**

- 凭据按租户 / 会话隔离存储于密钥管理系统，运行时按最小范围注入到「执行层」而非模型上下文。
- 凭据绝不进 prompt / 对话历史 / 日志明文；工具执行在隔离的执行环境内取用，模型只看到结果不看到密钥。
- 越权阻断靠架构而非靠 prompt：每次工具调用携带租户身份，下游鉴权按身份校验；租户 A 的会话在数据 / 网络 / 凭据层根本拿不到租户 B 的资源。
- 凭据轮转、最小权限、调用审计齐备。

**🟡 加分项**

- 短期凭据 / 动态令牌(STS 风格)替代长期密钥。
- 执行层与编排层分离，密钥只活在执行层。
- 对凭据使用做异常检测(异常调用量 / 跨租户尝试)。

**🔴 危险信号**

- 把 API key 放进 system prompt 或工具描述里。
- 靠 prompt 叮嘱模型「不要访问别人的数据」当隔离手段。
- 所有租户共享一套凭据，靠应用层逻辑区分。

## Q12 　代码执行类工具的沙箱设计

**🔵 考察点**

- 对执行不可信代码的隔离工程能力。
- 爆炸半径控制意识。

**🟢 参考答案要点**

- 隔离粒度：每次执行用一次性、强隔离的环境(容器 / microVM / gVisor 类)，会话间不复用敏感状态。
- 网络：默认禁止出网,按需白名单；入站隔离。文件系统：只读基镜像 + 临时可写层,执行后销毁。
- 资源：CPU / 内存 / 磁盘 / 进程数限额 + 执行超时,防资源耗尽。
- 爆炸半径：即使逃逸也困在最小权限的隔离域内,无生产网络 / 凭据 / 横向移动能力；监控 + 自动熔断。

**🟡 加分项**

- 用 microVM(Firecracker 类)而非纯容器以获得更强隔离。
- 默认无网络、无凭据、无持久化的「三无」执行环境。
- 对执行行为做 syscall / 网络审计,异常即杀。

**🔴 危险信号**

- 直接在共享主机 / 共享容器里跑用户 / 模型生成的代码。
- 执行环境能直连生产网络或持有云凭据。
- 无资源限额与超时,一段死循环拖垮节点。

# 四、评测、可观测与质量

## Q13 　面向轨迹的离线 eval harness 设计

**🔵 考察点**

- 理解 agent 评测与传统断言式测试的本质区别。
- 对「过程正确性」与「结果不确定性」的评测设计能力。

**🟢 参考答案要点**

- 任务集：覆盖真实分布 + 难度分层 + 边界 / 对抗用例；带可复现的环境与初始状态。
- 评分不只看终态：对轨迹打分(是否调对工具、步数效率、是否走弯路、是否产生不当副作用)，终态正确性 + 过程合理性结合。
- 应对不确定：同任务多次运行取分布(成功率 / 方差)而非单次；用 pass@k、稳定性指标。
- 评判方式：可程序化校验的用程序；开放性结果用 rubric + 模型评审(LLM-as-judge)并校准其可靠性。

**🟡 加分项**

- 区分「结果对但过程危险(瞎试中了)」与「过程稳健」，前者不算高分。
- 对 LLM-as-judge 做一致性校验与人工抽检，防裁判本身不可靠。
- 环境可重放、种子可固定，保证评测可复现。

**🔴 危险信号**

- 只用最终答案做精确匹配，无视过程与副作用。
- 单次运行就下结论，忽略 agent 的随机性。
- 完全信任模型评审分数，不做校准。

## Q14 　线上轨迹的根因定位与可观测体系

**🔵 考察点**

- 对 agent 这类非确定、多步系统的可观测设计能力。
- 能否区分「模型决策错」与「工具 / 环境错」。

**🟢 参考答案要点**

- 一条完整轨迹要可记录可回放：每步的输入上下文(渲染后的实际 prompt)、模型原始输出、解析后的动作、工具调用与返回、决策耗时与用量。
- Trace 贯穿异步 / 并行步骤(子 agent、并行工具)用统一 trace id 串联。
- 区分错误类型：工具返回错误码 / 超时 → 环境侧；模型选错工具 / 参数 / 逻辑 → 决策侧；据此分流定位。
- 支持「按轨迹回放」复现问题：固定历史重跑某步，观察模型行为。

**🟡 加分项**

- 记录「渲染后的真实上下文」而非模板，定位 prompt 拼装 bug。
- 对决策侧问题能进一步归因到 prompt / 模型版本 / 上下文污染。
- 采样 + 全量关键事件的分层存储，平衡成本与可观测。

**🔴 危险信号**

- 只记最终结果，出问题无从复现。
- 无法区分是模型蠢还是工具挂，一律归咎模型或一律归咎环境。
- 异步 / 多 agent 轨迹断裂，无法串成一条链。

---

## Q15 　模型升级回归的持续评测与发布门禁

**🔵 考察点**

- 对「模型静默退化」这一生产风险的防控能力。
- 评测集防过拟合的工程意识。

**🟢 参考答案要点**

- 建立持续评测：新模型 / 新 prompt 上线前跑回归评测集，与基线对比关键指标，设门禁(回退超阈值则阻断)。
- 区分整体均值与分项：总成功率不降但某类任务暴跌也要拦，做切片对比。
- 防过拟合：评测集分公开 / 私有(holdout)，私有集不进迭代；定期刷新用例；关注「迭代时没见过」的分布。
- 灰度上线 + 线上指标监控，门禁挡不住的退化靠灰度兜底回滚。

**🟡 加分项**

- 影子流量 / 双跑对比新旧模型在真实流量上的行为差异。
- 评测集随业务演进持续扩充，防止「刷分」。
- 把行为回退(不只是准确率,还有成本 / 延迟 / 越界率)纳入门禁。

**🔴 危险信号**

- 供应商升级就直接全量切，无回归评测。
- 只看总成功率，忽略分项退化。
- 评测集长期不变且参与调参，分数虚高。

## Q16 　生产 agent 平台的质量与效率度量

**🔵 考察点**

- 能否给出超越「成功率」的多维指标体系。
- 对指标间此消彼长的运营理解。

**🟢 参考答案要点**

- 质量维度：任务完成率、完成质量(rubric / 人工)、正确性、不当副作用率、越界 / 安全事件率。
- 效率维度：平均步数、token/成本、端到端延迟、首响时间。
- 人机维度：人工介入率、升级率、用户满意 / 采纳率。
- 权衡：提升成功率常以更多步数 / 成本 / 延迟为代价；降成本(小模型 / 裁上下文)可能降质量；减人工介入可能升风险。需按业务设定可运营的目标区间而非单点最优。

**🟡 加分项**

- 区分「线上业务指标」与「离线评测指标」并建立对应关系。
- 强调防止指标被刷(古德哈特)：如只优化成功率会鼓励瞎试。
- 按任务类型分别设指标基线，而非全局一刀切。

**🔴 危险信号**

- 只报成功率一个数。
- 无成本 / 延迟 / 安全维度。
- 看不到指标间的取舍，追求单一指标极值。

# 五、性能、成本与工程权衡

## Q17 　端到端延迟优化及其正确性风险

**🔵 考察点**

- 对 agent 延迟来源(串行多轮模型调用)的准确认知。
- 每种优化「省时间换什么风险」的清醒权衡。

**🟢 参考答案要点**

- 主因：串行的多轮 LLM 调用 + 工具往返。手段(按收益排序大致)：流式输出降首响、并行无依赖的工具调用、合并 / 减少不必要的步骤、用更快 / 更小模型跑简单步、缓存(prompt 前缀缓存 / 结果缓存)、推测执行 / 预取。
- 风险：并行工具调用要求步骤间真无依赖,错并行会用脏数据；步骤合并可能让模型一步做太多易出错；小模型提速但可能降质量；推测执行做错了浪费且可能引入不一致；缓存可能命中过期 / 不该复用的结果。
- 原则：先减少轮数(最大头)，再压单轮延迟；每项优化都要有正确性护栏。

**🟡 加分项**

- 量化各环节耗时占比再优化(别拍脑袋)。
- prompt 前缀缓存(KV cache 复用)对长 system prompt 收益大。
- 对推测 / 预取设回退,错了不影响正确性。

**🔴 危险信号**

- 无脑并行所有工具调用,无视依赖关系。
- 为提速强行合并步骤导致正确率下滑还不自知。
- 缓存不设失效与正确性边界,复用了过期结果。

## Q18 　成本控制体系

**🔵 考察点**

- 对 agent 高 token 成本的体系化控制能力。
- 成本与成功率间设定可运营策略的能力。

**🟢 参考答案要点**

- 预算：任务级 + 子任务级预算，超支熔断或降级。
- 模型分级路由：简单 / 分类步用小模型，复杂推理用大模型；按难度动态选型。
- 上下文裁剪：只带必需上下文，压缩历史，外置大结果，降低每轮 token。
- 缓存：prompt 前缀缓存、相同子问题结果缓存。策略：在「成本上限」与「成功率下限」之间设可运营区间，按业务价值分配预算。

**🟡 加分项**

- 贵的大模型只在「值得」的步骤用，先用小模型判断是否需要升级。
- 对高频固定 system prompt 用前缀缓存显著降本。
- 用离线评测验证「降本策略」对成功率的实际影响，数据驱动调参。

**🔴 危险信号**

- 全程一个最贵模型梭哈，无路由无预算。
- 为省钱激进裁上下文 / 换小模型，成功率暴跌还不监控。
- 无任务级预算，单个任务可无上限烧钱。

## Q19 　自研 harness vs 基于开源框架二次开发的选型

**🔵 考察点**

- 架构师的技术选型判断框架(而非站队结论)。
- 对生产级要求(可观测 / 可控 / 稳定 / 维护)的清醒认知。

**🟢 参考答案要点**

- 判断维度：控制粒度需求(对循环 / 停止 / 状态的掌控)、可观测与可调试、生产稳定性、长期维护成本、与现有基础设施(鉴权 / 网关 / 监控)的契合、团队规模与能力。
- 开源框架：起步快、生态好，但黑盒程度高、定制深处易受框架约束、生产级可观测 / 可控常需自己补。
- 自研：控制力强、贴合自身基础设施，但投入大、需长期维护、重复造轮子风险。
- 务实路径：常见是「核心运行时(循环 / 状态 / 停止 / 可观测)自研或薄封装以保控制力，外围(工具集成 / 部分编排)借力开源」，而非全有或全无。

**🟡 加分项**

- 强调「可调试性」对 agent 系统的极端重要性，作为选型关键权重。
- 给出随团队 / 业务阶段演进的选型路线，而非一锤定音。
- 提到框架锁定(lock-in)风险与退出成本评估。

**🔴 危险信号**

- 无条件「自研更好」或「用 X 框架就行」式站队。
- 只看 demo 跑得快，忽略生产可观测 / 可控 / 稳定性。
- 全盘押注某框架黑盒，出问题无法深入。

## Q20 　 harness 与模型能力的边界（开放题）

**🔵 考察点**

- 对「确定性工程约束」与「模型自主决策」分工的深层理解。
- 前瞻性：边界随模型能力演进如何移动，架构如何预留空间。

**🟢 参考答案要点**

- 应由 harness 强约束(确定性工程)：停止条件、预算、权限 / 授权、沙箱隔离、审计、不可逆动作的卡点——这些是安全与成本的底线，不该赌模型自觉。
- 可信任模型自主：具体的规划、工具选择、内容生成、纠错策略等「智力活」，模型越强越该放权，过度硬编码反而限制能力。
- 边界移动：模型越强，可把更多「编排 / 判断」从硬规则交还给模型；但安全 / 成本 / 合规的硬边界应长期保留甚至加强(能力越强破坏力越大)。
- 架构预留：把策略与能力解耦、约束做成可配置的「护栏」而非写死的流程；让上层逻辑能随模型增强而简化，而护栏独立演进。

**🟡 加分项**

- 提出「护栏(guardrail)恒定、编排(orchestration)随模型退化」的演进观：模型越强，编排代码越少。
- 区分「为安全而约束」(不可让步)与「为弥补模型不足而约束」(随能力放开)。
- 有自己的判断与论证，而非复述常识；承认这是动态、需持续校准的边界。

**🔴 危险信号**

- 把安全 / 预算 / 权限也交给模型自觉，无确定性兜底。
- 另一极端：什么都硬编码，把强模型当弱模型用，系统僵化。
- 没有演进视角，认为边界一旦划定永不变。
